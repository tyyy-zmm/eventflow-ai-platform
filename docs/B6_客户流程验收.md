## 2. 第一步：真实客户身份

- `Accounts` 实现账号注册、密码登录、会话创建、验证、撤销和过期清理。
- 用户名规范化为小写，数据库唯一约束；账号 ID 使用与旧实验用户不同的高位范围，新用户 DTO 以字符串返回 ID。
- BCrypt cost 12 保存密码摘要。密码至少 12 个字符且 UTF-8 不超过 72 字节，防止 BCrypt 截断造成口令歧义。
- 登录产生 256-bit 随机会话，数据库只保存令牌 SHA-256 摘要；Cookie 为 `HttpOnly; SameSite=Strict; Path=/v2`，8 小时有效。
- 同账号最多保留 8 个会话，登录时通过账号行锁串行化淘汰决策。退出登录删除当前会话摘要。
- 账号与会话在 MySQL 中，不依赖 Redis 登录态。Redis 不可用不应连带阻断既有订单查询/确认/取消。
- Cookie 写请求检查 CSRF；登录注册要求 JSON，非安全方法检查 Origin。请求体最多 16 KiB；密码哈希并发最多 4，IP/账号尝试次数本地有界限流。
- 默认启动不再接受旧实验 HMAC Bearer，只有显式开启 `upgrade.benchmark=true` 的实验进程接受。普通注册账号不能获得管理员角色。
- 页面请求携带期待的 `X-Account-ID`，服务器与真实 Cookie 身份比对。另一个标签页更换账号时，旧页面收到 `SESSION_CHANGED` 后清空旧用户视图并要求重新登录。这个头只用于防混用，不能用于冒充用户。

没有接第三方短信、找回密码或生产统一身份平台；不是生产级身份系统的完整替代。当前仅本机 HTTP loopback，HTTPS 部署需要 Secure Cookie 与可信反向代理配置，不能直接把开发服务器暴露公网。

## 3. 第二步：真实商家与券展示

- 未登录可浏览商家、按分类筛选、按关键词搜索、查看券详情；无结果、依赖异常与加载中分别展示。
- 商家详情通过 `ShopCache` 读取允许短暂陈旧的名字/介绍；商家目录筛选和扩展元数据目前查询 MySQL，不把整页所有查询宣称为 Redis 命中。
- 券价格、活动时间和剩余库存直接读 MySQL，不使用逻辑过期介绍缓存作交易依据。
- 页面报价仅供展示，真正建单仍在服务端活动锁内取价格快照和条件扣库存。浏览时显示剩余不承诺下一次抢购一定成功。
- 每张券明确每人每场一次、5 分钟内确认、取消/过期不能重购、仅本地演示不涉及支付/核销。
- PC 和手机均可操作；真实图片可用、按钮内容不溢出、页面无水平滚动。弹窗使用原生 dialog，支持 Escape 与焦点恢复。

## 4. 第三步：完整订单链路

```text
注册或登录
  -> 浏览商家与实时券信息
  -> 生成客户端 requestId，并先写入当前账号的 localStorage
  -> POST /v2/requests
  -> 202 只显示受理中
  -> 通过本人请求/订单联合接口轮询
  -> SUCCEEDED + PENDING_CONFIRM：展示订单和确认倒计时
  -> CONFIRMED / CANCELLED / EXPIRED：展示真实订单终态
```

请求和订单是两层状态。取消订单后，原请求仍是“成功建单”，订单状态变成 CANCELLED；页面优先展示订单当前状态，不把建单事实改成失败。

### 4.1 未知结果与重复提交

1. 浏览器先持久化 UUID，再发送请求；无法写本地存储时不发送下单。
2. 本地记录按用户 ID 隔离，不保存密码、Cookie 或 CSRF。
3. 网络中断、超时或 5xx 不等于交易失败，保留原键，显示“结果待确认”。
4. 页面刷新后先恢复会话，再按原键调用 `/v2/account/requests/by-key/{key}` 查找。
5. 暂未查到不证明永远未提交；允许用户使用原键重试，不生成新键。
6. 只有看到服务端请求终态，或明确受理前拒绝的参数/活动错误，才清除这条待确认记录。
7. 同页提交按钮互斥；跨页即使生成不同键，数据库每用户/活动唯一约束仍防止重复订单，但不声称浏览器能跨标签页原子创建同一个请求键。

本地存储不包含秘密，但包含待确认活动标题和请求键。退出后不显示上一账号记录，为原账号下次登录恢复保留它们；共用电脑需注意本地浏览器数据。清除浏览器数据会丢失待确认键，但已落库订单仍可从本人订单列表找回。

### 4.2 确认、取消与到期

- 倒计时按服务器时间校正，客户端到零只停止确认按钮，不自行断言订单已过期。
- 服务器扫描和查询时检查到期，仍由 MySQL 状态机执行库存释放。
- 确认/取消后重新读取订单，若并发操作或过期先胜出，展示服务器实际状态，不显示乐观假成功。
- 取消前二次确认，明确不能重购同场。取消、重复取消、到期都依赖既有事务及状态条件，只回补一次。
- 确认仅是本地业务确认，不是微信/支付宝支付；没有支付成功、退款或核销承诺。

## 5. 验收结果

### 5.1 后端：69 项通过

由单元测试与两次专项集成命令分别执行，不是普通 `mvn test` 自动连接所有中间件。普通单元命令会跳过需 `UPGRADE_INTEGRATION=true` 的测试，归档的是各专项实际执行后的记录。

| 测试组 | 数量 | 主要覆盖 |
|---|---:|---|
| 原有单元测试 | 25 | 交易状态机、约束、事务、令牌校验、投递错误 |
| AccountsTest | 7 | 密码/会话摘要、用户名唯一、登录失败、会话撤销/过期/上限、本人查询与过期回补 |
| CustomerAuthTest | 9 | 公开目录、私有接口、CSRF、同源、管理员隔离、请求体限制、实验身份默认关闭、跨标签页账号校验 |
| MiddlewareTest | 22 | 真实 MySQL/Redis/Kafka 的并发、幂等、缓存、投递等既有回归 |
| CustomerHttpTest | 6 | 实际 HTTP 注册登录、目录、Kafka 异步订单、确认、取消、重购拒绝、越权和超时 |

超时测试通过把本地测试订单截止时间设到过去来触发，不冒充等待了完整 5 分钟。测试仅使用独立演示数据库。

### 5.2 浏览器：8 组通过

使用 Playwright 驱动本机已安装 Chrome，无外部模型调用。

1. 未登录目录、分类、搜索无结果和桌面布局。
2. 注册、HttpOnly Cookie、刷新恢复登录。
3. 真正发送请求、Kafka 消费建单、前端本地确认。
4. 取消订单、再次购买同场被拒绝。
5. 将真实已提交的 POST 响应丢弃，同时中断查询；刷新后使用相同 requestId 重试，返回同一个服务端请求，页面只有一张对应订单。
6. 390×844 手机目录/券详情/订单布局与 Escape 关闭弹窗；桌面 1440×1000。
7. 禁止 localStorage 写入时，下单 POST 发送数为 0。
8. 退出、换账号无前账号订单；旧标签页在 Cookie 被另一账号替换后要求重新登录；原账号再次登录可找回历史。

浏览器截图检查图片加载与按钮溢出，并人工复核了桌面列表、手机弹窗和订单排版；浏览器运行时异常为 0。真实密码仅在测试进程中随机生成，没有写入证据文件。

## 6. 复现

后端目录：

```bash
bash scripts/local.sh up
bash scripts/local.sh package
bash scripts/local.sh integration
bash scripts/local.sh customer-test
bash scripts/local.sh start --upgrade.demo-data=true
```

前端目录另开终端：

```bash
npm run dev -- --port 4176 --strictPort
```

访问 `http://127.0.0.1:4176/life/`，自行注册新账号后抢券。注册密码至少 12 字符，勿使用其他网站的真实密码。旧的 4175 页面不受影响。

浏览器测试位于 `eventflow-ui/tests/life-browser.mjs`。环境已安装 Playwright 时可直接执行；也支持 `PLAYWRIGHT_MODULE` 指向已有 Playwright 的模块路径，`LIFE_BROWSER_CHANNEL=chrome` 复用系统 Chrome。`LIFE_EVIDENCE` 指定截图结果目录，`LIFE_URL` 可改端口。脚本只针对本地示例商家生成测试账号与订单，不应对生产环境执行。

`npm run build` 同时构建原入口和新 `/life/` 入口。真实部署需正确配置 `/v2` 同源反向代理，不能只双击构建出的 HTML。
