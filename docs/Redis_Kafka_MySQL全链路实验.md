# Redis、Kafka、MySQL 全链路实验

## 链路与方法

正式路径为：HTTP 请求 → Redis Lua 预扣 → MySQL 请求与 Outbox → Kafka → MySQL 建单 → Redis 确认。每轮使用新活动，1000 个不同用户争抢 100 份库存，16 个并发客户端；共运行 3 轮。

入口 QPS 和 P95 包含成功受理与售罄拒绝。建单端到端 P95 按客户端发出请求到 MySQL 写入终态计算。实验在同一台电脑上运行单节点 MySQL、Redis、Kafka，不能外推生产容量。

## 结果

| 轮次 | HTTP QPS | HTTP P95 | 受理/售罄 | 最终订单 | 建单端到端 P95 | 进入 MySQL 的请求 | 违规 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1329.8 | 76.6 ms | 100 / 900 | 100 | 1295 ms | 100 | 0 |
| 2 | 1344.7 | 87.9 ms | 100 / 900 | 100 | 1201 ms | 100 | 0 |
| 3 | 1879.3 | 61.0 ms | 100 / 900 | 100 | 1098 ms | 100 | 0 |

三轮入口 QPS 中位数为 1344.7，最差 HTTP P95 为 87.9ms，最差建单端到端 P95 为 1.295s。每轮只有 100 个预扣成功请求进入 MySQL，最终生成 100 个订单；900 个售罄请求未进入数据库。每轮结束时 Redis `PENDING`、未应用补偿动作、MySQL 待处理请求及两类一致性违规均为 0。

## 解释边界

该实验说明在固定“千人抢百券”场景下，入口能够快速拒绝无库存请求，并且 Kafka 异步链路最终收敛。1344.7 QPS 包含 900 个 Redis 快速拒绝，不能写成“每秒创建 1344 个订单”。100 个订单的完成时间受单活动 MySQL 行锁、Outbox 轮询和 Kafka 消费影响，端到端 P95 约 1.1–1.3 秒。

正式证据：`evidence/full-chain-1790100161390/`，其中 `results.json` 保存三轮数据，`*-raw.json` 保存逐请求状态和延迟，`server.log` 保存运行日志。

## 简历取值

简历优先使用隔离 A/B 实验中的“进入 MySQL 请求减少 90%、业务 SQL 减少 89.1%”，因为它直接回答 Redis 的作用。全链路 QPS/P95 留作面试扩展，用来说明你区分入口响应能力、成功订单吞吐和异步建单延迟。
