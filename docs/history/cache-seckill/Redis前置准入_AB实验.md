# Redis 前置准入 A/B 实验

## 实验问题

在 1000 个不同用户并发争抢 100 份库存时，先用 Redis Lua 原子完成库存预扣和一人一单校验，能够减少多少进入 MySQL 的请求和业务 SQL？入口吞吐与延迟如何变化？

本实验只回答上述问题。它不证明线上最大吞吐，也不把售罄后的快速拒绝算成成功建单能力。

## 对照设计

两组均通过相同的 HTTP、鉴权和同步 MySQL 建单逻辑，MySQL 仍以条件扣减和唯一约束作为最终正确性防线。唯一变量是 Redis 是否位于数据库之前：

- MySQL-first：1000 个请求全部进入 MySQL，由数据库完成库存判断，最终 100 单成功、900 单售罄。
- Redis-first：Redis Lua 原子校验用户资格、预扣库存并记录请求结果；仅 100 个预扣成功的请求进入 MySQL，其余 900 个在数据库前返回售罄。

每种模式运行 3 轮，每轮 1000 请求、100 库存、64 并发。各轮使用新的活动 ID，并轮换两种模式的执行顺序。应用 JVM 堆 384 MiB、HTTP 线程 48、MySQL 连接池 12；MySQL 8.4 与 Redis 7.4 均为本机 Docker 单节点。

为隔离 Redis 准入本身，本实验关闭 Kafka/Outbox 后台任务并同步完成建单。鉴权使用仅在 benchmark 模式开启的 HMAC 身份，不包含客户 Session 查询。

## 数据口径

- 数据库入口请求：HTTP 返回中的 `enteredDatabase=true` 数量，表示请求真正进入了统一 MySQL 交易方法。
- 业务 SQL：每轮负载前清空 MySQL `performance_schema.events_statements_summary_by_digest`，负载后汇总涉及 `ux_activity`、`ux_request`、`ux_order`、`ux_outbox` 的语句次数。
- QPS：固定 1000 个请求在 64 并发闭环下的实际完成速率，包括成功与售罄响应。
- P95：一轮中 95% HTTP 请求的耗时不超过该值，包括成功与售罄响应。
- 正确性：成功订单数必须等于 100，且库存不变量、请求/订单状态不变量均为 0 违规。

## 正式结果

| 轮次 | 模式 | 进入 MySQL | 业务 SQL | 入口 QPS | HTTP P95 | 成功订单 | 售罄 | 不变量违规 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | MySQL-first | 1000 | 10100 | 230.8 | 406.9 ms | 100 | 900 | 0 |
| 1 | Redis-first | 100 | 1100 | 1654.7 | 278.7 ms | 100 | 900 | 0 |
| 2 | Redis-first | 100 | 1100 | 1838.6 | 214.8 ms | 100 | 900 | 0 |
| 2 | MySQL-first | 1000 | 10100 | 279.7 | 255.8 ms | 100 | 900 | 0 |
| 3 | MySQL-first | 1000 | 10100 | 279.1 | 293.9 ms | 100 | 900 | 0 |
| 3 | Redis-first | 100 | 1100 | 2101.0 | 213.1 ms | 100 | 900 | 0 |

三轮中，Redis-first 均将数据库入口请求从 1000 降至 100，减少 90%；业务 SQL 从 10100 降至 1100，减少 89.1%。中位入口 QPS 从 279.1 提升至 1838.6，约为 6.6 倍；但该 QPS 包含 900 个 Redis 售罄响应，不能表述为“每秒成功创建 1838 个订单”。两组每轮均仅成功创建 100 个订单。

## 为什么 SQL 不是刚好减少 90%

MySQL-first 的 900 个售罄请求仍会执行活动加锁、幂等检查、请求落库、库存条件扣减、终态更新与补偿动作记录，但不会插入订单；Redis-first 的 100 个准入请求均成功建单。最终 SQL 从 10100 降至 1100，即减少 89.1%，与 `performance_schema` 的逐语句统计一致。

## 能支持与不能支持的结论

可以支持：在库存明显小于请求量的本地抢购场景中，Redis Lua 前置准入能够在保持最终订单数和数据库兜底约束不变的情况下，显著减少无效请求进入 MySQL。

不能支持：线上峰值 QPS、集群扩展能力、Redis 主从切换期间的数据安全，以及跨可用区容灾。本实验本身只比较准入位置；后续正式链路实现与故障证据见 `Redis_MySQL一致性与故障恢复.md` 和 `Redis_Kafka_MySQL全链路实验.md`。

## 证据与复现

正式证据目录：`evidence/redis-db-1790100701576/`。

- `results.json`：六轮汇总及逐类 SQL digest。
- `summary.json`：90% 数据库入口降幅、89.1% SQL 降幅与 QPS/P95 摘要。
- `*-raw.json`：每个 HTTP 请求的状态、原因、延迟及是否进入数据库。
- `server.log`、`environment.json`：服务日志和实验环境。

复现命令：`bash scripts/local.sh redis-db-benchmark`。冒烟验证可使用 `bash scripts/local.sh redis-db-benchmark --smoke`。

## 简历使用建议

结合已完成的正式链路、补偿与对账，可写为：

> 秒杀准入：基于 Redis Lua 原子完成库存预扣与一人一单校验，将无效请求拦截在数据库前；本地三轮千人抢百券实验中，进入 MySQL 的请求减少 90%、业务 SQL 减少 89.1%，并由 MySQL 条件扣减与唯一约束兜底。

面试中应说明：90% 和 89.1% 来自隔离 A/B 实验；正式链路另外经过 Redis 预扣、MySQL Outbox、Kafka 建单、补偿动作和超时对账测试，不能把两套实验的指标混成同一个线上结论。
