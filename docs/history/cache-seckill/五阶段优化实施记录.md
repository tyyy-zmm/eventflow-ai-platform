## 秒杀：正确性优先

### 孤儿预占裁决

过去的风险是“数据库暂时查不到请求 → 直接释放 Redis 库存”，但原事务可能随后提交。

现在 `Trading.adjudicateReservation` 与受理使用同一个活动行锁：

1. 若数据库已有请求，按已提交状态处理，ACCEPTED 不释放。
2. 若确实没有，写入同一 `(user_id, request_key)` 的 EXPIRED 请求和 RELEASE 动作。
3. 数据库提交后执行 Redis 释放；迟到受理只能返回已有终态。
4. 释放失败由持久任务重试，不能因为 Redis 返回非法状态就将任务标为成功。

未知提交结果不会触发盲目回补。客户端用原请求键重试或查询；对账在事务锁下判断实际提交结果。原键一旦终态不再复用，新尝试需要新键。

### Redis 状态丢失与 epoch

缺失库存键返回 `RESERVATION_RECOVERY_REQUIRED`，不会在线从 MySQL 的 available 直接 SET 库存。显式恢复接口：

`POST /v2/admin/activities/{id}/recover`

它沿用已有管理员认证，目前仅适用于显式开启 benchmark 的本地管理流程，不向普通注册账户开放。

恢复步骤：

1. 锁定数据库活动行，阻止并发受理、建单和订单状态修改。
2. 将尚未建单的 ACCEPTED 请求转为 EXPIRED（原因 RESERVATION_RECOVERY），保留已有订单。
3. 按数据库订单状态重建 Redis 库存、请求状态及已购买用户集合。取消或过期订单也保留购买限制。
4. 安装新 epoch 的暂停快照；提交数据库及恢复审计后，条件激活该 epoch。
5. 预占 Lua 将 epoch 与结果一起返回；受理事务校验数据库 epoch，拒绝旧批次迟到请求。

恢复中断或提交结果未知时不会主动激活；重复显式恢复生成新 epoch。正常交易事务不调用 Redis；管理恢复为了获得一致快照，会在活动锁内执行有界 Redis 重建。这是明确的可用性取舍，不适合无限规模的活动。

当前单活动恢复上限为 10,000 条请求，超过返回 RECOVERY_BATCH_REQUIRED；需后续实现暂停期间的分批构建和切换，不能把现有方法当任意规模恢复。恢复期间的排队请求会失败，需要客户端展示终态。新迁移为 V5__reservation_epoch.sql。

### Kafka 与补偿

消费者数据库事务完成后确认消息。Redis 补偿由独立调度任务应用，失败退避，不再让一次 Redis 故障拖住已提交订单的 Kafka ack。售罄提示只是短 TTL 优化，写入失败不会撤销数据库提交。

## 缓存：选型与边界

| 项目 | 实现 | 选择理由 |
|---|---|---|
| L1 | Caffeine，最多 10,000 条、最长 1 秒 | 减少热点请求网络访问，有界内存，复用成熟淘汰机制 |
| L2 | Redis，软过期 5 秒，硬过期 15～16.5 秒 | 共享数据和重建锁；保留逻辑过期设计 |
| 过期继承 | Entry 新增 hardUntil；L1 取剩余硬期限与本地期限的较小值 | 复制到 L1 不重新赋予完整生命周期 |
| 防穿透 | 空值缓存 1 秒，可进入 L1 | 适合重复查询相同不存在 ID；暂不加布隆过滤器 |
| 重建 | Redis owner 锁；2 线程、16 队列；数据库 4 槽位 | 合并同键数据库加载，限制回源并发和任务积压 |
| 更新失效 | 同事务持久失效任务；Lua 删除 L2/锁并发布通知 | 数据库提交与任务可靠性由现有 Outbox 式机制承担 |
| 多实例 | Redis Pub/Sub；重订阅清空 L1 | 低复杂度加速失效；丢消息由 TTL 兜底，不宣称可靠投递 |
| 旧读取回填 | 固定 256 个 generation guard，读取前取代数，写 L1 前再校验 | 避免失效后旧读取重新填充；固定内存，不维护无界版本表 |
| Redis 故障 | 有效 L1 仍可读；否则每实例每秒最多 20 次数据库降级尝试，仍受 4 槽位约束 | 商家介绍允许有限降级，避免依赖故障造成无界回源 |

固定窗口可能在秒边界产生短时突发；多实例总降级预算随实例数增加。SQL 超时设置为 2 秒。此处不构成严格的集群限额或端到端 SLA。

旧格式 Redis Entry 没有 hardUntil，可以继续从 Redis 读取，但不会提升到 L1。广播未丢失时，代数校验阻止旧读取回填；广播丢失时依靠本地 TTL 及源数据绝对硬期限约束，不能保证更新后所有请求立刻读到新值。缓存不参与交易库存和价格裁决。

## 本轮验证

前一轮执行（88 项）：

```bash
UPGRADE_INTEGRATION=true UPGRADE_RELIABILITY_INTEGRATION=true bash scripts/verification.sh package
```

此命令执行 clean package，避免重命名的迁移残留在 target。该轮共 88 项测试全部执行通过，失败 0、错误 0、跳过 0；包含 26 项真实中间件测试、6 项 MySQL/Redis 可靠性测试、6 项客户 HTTP 测试和 50 项单元测试。

已验证的重点包括：

- 孤儿裁决和迟到受理竞态只有一个持久结果。
- 已提交 ACCEPTED 不被误释放。
- Redis 状态缺失时拒绝新增，未完成补偿仍可重试。
- 恢复后旧 epoch 不可建单，迟到消息不复活已过期请求。
- 取消后重复购买限制在 Redis 重建后仍保留。
- Kafka 已提交事务不依赖 Redis 修复成功才确认。
- 第二次热点读取命中本地缓存；失效期间旧读取不能重新填入 L1。
- Redis 两个缓存实例之间的通知失效，断开订阅后的 TTL 兜底。
- L1 不延长 Redis 剩余硬期限，Redis 故障降级预算有界。

单独执行 `local.sh reliability-test` 默认使用 Redis DB14 和进程内 H2；本轮全量验证通过 `verification.sh` 切换为真实 MySQL。该可靠性测试使用同进程的两个 ShopCache 实例；另有双独立 JVM 的正式 HTTP 缓存对比。测试使用独立活动 ID，不 FLUSHDB。

本轮全量证据见 `evidence/verification-20261002/test-summary.json` 与 `build.log`。`evidence/upgrade-20261002` 是此前仅执行 54 项测试的记录，保留以便追溯。
