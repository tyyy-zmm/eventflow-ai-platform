# 完整成功下单容量实验

## 1. 实验目的

此前的“1000 人争抢 100 份库存”实验主要验证 Redis 前置拦截能力。其入口 QPS 包含 900 个售罄快速失败请求，不能等同于成功下单吞吐。

本实验将每轮库存设置为请求数，并为每个请求分配不同用户，使全部请求都必须经过：

`HTTP -> Redis Lua 预扣 -> MySQL 请求与 Outbox -> Kafka -> MySQL 建单 -> Redis 确认`

因此，本实验中的 `successfulOrderQps` 表示完整链路最终成功订单吞吐，不包含售罄快速失败。

## 2. 实验设计

- 环境：本地单机，Java 堆 384MB，Tomcat 48 线程，HikariCP 12 连接。
- 中间件：单节点 Redis、MySQL 8.4、单 Broker Kafka，Kafka 消费并发为 2。
- 热点模型：每轮只使用一个活动，Kafka 以活动 ID 为 key，同活动消息保持顺序。
- 请求规模：每档并发运行 3 轮，每轮 1000 个不同用户、1000 份库存。
- 并发档位：4、8、12、16。
- 正确性条件：每轮必须 1000 次 HTTP 受理、1000 个成功订单、错误率为 0，且无超卖、重复订单、状态违规、当前活动 Redis 待确认或未应用补偿。
- 吞吐口径：从首个请求发出到最后一个订单完成的时间计算完整成功下单 QPS。
- 延迟口径：从单个请求发出到对应 MySQL 请求进入 `SUCCEEDED` 的端到端耗时。

运行命令：

```bash
bash scripts/local.sh order-capacity-benchmark
```

原始证据位于 `evidence/order-capacity-1790134334287/`。

## 3. 正式结果

| 并发 | 三轮中位 HTTP 受理 QPS | 三轮中位成功下单 QPS | 最差下单 P95 | 最差下单 P99 | 成功订单 | 错误率 |
|---:|---:|---:|---:|---:|---:|---:|
| 4 | 249.4 | **84.8** | 7.530s | 7.972s | 3000/3000 | 0% |
| 8 | **267.3** | 81.0 | 8.678s | 8.918s | 3000/3000 | 0% |
| 12 | 248.9 | 68.5 | 11.584s | 11.894s | 3000/3000 | 0% |
| 16 | 210.4 | 65.8 | 11.025s | 11.322s | 3000/3000 | 0% |

合计完成 12,000 次完整下单，12,000 个订单全部成功；库存违规、状态违规、重复订单和当前活动遗留补偿均为 0。

## 4. 结果解释

1. **成功下单吞吐不是 1839 QPS。** 1839 QPS 是低库存场景下包含售罄响应的 Redis 入口吞吐；当前实验测得单热点活动完整成功下单吞吐约为 85 单/秒。
2. **异步受理高于最终建单吞吐。** HTTP 可以约 250 QPS 接收并持久化请求，Kafka 将瞬时流量转化为后端可控的订单处理队列。
3. **增加并发不会无限提高吞吐。** 同一活动的 Kafka 消息进入同一分区，MySQL 又会锁定同一活动行完成条件扣减；并发从 8 提升至 16 后，锁竞争和排队使吞吐下降、尾延迟升高。
4. **P95 不是在线请求响应时间。** 接口在持久受理后即返回 202；表中 7~11 秒是 1000 个请求突发进入后，排队直到订单最终生成的耗时，不能解释成同步接口 P95。
5. **本地结果不能外推生产环境。** 单机、单 Redis、单 Kafka Broker 和本地 MySQL 只用于方案验证及相对比较，不代表线上集群容量。

## 5. 简历与面试用法

简历若需要完整成功吞吐数据，可写：

> 在单机单热点全链路实验中完成 1.2 万次下单，零超卖、零重复订单；最佳受测中位成功下单吞吐约 85 单/秒。

更推荐把简历正文的主指标放在 Redis 对数据库的减压效果：

> 千人抢百券实验中入口 QPS 由 279 提升至 1839，进入 MySQL 的请求减少 90%。

面试时再补充：1839 是包含售罄快速失败的入口 QPS；充足库存、全部成功的单热点完整链路约为 85 单/秒。这样既能体现入口抗压能力，也不会混淆成功订单吞吐。
