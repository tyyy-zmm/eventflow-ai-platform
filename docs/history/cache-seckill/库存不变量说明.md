# 库存与订单的不变量

## 先限定保证范围

这里的“不超卖”是指：在使用本模块受控写入路径、MySQL 正常提供事务及约束、活动容量不被外部脚本随意改写的前提下，数据库中生效订单不会超过活动容量。不是承诺任意机房故障、磁盘损坏、人工改库或真实支付系统异常下仍然百分之百可用。

测试中的 1000 用户是合成不同身份；用 16 个工作线程并发争抢 100 份库存。另有真实 HTTP 突发实验验证限流/拒绝行为。两类测试不要混为 1000 个线程同时执行。

## 守恒式

设活动初始容量为 C，可用库存为 A，订单处于 PENDING_CONFIRM 或 CONFIRMED 的数量为 L。需要始终保持：

```
A >= 0
A <= C
A + L = C
每个 (activity_id, user_id) 最多一行订单
SUCCEEDED 请求恰有一行对应订单，其他状态无订单
```

### 成功建单

同一事务内 `A := A - 1` 并插入一张生效订单 `L := L + 1`；SQL 带 `available > 0` 条件。任何后续写入失败，整个事务回滚，A 和 L 都回到原值。

### 取消或过期

仅 PENDING_CONFIRM 可以转换。事务内订单变为 CANCELLED/EXPIRED，相当于 `L := L - 1`，随后 `A := A + 1`。再次取消遇到终态直接返回，不能再加库存。确认成功保持订单生效，因此不改 A。

### 确认与取消竞争

两者先取得同一活动行锁。先执行者合法地改变订单状态，后执行者看到终态不再改写。若处理时确认期限已经过去，无论客户端叫“确认”还是“取消”，都会按 EXPIRED 释放一次库存。

### 重复消费

消费者先读请求持久终态。已经成功/拒绝/过期的请求直接结束，不再扣库存。即使应用路径漏掉前面的查重，订单 `(activity_id, user_id)` 唯一键和 `request_id` 唯一键仍阻止第二张订单；插入约束失败会回滚同事务扣减。

### 请求已过期，消息晚到

关闭请求与消费走相同的活动锁和请求状态检查。已 EXPIRED 的请求不能建单；尚未关闭但已经超过 deadline 的请求，在消费者检查处直接转 EXPIRED。判断的线性化点是持锁后的数据库时间/状态检查，不是用户发出请求的本地时间。

## 为什么还要实验

推理说明设计应该成立；测试验证实际代码是否真的把操作放进同一个事务、异常是否被吞、条件更新是否漏写、消息何时 ack，以及崩溃时数据库究竟留下什么。二者缺一不可。

本轮不是用压测“证明所有未来都正确”，而是结合约束、事务边界、不变量推理和可复现故障案例，说明保证成立的条件，并暴露尚未覆盖的边界。
