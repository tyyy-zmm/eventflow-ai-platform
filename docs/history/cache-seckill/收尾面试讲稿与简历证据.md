# 收尾面试讲稿与简历证据

## 三分钟主线

我基于黑马点评，把改造重点放在商家缓存与优惠券秒杀。页面已经打通注册、查询、下单、结果查询、确认取消，后端独立连接真实 MySQL、Redis 和 Kafka。这里的订单确认是本地业务动作，没有接真实支付。

读链路是 Caffeine、Redis、MySQL。商家描述更新少而热点集中，L1 用来省去 Redis 网络往返，容量和 TTL 都有界；L1 继承 L2 的绝对硬过期时间，避免层层续期。软过期允许暂时返回旧值并异步重建，硬过期必须重新读；失效任务与资料更新同事务保存，Redis 恢复后重试。Pub/Sub 用于尽快清理其他实例 L1，丢消息依靠 TTL，重订阅清空 L1。这是最终一致，不是强一致。Redis 故障回源有速率和并发上限。

写链路由 Redis Lua 做预扣、一人一单和入口保护，然后 MySQL 保存请求与 Outbox。Kafka 消费事务通过活动行锁、条件扣减、唯一约束完成建单；数据库提交后才确认消费，Redis 补偿不阻塞已提交事务的 ack。Outbox 可能重复发送，消费也可能重复执行，所以必须靠业务幂等。取消、超时与恢复使用同一个活动锁串行化，补偿动作同事务持久化。孤儿预扣要先在数据库裁定终态再释放，防止迟到请求继续建单。

我验证的是正确性和实测边界：103 项后端测试、7 类故障、200 笔积压崩溃恢复，以及页面验收；双实例热点查询三轮 QPS 中位数是 Redis 单层的 2.20 倍。固定 40 次/秒持续 15 分钟，36,000 次请求全部建单且库存守恒。SQL 精简确实减少了往返，但受同活动行锁串行化限制，吞吐提升很小，我不会把它说成数量级突破。

## 高频追问

1. **为什么不用布隆过滤器？** 当前非法 ID 的分布、规模没有证明其收益。短负缓存配合有界回源解决当前问题；若实测大量不同不存在 ID，再评估布隆初始化、增量更新和误判成本。
2. **为什么不删除 DB 行锁提速？** 它统一受理、取消、过期、恢复的时序。先去掉重复读取、修正索引扫描，保留正确性边界。继续拆锁需要新的不变量证明和并发测试。
3. **为什么 202 不能显示购买成功？** 202 只是请求和 Outbox 已落库；还要等消费者完成。SUCCEEDED 是建单事实，订单本身仍可取消或过期。
4. **发送成功后宕机会怎样？** Outbox 租约过期重发；请求终态和唯一约束消除重复业务效果。生产者幂等不等于端到端 exactly-once。
5. **Redis 挂了是否全量回源？** 商家读用有效 L1 与有界 DB 降级；新秒杀拒绝受理，已有订单查询和确认取消仍依赖数据库。
6. **网页重试如何避免重复单？** 请求前持久化客户端键，断网后按键查结果或复用原键。明确入口拒绝清除意图；未知结果不生成新键。连续点击由同步锁阻止。
7. **怎么证明没有超卖？** 检查 available 加 PENDING_CONFIRM/CONFIRMED 数等于 capacity、库存非负、用户活动唯一以及请求订单状态匹配；不能只看 HTTP 成功率。
8. **你做的观测是什么？** 固定阶段直方图、队列大小/最老年龄、JVM 堆与 GC、SQL 执行计划和锁等待采样。桶 P95 是上界，事务内 completed_at 是近似，未接生产监控平台。
9. **还能改什么？** 超过 10,000 请求的恢复、历史归档、多节点故障和生产观测。当前明确列为限制，不包装成已实现。

## 已写入 PDF 的四条表述

- 多级缓存：采用 Caffeine + Redis，实现软硬过期、异步重建与失效重试；本机双实例热点查询三轮对照中，QPS 中位数达 Redis 单层的 2.20 倍，P95 中位数下降 48.4%。

- 秒杀一致性：Redis Lua 预扣与一人一单校验，MySQL 行锁、条件扣减及唯一约束兜底；持久化补偿任务结合幂等状态机、超时对账，处理宕机、取消及过期回补。

- 可靠异步建单：请求与 Outbox 同事务持久化，Kafka 异步建单；发布租约、提交后确认及消费幂等保障恢复，通过 7 类故障与 200 笔积压崩溃重启验证，无重复订单。

- 链路优化与验证：精简锁内 SQL、优化补偿扫描；本机以 40 次/秒持续 15 分钟，36,000 次请求均成功建单，库存守恒、无重复订单。
