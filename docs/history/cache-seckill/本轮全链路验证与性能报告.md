# 本轮全链路验证与性能报告

日期：2026-10-02。模块：`hm-dianping/backend-upgrade`。所有数据均为合成数据。

## 环境与隔离

使用独立 MySQL 库 `upgrade_verification`、Redis DB14、Kafka topic/group `upgrade-verification-v1`。中间件测试另建每次运行专用 Kafka topic。没有修复、覆盖原 `upgrade` 库的 Flyway 历史，也没有清空共享 Redis。

本机为 Apple M5、10 个逻辑 CPU、24 GiB 内存，macOS arm64。应用、容器和 Node.js 负载生成器位于同一台机器，未固定 CPU，机器上还存在其他容器。测试不是生产最大容量认证。

## 功能与可靠性测试

执行：

```bash
UPGRADE_INTEGRATION=true UPGRADE_RELIABILITY_INTEGRATION=true bash scripts/verification.sh package
```

**88 项全部通过：失败 0、错误 0、跳过 0。** 包含 50 项单元测试、26 项真实中间件测试、6 项 MySQL/Redis 恢复测试、6 项客户 HTTP 测试。

本轮修复了完整 Spring 启动才暴露的 Bean 名称冲突：`CacheNotifications` 配置类和监听器方法使用同名默认 Bean，现监听器显式命名为 `shopInvalidationListener`。HTTP 测试实际启动应用，覆盖注册登录、受理与幂等、确认/取消/过期、订单访问权限及缓存查询。

新增 MySQL 恢复故障覆盖：

- Redis 快照已写入、数据库事务随后回滚：Redis 保持暂停；数据库 ACCEPTED 和旧 epoch 回滚保留；显式重试恢复后收敛。
- 数据库已提交但提交响应丢失：不会执行 Redis 激活；再次显式恢复能够生成新 epoch 并开放入口。

## 双实例热点缓存对比

执行 `bash scripts/verification.sh multilevel-benchmark`。两个独立 JVM，端口 18093/18094，每实例最大堆 384 MiB，总并发 8，1,024 个合成用户。每种方案预热 100 次，每轮测量 30 秒，共 3 轮，轮换方案顺序。

对比接口为数据库直读 `/v2/benchmark/direct/{id}`、Redis TTL `/v2/benchmark/ttl/{id}`、多级缓存 `/v2/shops/{id}`。三组均经过 HMAC 鉴权；预生成令牌，避免每个请求都在负载生成器计算签名。未关闭服务端限流，合成用户分摊请求以避免测成单用户限流上限。

以下为各轮统计量的中位数，不是将所有请求合并后重算的分位数：

| 方案 | 成功 QPS 中位数 | 三轮 QPS 范围 | P95 中位数 | P99 中位数 | 总请求数 | 错误 |
|---|---:|---:|---:|---:|---:|---:|
| MySQL 直读 | 5,257 | 5,160～8,515 | 3.019 ms | 4.960 ms | 567,966 | 0 |
| Redis 单层 TTL | 7,435 | 5,868～10,061 | 2.210 ms | 3.595 ms | 700,949 | 0 |
| Caffeine + Redis | 16,376 | 16,083～21,544 | 1.141 ms | 2.524 ms | 1,620,111 | 0 |

多级缓存相对 Redis 单层的 QPS 中位数比值为 **2.20**，P95 中位数下降 **48.4%**。相对数据库直读的 QPS 中位数比值为 **3.12**。

多级缓存 1,620,111 次请求中，L1 命中 1,619,268 次（**99.948%**），L2 命中 843 次，数据库读取 15 次。Redis TTL 组数据库读取 48 次：同一 key 硬过期时，多请求可能同时回源；多级缓存保留了合并数据库重建的机制。

跨 JVM 更新可见性单次观察约 13.55 ms；这是一次功能探针，不代表失效延迟 P95/P99 或 SLA。

此测试为单个热点商家描述的闭环压测。前端 `/v2/catalog/shops/{id}` 还查询实时优惠券信息，不能直接使用本表作为整站吞吐，也不能把 1.64 万 QPS 写成秒杀成功 TPS。三轮结果有明显波动，因此保留中位数和范围，不使用最好一轮作为结论。

证据：[汇总](../evidence/multilevel-benchmark-1790952312445/summary.json)、[逐轮结果](../evidence/multilevel-benchmark-1790952312445/results.json)、[环境与源码 SHA-256 清单](../evidence/multilevel-benchmark-1790952312445/environment.json)。同目录保留逐请求原始样本。

## 真实进程与依赖故障实验

执行 `bash scripts/verification.sh verification-experiment --faults`。脚本只终止自己启动的 JVM；Redis 断连通过此 JVM 专用 TCP 代理注入，不停止共享 Redis 容器。

首次完整实验七种场景全部通过：

| 注入点 | 验证结果 |
|---|---|
| Redis 预占后、数据库受理前进程退出 | 恢复为 EXPIRED，0 订单，库存释放一次；原键不能迟到建单 |
| 数据库受理提交后、HTTP 响应前退出 | 原键找回 SUCCEEDED，只有 1 订单 |
| Kafka 发送后、Outbox 标记前退出 | 重投没有产生重复订单 |
| 订单事务提交后、Kafka ack 前退出 | 重复消费没有产生重复订单 |
| 取消事务提交前退出 | 未提交取消回滚；重试取消最终只回补一次 |
| 删除测试活动的 Redis 库存键 | 新请求 503，已存在请求可找回；显式恢复后正确继续下单 |
| 应用与 Redis 连接中断 | 有效 L1 可读；新秒杀拒绝；原订单仍可查询；缓存更新失效任务持久保留并在重连后完成 |

首次 Redis 断连实验中，L1 过期后的 100 个并发缓存请求返回 6 个 200、94 个 503；其中 20 次获得降级尝试预算，80 次被预算拒绝，其余拒绝来自数据库并发槽位保护。该结果表明系统会主动拒绝超出预算的流量，不代表断连期间所有读取均成功。

七个场景检查的库存与请求状态不变量均为 0 违规。首次完整实验见 [故障结果](../evidence/verification-faults-1790952621207/results.json)。

原消费者使用客户端默认 45 秒会话超时，两次涉及重新消费的实验在 HTTP 服务恢复就绪后，分别再等待约 34.4 秒和 40.9 秒才收敛。这些时间不包含 JVM 启动，也不是生产 RTO。该结果触发了第五阶段的会话参数优化，而非直接引入库存分桶。

## 根据故障证据实施的 Kafka 调整

消费者会话超时从客户端默认 45 秒调整为 **15 秒**，心跳间隔保持 **3 秒**；可通过 `UPGRADE_KAFKA_SESSION_TIMEOUT_MS`、`UPGRADE_KAFKA_HEARTBEAT_MS` 覆盖。缩短会话超时提高异常进程的识别速度，同时也降低了对长 GC 停顿和网络抖动的容忍度，生产设置需要结合实际暂停时间与重平衡频率。

调整后再次运行七种故障场景，全部通过，库存和状态违规仍为 0。两个涉及重新消费的检查点，HTTP 恢复后收敛的单次观察如下：

| 检查点 | 原会话超时 45 秒 | 调整为 15 秒 |
|---|---:|---:|
| 受理提交后、响应前退出 | 34.434 秒 | 18.595 秒 |
| Kafka 发送后、Outbox 标记前退出 | 40.873 秒 | 11.375 秒 |

恢复还受到租约、重平衡和调度时机影响，不能将 session timeout 等同于端到端恢复时间，也不能用这两次单样本对照宣称固定改善百分比。部署仍是单 Broker，并没有因此获得 Broker 故障容灾。

调整后的 Redis 断连实验中，100 个缓存请求返回 9 个 200、91 个 503；降级尝试预算仍为 20 次，预算拒绝 80 次；更新失效任务在重连后完成。相关现象与有界降级设计一致。

证据：[调整后的完整故障结果](../evidence/verification-faults-1790952974473/results.json)、[环境和源码清单](../evidence/verification-faults-1790952974473/environment.json)。缓存性能测试期间消费者任务关闭，因此上述消费者会话参数调整不影响该缓存对比路径。

## 成功下单吞吐观察

执行 `bash scripts/verification.sh verification-experiment --capacity`。一个 JVM，最大堆 384 MiB，并发 4/8/12 各跑三轮，每组 500 请求。每次请求使用不同用户，库存等于请求数，活动限流和积压阈值在实验进程中提高，避免测成售罄或限流拒绝吞吐。生产默认限额未改。

**4,500 请求全部返回 202，最终全部 SUCCEEDED，生成 4,500 个订单；每组最终库存和状态违规均为 0。** 202 只代表受理，成功订单数由数据库核对。

以下是三轮中位数：

| 并发 | 成功订单数 | 建单完成 TPS | 含 Redis 补偿收敛 TPS | HTTP P95 | 建单端到端 P95 | HTTP 结束时待建单 / 待发送 |
|---|---:|---:|---:|---:|---:|---:|
| 4 | 1,500 / 1,500 | 97.92 | 72.17 | 24.01 ms | 3,104 ms | 371 / 300 |
| 8 | 1,500 / 1,500 | 94.82 | 64.99 | 36.79 ms | 3,380 ms | 432 / 340 |
| 12 | 1,500 / 1,500 | 89.67 | 64.61 | 59.58 ms | 3,549 ms | 449 / 360 |

统计口径：

- 建单完成 TPS = 成功订单数 / 从最早客户端发送到最后一笔数据库完成的时间。数据库完成时间来自 MySQL，客户端时间来自同宿主机；仍依赖时钟一致。
- 含 Redis 补偿收敛 TPS = 成功订单数 / 从开始发送到该活动所有请求终态及补偿任务完成的时间，包含轮询开销，较保守。
- 端到端延迟包含请求受理、Outbox、Kafka 和订单事务排队，不是 HTTP 返回 202 的延迟。
- 这是每组 500 次的有限批次观察，不是长时间稳态极限容量测量。

提高并发没有提高成功订单吞吐，反而增加待建单和未发送 Outbox 数量。代码中的 Outbox 调度每批最多 20 条、轮次间隔 100ms，补偿调度每轮最多 100 条、间隔 1 秒；实际还包含数据库和网络耗时。结果足以表明入口并发不是唯一限制，但**没有足够证据将瓶颈直接归因于库存行锁**。因此本轮不直接加库存分桶。

证据：[统计定义及汇总](../evidence/verification-capacity-1790953105626/summary.json)、[逐轮数据](../evidence/verification-capacity-1790953105626/results.json)、[环境和源码清单](../evidence/verification-capacity-1790953105626/environment.json)。同目录保留逐请求状态、HTTP 延迟及最终建单延迟。

## 第五阶段决策与交付边界

已根据故障证据落地 Kafka 会话检测参数优化，并通过全量 88 项测试及七种真实故障复验。

暂不引入网关缓存：现有热点描述场景 L1 命中率已达 99.948%，尚未证明网关缓存带来的额外收益足以抵消失效链路复杂度。

暂不引入库存分桶：成功链路中已有可见 Outbox 和补偿排队，应先做单变量调度/批处理实验及活动行锁等待采样，再判断是否需要改变库存模型。不能通过只拆 Redis key 宣称解决 MySQL 单行瓶颈。

如继续扩展实验，优先级为：持续开放速率压测 → Outbox/补偿分阶段耗时与队列观测 → 调度批量的单变量对照 → 再评估库存分桶。当前恢复仍限制单活动最多 10,000 条请求，缓存仍为有陈旧上限的最终一致性，部署仍是单节点中间件。

本轮启动的应用和断连代理在实验结束后由脚本关闭；独立验证库与合成测试数据保留，便于复查。原业务库迁移历史未修改。
