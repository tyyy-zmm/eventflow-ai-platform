# 秒杀链路观测与单变量优化报告

本轮把后续工作落到了代码、真实中间件实验和可复述的设计材料中。选择 Outbox 每批 100、发送窗口 1、补偿每批 100 / 间隔 1 秒作为默认参数。对照结果支持小幅改善最终建单排队，但没有证据支持“整个秒杀吞吐翻倍”。

## 已实现内容与口径

新增管理员接口 `GET /v2/admin/pipeline`，返回固定阶段直方图、失败次数、积压数量、最老任务年龄和实际生效参数。统计使用固定枚举和固定桶，不带用户、活动、请求 ID 标签，内存不会随请求数量增长。接口受原有管理员身份校验保护，不对普通用户开放。

| 阶段 | 计时含义 | 不能推导什么 |
|---|---|---|
| RESERVE / ADMISSION | Redis 预占 / 准入检查 | 不等于业务完成 |
| ACCEPT_TX / ORDER_TX | 持久受理 / 建单事务执行总耗时 | 不能直接当成 CPU 时间 |
| ACCEPT_LOCK_QUERY / ORDER_LOCK_QUERY | FOR UPDATE 查询耗时 | 包含连接、网络、执行、锁等待，不能全部称为锁等待 |
| OUTBOX_CLAIM | 一次领取事务，包括空轮询 | 不等于每个独立订单的耗时 |
| OUTBOX_AGE | Outbox 创建至发送尝试 | 重试会重复采样 |
| KAFKA_SEND | send 调用至 Future 完成 | 不含消费者建单时间 |
| KAFKA_RECORD_AGE | Kafka 记录时间戳至进入消费处理 | 包含生产端和队列阶段，不是纯 broker 内部延迟 |
| RESERVATION_APPLY / RESERVATION_AGE | Redis 补偿执行 / 动作创建至尝试 | 补偿完成晚于数据库建单完成 |
| RELAY_CYCLE / REPAIR_CYCLE / RECONCILE_CYCLE | 一次对应后台任务周期 | fixedDelay 是执行完后再等待，不是固定吞吐率 |

计数为进程启动以来的尝试次数；实验用前后快照差值。并发快照不是原子事务；直方图 P95 只能报告桶上界。跨组件年龄依赖时钟，未来时间戳单独计入 clockSkewSamples。HTTP P95 则来自逐请求原始样本。

额外用 MySQL `performance_schema.data_lock_waits` 与 `data_locks` 只读采样本验证库的活动表。每次返回后等待 200 ms 再查询，没有清空全局统计。记录的是**等待者与阻塞者之间的关系数**：同一个等待事务可能对应多条关系，不能把 peak=28 写成 28 个等待事务，也不能从采样关系数推算精确锁等待毫秒。短于采样间隔的等待可能漏采。

Outbox 保留租约、owner 条件确认、失败退避和幂等消费。新增可配置发送窗口 1–8，只保留有限 Future；异常后已经领取的记录依靠确认、重试和租约过期恢复。补偿任务与过期/对账调度分离，可以单独调节批量和间隔。

## 单变量对照

证据：[逐组结果](../evidence/pipeline-variants-1790955360089/results.json)、[汇总](../evidence/pipeline-variants-1790955360089/summary.json)、[环境与源文件哈希](../evidence/pipeline-variants-1790955360089/environment.json)。每组原始请求、队列轨迹、锁采样、计时快照与应用日志均位于同目录。

条件：Apple M5，本机真实 MySQL / Redis / Kafka，单 JVM 384 MiB；独立 `upgrade_verification` 数据库、Redis DB14 和 Kafka topic/group；每轮一个新活动、500 个不同用户、HTTP 并发 8。每组 3 轮，轮换执行顺序。所有组均包含本轮观测和调度拆分，基线不是上一份报告的旧二进制。总计 7,500 请求全部 202 后最终 SUCCEEDED，库存与请求/订单状态违规为 0。

下表是三轮中位数。databaseOrderTps 使用数据库 completed_at 作为业务完成时间近似；该字段在事务内部写入，不是精确的 commit 时间戳，不能当成事务提交追踪。排空 TPS 采用已提交状态的查询确认，并包含补偿动作排空和轮询观察耗时。最终建单延迟同样使用 completed_at，保留毫秒级近似这一限制。

| 唯一变化 | 数据库建单 TPS | 含补偿排空 TPS | HTTP P95 ms | 最终建单 P95 ms |
|---|---:|---:|---:|---:|
| 基线：relay 20、window 1、repair 100/1000ms | 51.43 | 48.19 | 73.89 | 5587 |
| relay batch → 100 | 57.77 | 48.70 | 86.09 | 4663 |
| send window → 4 | 56.73 | 50.55 | 87.14 | 4773 |
| repair batch → 300 | 54.81 | 50.16 | 89.14 | 5018 |
| repair delay → 100ms | 50.71 | 49.32 | 99.98 | 5483 |

批量 100 的数据库建单 TPS 中位数比基线高约 12.3%，最终建单 P95 中位数降低约 16.5%；但 HTTP P95 变差，包含补偿排空的 TPS 只改善约 1.1%。所以选择理由是减少发布调度造成的排队，不能称为所有指标都提升。

为什么暂时保留发送窗口 1：Kafka send 平均耗时中位数约 1.3–1.5 ms，已经很短；窗口 4 没有显示出相对批量 100 的明确优势。更大的窗口仍作为受限配置保留，默认不叠加两个未经组合对照的变化。

为什么保留补偿间隔 1 秒：100 ms 间隔确实把补偿动作年龄均值中位数从约 825 ms 降到约 120 ms，但最终建单 TPS 没有提高，HTTP P95 反而增大。若业务要求更快释放预占，可选择这项延迟/资源折中；本轮默认优先保持数据库建单链路的资源余量。

### 能定位到哪里，不能定位到哪里

基线的 OUTBOX_AGE 均值中位数约 1980 ms，批量 100 降至约 1164 ms；KAFKA_RECORD_AGE 同时由约 2038 ms 增至约 2610 ms，说明部分等待移到了消费侧。不能只看 Outbox 积压下降就宣称端到端问题解决。

基线受理 FOR UPDATE 查询均值中位数约 43.5 ms，建单对应查询约 6.1 ms；采样确实捕获到活动表锁等待。热点串行化是需要关注的因素，但这些计时还包含网络、执行和连接开销，现有证据不能给出“锁等待占总耗时 X%”。不应立即删除保证一致性的行锁。

本机实验存在明显轮次漂移：基线数据库建单 TPS 从第一轮约 75.63 到第三轮约 46.80。历史数据持续增长、后台扫描、JVM 热身和共享宿主机资源都可能影响结果；当前没有把这些因素逐个隔离证明。保留全部结果，参数选择可回退，不将中位数差异包装成生产容量或严格统计显著性。

## 持续流量与突发边界

生成器按计划到达时间发请求，不等待前一请求完成后才安排下一次；在途上限 64。记录计划数、实际发出数、跳过数、调度延迟、HTTP 状态、最终状态和每秒队列快照。达到生成器上限的实验明确标记 generatorLimited，不能用实际发出的数量假装完成了全部目标负载。

已完成的首组证据：[持续与突发原始结果](../evidence/pipeline-sustained-1790955732671/results.json)。

| 场景 | 计划请求 | 实际发送 | 成功建单 | HTTP 503 | 生成器跳过 | 发压结束 ACCEPTED | 随后含补偿排空 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 单热点 80/s × 60 秒 | 4800 | 4800 | 4795 | 5 | 0 | 29 | 约 1.9 秒 |
| 单热点 40→160→40/s，各 20 秒 | 4800 | 4792 | 4006 | 786 | 8 | 1075 | 约 19.8 秒 |

所有已经 202 受理的请求最终成功，库存和状态约束均为 0 违规。80/s 的 HTTP P95 约 20.27 ms、最终建单 P95 1109 ms；突发场景分别约 332.00 ms 和 22544 ms。80/s 也存在拒绝，不能作为零失败稳定容量。

首次突发实验的脚本把“生成器跳过=0”设为严格断言，因此保存结果后停止了后续场景；对应 failure.json 保留。这是负载资格判定失败，不是忽略掉的成功结果。后续脚本将生成器受限显式分类，并继续验证其他负载；原始失败文件不覆盖。

补充完成：

| 场景 | 请求 / 成功建单 | HTTP P95 | 最终建单 P95 | 停压时 ACCEPTED | 含补偿排空 | 生成器跳过 |
|---|---:|---:|---:|---:|---:|---:|
| 10 个活动合计 80/s × 60 秒 | 4800 / 4800 | 16.23 ms | 217 ms | 0 | 约 1.11 秒 | 0 |
| 单热点 40/s × 60 秒 | 2400 / 2400 | 13.63 ms | 113 ms | 0 | 约 0.84 秒 | 0 |

证据：[多活动持续流量](../evidence/pipeline-sustained-1790956010234/results.json)、[单热点低负载](../evidence/pipeline-sustained-1790956164188/results.json)。两组均无库存或状态违规。多活动场景 307 次锁关系采样均为 0，单热点 40/s 有 12/306 次采样捕获到等待；未采到等待不意味着绝对没有等待。

四个场景计划到达 16,800 次，实际发送 16,792 次，成功建单 16,001 次，503 共 791 次（均为 ADMISSION_BUSY），生成器跳过 8 次。没有把失败样本从分母中删除。60 秒持续实验是本机负载观察，不是数小时稳定性验证，也没有据此宣称最大容量。

### 最终回归与有积压崩溃验证

最终 clean package 执行 96 项测试，失败、错误、跳过均为 0。包括 57 项单元测试、26 项真实中间件测试、7 项可靠性测试、6 项客户 HTTP 测试；[测试汇总与产物 SHA-256](../evidence/pipeline-final-20261002/test-summary.json)，完整 build.log 位于同目录。

额外准备 200 条已持久受理的积压请求，以 batch=100、window=4 启动发布。在 Kafka 已确认但 Outbox 尚未标记的故障点强制退出 JVM（exit 91），再重启。最终 200 条全部建单，200 个原请求键重放均返回同一请求，订单没有增加，Redis 库存为 0，所有不变量通过。恢复约 19.9 秒，包含故障进程启动、失败检测与恢复进程重启；这是一次本机观察，不是 RTO 承诺。证据：[有积压崩溃恢复](../evidence/pipeline-crash-1790956337228/results.json)。此场景刻意使用窗口 4 验证可选功能，默认仍为 1。

最终默认配置下，七类故障回归全部通过：[原始结果](../evidence/verification-faults-1790956445018/results.json)。包含预占后未落库、持久受理后响应丢失、发送后未标记、建单提交后未确认消费、取消事务中断、Redis 库存键丢失、Redis 连接中断。最后一项使用专用 TCP 代理断开实验 JVM 的连接，没有停止共享 Redis：新购买返回 503，既有订单可查，失效任务恢复后重试成功，100 次冷读中 11 次成功、89 次受控拒绝。

200 单积压崩溃实验和七类故障回归均未发现库存或请求/订单状态违规。恢复时间受本机资源、Kafka 消费者重平衡与重试时序影响，不能用单次数字承诺生产恢复时间。

## 复现

先确保已授权的独立验证库存在；以下脚本不创建数据库、不修改授权、不停止共享 Redis / MySQL / Kafka。

```bash
UPGRADE_INTEGRATION=true UPGRADE_RELIABILITY_INTEGRATION=true bash scripts/verification.sh package
bash scripts/verification.sh pipeline-experiment
PIPELINE_CONFIG='{"batch":100}' bash scripts/verification.sh pipeline-experiment --sustained
PIPELINE_CONFIG='{"batch":100}' bash scripts/verification.sh pipeline-experiment --sustained --safe-only
bash scripts/verification.sh pipeline-crash
bash scripts/verification.sh verification-experiment --faults
```

不要并行运行性能实验与其他重负载测试。脚本仅管理自己启动的 JVM，并保留应用日志和原始结果。持续流量使用提高后的实验限流参数，以观察链路边界；不代表生产默认限流配置。
