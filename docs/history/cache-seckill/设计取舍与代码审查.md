# 设计取舍与本轮代码审查

## 为什么不在 Redis 里硬预扣库存

原版 Lua 的“检查库存、判断是否买过、扣 Redis 库存”在单个 Redis 主节点执行期间是原子的，这不等于“从入口到最终 MySQL 订单的所有环节都是原子的”。Redis 成功之后进程崩溃、消息发送失败、MySQL 插单失败，都需要跨系统修复；如果最终 SQL 本身没有 stock>0 与唯一约束兜底，更不能只靠缓存锁宣称绝不超卖。

当前原版私有建单方法已经有 `stock > 0` 条件扣减，因此不能据此断言“原版必然超卖”。实际查到的问题是生效入口缺少落单投递、库存扣减与插单事务边界不足，以及数据库唯一约束和失败恢复没有形成完整链路。优化应针对这些真实缺口，而不是夸大原版缺陷。

本轮选择一个更容易验证的边界：Redis 只挡流量，MySQL 维护最终库存和订单。新请求先持久化，再异步处理；没有必要引入复杂的 Redis 预扣补偿协议。代价是每个受理请求仍需一次数据库事务，不能以“全部请求都在 Redis 完成”作为性能卖点。

## 为什么还用 Kafka

它把受理与后续建单解耦，允许暂时积压、按分区处理，以及在下游中断后重新处理。Outbox 解决 DB 提交后到消息可靠投递的缺口，业务幂等解决重复投递的影响。

对于本地短小建单事务，Kafka 未必比同步 SQL 更快，排队会增加完成延迟。这是本轮实验明确要比较的事实，不预设提升倍数。后续若处理链路没有昂贵操作、峰谷差异也很小，可以保留同步方案作为更简单的部署选择。

## 为什么同时有行锁、条件扣减和唯一键

活动行锁统一串行化同活动的下单、确认、取消、到期，简化锁顺序和状态竞争分析。`available>0` 条件扣减让数据库更新语义本身有边界；用户/活动唯一键让遗漏应用查重的路径也不能写入第二单。

三者的职责不同，不是叠几个术语就有高并发能力。同一活动行会成为热点；本轮先确保正确和故障可恢复，再通过数据判断要不要分段库存或进一步削减 SQL 次数。

## 为什么 Outbox 不再加一个通用 Inbox

每条消息只对应一个持久请求。事务中检查并锁定请求状态，成功、业务拒绝、过期都是不可逆终态，足以对建单这个业务效果去重。再加一张通用消费去重表没有消除新的复杂度，所以暂不加入。

这不意味着 Inbox 永远没用。一个事件触发多个独立业务效果、不同消费者拥有不同处理语义时，应重新审视消费去重模型。

## 缓存为什么用 Owner，而不是固定锁值

固定值加直接 DEL 会让过期的 worker 删除后来者的锁。唯一 owner 必须同时约束“谁能释放”和“谁能回填”，所以缓存值写入与 owner 校验必须在同一 Lua 中原子执行。仅改解锁、不改回填，仍会让慢 worker 覆盖新数据。

更新提交后失效还需要处理 Redis 失败和旧重建任务：数据库任务持久重试；失效时同时删除旧 owner；generation 条件确认防止旧 worker 清理新的失效任务。这里追求有界最终一致性，绝不把描述缓存当成下单库存依据。

## 已审查的边界

| 边界 | 检查结果/处理方式 |
|---|---|
| `@Transactional` 自调用失效 | 核心用 TransactionTemplate 包裹实际动作，异常退出回滚；不依赖 private 方法注解 |
| 锁顺序 | 同活动业务修改先锁活动，再检查请求/订单，避免反向锁顺序 |
| 事务内外部调用 | 交易事务只访问 MySQL；Redis 提示、Kafka send 在事务外 |
| DB 插单失败 | 条件扣减与请求终态回滚，消息重试；不是简单吞异常 |
| confirm/cancel/expire | 仅 PENDING_CONFIRM 可转移，库存释放与状态同事务 |
| 到期请求遇到迟到消息 | 消费读持久终态及 deadline，不能复活 |
| Kafka 默认错误恢复策略 | 明确无限退避处理基础设施失败，避免默认有限重试后丢弃 |
| 消息中的价格/身份 | 从数据库请求及活动读取，不信任外部消息传入的价格或 userId |
| 租约过期发送者 | owner 条件标记，旧发送者不能标记后来者已成功 |
| 缓存旧 owner | Lua 同时控制回填和解锁；更新失效使其失去所有权 |
| 缓存并发与失败 | 线程、队列、读槽、等待、SQL/Redis 超时均有界；失败不无限回源 |
| 凭据 | `.env` 0600 且 Git 忽略；日志、源码清单不包含真实 Secret |
| 运行隔离 | 使用新的 Compose 名称、端口、数据库、表前缀与 Redis 键；原目录已有修改未回滚 |

## 保留的工程局限

- 独立模块暂未接旧登录与旧页面。测试令牌在本地工具签发，不能表述为完成生产身份系统。
- 负载保护多处是每实例有界容量；跨实例精确配额、分布式时钟偏差、租约续期均未做生产级验证。
- 请求积压计数/最老时间每次查询数据库，适合当前体量；若测到它成为热点，需要采样指标或分片计数方案，不能在没有数据时随意优化。
- 请求/订单/Outbox/审计历史暂无归档清理。测试体量有限；长期运行须设计保留期与审计/幂等键保留契约，不能随意清掉去重依据。
- 单 Kafka Broker 无副本冗余；本地配置没有独立 Kafka 持久卷，容器重建不是本轮故障恢复保证。
- Flyway 10.x 对 MySQL 8.4 有“超出官方已测试版本”的警告；本次增量建表和测试已跑通，但这不是未来所有 migration 都兼容的承诺。
- 没有真实支付，因此不能把 PENDING_CONFIRM/CONFIRMED 写成支付成功、支付幂等或退款一致性。

这些限制不妨碍将项目用作秋招后端工程实践，但必须在面试中解释实际边界，而不是称为已经承载线上秒杀的平台。
