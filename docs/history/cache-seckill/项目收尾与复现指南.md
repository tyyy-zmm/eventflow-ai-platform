## 当前电脑启动与验收

在 `hm-dianping/backend-upgrade` 执行：

```bash
# 使用已经建立的隔离库。共享中间件正在运行时无需再次 up。
bash scripts/verification.sh start --server.port=18095 --upgrade.demo-data=true
```

另一个终端进入 `eventflow-ui`：

```bash
npm ci
LIFE_API_TARGET=http://127.0.0.1:18095 npm run dev -- --port 4176 --strictPort
```

访问 `http://127.0.0.1:4176/life/`，注册新账号后浏览商家、下单、确认或取消。示例活动每日生成且不重置库存；同一用户同一场取消后不能重购。验收创建的合成账号/订单保留在隔离库，不清空共享库。停止演示只需分别 Ctrl-C 停止自己启动的前后端进程，不停止共享中间件。

已有 Playwright 的环境可执行：

```bash
# 在 eventflow-ui；没有全局模块时用 PLAYWRIGHT_MODULE 指定已安装的 index.mjs。
LIFE_BROWSER_CHANNEL=chrome LIFE_URL=http://127.0.0.1:4176 \
  LIFE_EVIDENCE=../hm-dianping/backend-upgrade/evidence/your-ui-run \
  node tests/life-browser.mjs
npm run build
# 后端运行时，在 backend-upgrade 做只读审计：
bash scripts/verification.sh release-audit
```

审计脚本绑定本次 103 项测试的源码与 JAR 哈希；后续修改后应重新验收并更新基准，不能绕过校验。它使用与 `/v2/admin/pipeline` 相同的 epoch 补偿范围，同时单列无 epoch 的历史记录。

## 全新电脑复现

交付包包含独立模块源码、前端、锁文件、文档、精选证据和校验清单，不包含密码、依赖目录、数据库卷或 JAR。需要 Java 17、Maven、Node.js、Docker Compose；用 `npm ci` 依据锁文件安装，不用 `npm update` 漂移版本。

全新环境在 backend-upgrade 运行 `bash scripts/local.sh up`、`bash scripts/local.sh package`、`bash scripts/local.sh start --upgrade.demo-data=true`，前端使用默认代理端口 8093 即可。初始化脚本生成新的随机 `.env`，只有全新数据库卷才能与新密码配套；不要用新密码文件覆盖已有容器配置。

`verification.sh` 依赖本机已预先建立并授权的 `upgrade_verification`，它不创建库或授权，因此不是全新电脑的首次安装脚本。当前电脑原 `upgrade` 库含其他分支 V4 历史，不能直接对其执行本模块迁移，更不能关闭校验或 repair 掩盖差异；本轮始终使用隔离库。全新电脑安装路径已按配置核对，未额外销毁容器进行空机重装实验。

## 复测入口与指标边界

```bash
UPGRADE_INTEGRATION=true UPGRADE_RELIABILITY_INTEGRATION=true bash scripts/verification.sh test
bash scripts/verification.sh verification-experiment --faults
bash scripts/verification.sh pipeline-crash
bash scripts/verification.sh multilevel-benchmark
bash scripts/verification.sh hotspot-experiment --long
```

运行实验前停止自己的演示 JVM，避免端口占用和负载干扰。旧 `faults` 等脚本仅作历史实验留档，不作为本次推荐入口。数据库记录不做无条件清理；完整原始采样保留在工作区 evidence，交付包只收录精选汇总、环境、验收截图，不能替代全部原始采样。

缓存 QPS 来自双 JVM 的单热点 `/v2/shops/{id}`，不等于带实时券查询的页面吞吐；40 次/秒、15 分钟是固定负载验证，不是最大容量。36,000 成功建单不代表 36,000 已确认成交。端到端 P95 116ms 使用数据库事务内 completed_at 近似，非精确提交时间。单机 Redis、Kafka 无多节点故障保证，单活动超过 10,000 请求的恢复仍有限制。
