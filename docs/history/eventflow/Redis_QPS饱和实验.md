# Redis 热目录 QPS 饱和实验

## 1. 结论

2026-09-21 在同一台本机、同一构建、同一 MySQL 数据和同一个热点目录详情上进行开环对照。关闭 Redis 的基线与开启 Redis 的应用各自独立运行，正式复验覆盖 1000、1500、3000 QPS 三个档位，每档 6 秒、重复 3 次，窗口前固定冷却 3 秒并交替测试顺序。

预先冻结的“可持续”条件为：正确响应率不低于 99%、实际正确吞吐达到目标档位的 95%、成功响应 P95 不高于 100ms、调度延迟 P99 不高于 100ms、客户端丢弃为 0，且错误只允许标准 503。某档位必须三轮全部满足才接受。

正式复验结果：

| 模式 | 三轮全通过的最大测试档位 | 该档实际正确 QPS 中位数 | 最差成功率 | 最差 P95 | 目录读取/命中 |
|---|---:|---:|---:|---:|---|
| MySQL 直读 | 1000 QPS | 996.15 | 99.55% | 1.70ms | 每轮约 5973-5983 次读取 |
| Redis 热缓存 | 3000 QPS | 2998.02 | 100% | 18.18ms | 三轮均 0 次目录读取、18000 次命中 |

因此本机受控热目录链路的三轮可持续测试档位由 1000 QPS 提升至 3000 QPS，即达到原来的 3 倍。3000 QPS 是本轮最高正式测试档位，不声称它是 Redis 的绝对极限，也不外推为生产 SLO 或整个业务接口吞吐。

## 2. 为什么使用独立 benchmark 入口

正式 `/api/v1/sessions/{id}` 在进入 `CatalogService` 前还会执行鉴权和发布状态查询。若直接用它做饱和实验，即使命中 Redis，也仍混有与缓存无关的 MySQL 查询，无法回答“目录缓存层自身能承受多少读取”。

实验只在 `eventflow.benchmark-http=true` 时注册 `/benchmark/sessions/{id}`，默认关闭；它复用相同的 `CatalogService`、Redis 序列化、回填锁和 MySQL 查询，但排除鉴权与发布检查。入口由实验进程在 loopback 端口启动，不能作为生产 API。统一异常处理把回源并发门拒绝表现为可重试 503。

## 3. 负载和计数口径

- 每轮先读取 100 次，保证比较的是热点命中而不是首次冷启动。
- 负载器按目标速率开环调度，最多 512 个在途请求；延迟超过 250ms或超过在途上限会明确记为客户端丢弃。
- 只有 HTTP 200 且 `id/title/description` 与本轮合成 fixture 全部一致才计为正确响应。
- 实际 QPS 使用正确响应数除以从窗口开始到全部在途请求收敛的真实耗时，不用目标速率冒充吞吐。
- `databaseReads` 和 `cacheHits` 来自 `CatalogService` 进程累计计数器的窗口差值，只表示目录层。
- 503、网络错误和客户端丢弃均不计入成功吞吐，也不能借拒绝请求降低 P95。

## 4. 结果细节

MySQL 直读在 1000 QPS 三轮正确率分别为 99.62%、99.55%、99.72%，均满足阈值；1500 QPS 有一轮降至 98.97%，因此不接受 1500 档。3000 QPS 三轮正确率约为 73.79%-74.12%，过载部分均按 503 返回。

Redis 在 1000、1500、3000 QPS 的九个窗口全部通过。3000 QPS 三轮各发送 18000 次请求，均得到 18000 个内容正确的 200 响应，无客户端丢弃；成功 P95 分别为 3.29ms、1.98ms、18.18ms，目录 SQL 回源均为 0。

探索阶段曾测试 4000/5000 QPS。一次短测可通过，但连续高档后未设置冷却，后续低档也出现异常高延迟，说明受到前序高压残留和本机负载器影响。该探索数据保留但不进入简历结论；修订实验合同后加入固定冷却并重新运行三轮。

## 5. 复现与证据

正式关键档复验：

```bash
EVENTFLOW_QPS_RATES=1000,1500,3000 \
EVENTFLOW_QPS_SECONDS=6 \
EVENTFLOW_QPS_REPETITIONS=3 \
EVENTFLOW_QPS_COOLDOWN_SECONDS=3 \
bash scripts/local.sh cache-qps
```

最终证据：`experiments/process-1789971576308/cache-qps/cache-qps-results.json`。每个窗口另有包含逐请求状态、延迟、调度延迟和内容校验结果的独立 JSON。外层 `results.json` 记录两个 Java 进程及业务不变量检查。

## 6. 简历准入文案

推荐表述：

> 实现 Cache-Aside、随机 TTL、owner 回填锁、revision 失效及用户/活动级 Lua 准入；同机三轮热目录压测中，可持续档位由 MySQL 直读 1000 QPS 提升至 Redis 3000 QPS，3000 档成功率 100%、P95 不高于 18.2ms、目录回源为 0。

不能表述为“系统 QPS 提升 3 倍”“生产支持 3000 QPS”或“所有数据库查询降为 0”。
