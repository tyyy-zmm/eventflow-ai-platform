# 双进程与故障实验

## 安全与执行

```bash
bash scripts/local.sh experiments
```

脚本先clean package并执行普通机制测试，再运行四组实验。需要本机中间件健康；18191/18192必须空闲。只接受loopback eventflow_it URL，固定操作专用库、不清库，绝不指向开发eventflow或旧点评。每轮创建新场次及独立topic/group，关闭所有容量补偿/过期/清理扫描与真实模型。它会写测试数据，不能拿正在压测或重要数据的库运行。

应用由脚本启动为两个真正独立Java进程。只终止脚本自己的进程；正常停止SIGTERM，必要时SIGKILL。目标故障点使用halt137模拟硬退出。所有故障都限定本轮场次，发送/消费点还限定CapacityMayBeAvailable，避免旧待发消息误触发。

运行锁防止两个脚本抢同一组端口/全局Outbox。正常中断会终止子进程并进入清理；不要强制杀整个进程树或断电。异常遗留锁时先确认锁中PID及实验子进程均已停止，再人工处理，不自动删未知锁。

测试账户来自现有私有.env，不打印密码/token。结束按本轮生成token的SHA256撤销会话，不撤销别人的会话。若数据库不可用导致撤销失败，记录错误，原会话按8小时正常到期。

## 四组断言

| 组 | 过程 | 通过条件 |
| --- | --- | --- |
| 双进程 | 32个同key请求分发两节点；两用户各申请6个争10个；同游标跨节点；两Redis节点20请求 | 同key一个预约、余量8；争抢仅一方成功余量4；游标有效且递增；5放行15拒绝且只占1名额 |
| 响应丢失 | 预约提交后响应前进程halt；向另一节点重放原key | 确认网络响应丢失、退出137及故障标记；重放id与标记一致、DB一条预约、余量8 |
| Outbox发送窗口 | 初始占满/候补消息先完整消费；取消后发送容量释放事件，broker确认后DB标记前halt；重启 | 崩溃时published=false，稳定eventId至少2次发送尝试；最终发布/消费、Inbox1、补位1、候补用户预约1、余量8 |
| 消费提交窗口 | 同样先消费初始消息；释放事件导致补位提交，ack前halt；同group重启 | 崩溃后Inbox已经1，但committed offset未越过目标消息；重启后offset越过且lag0；预约/补位各1、余量8 |

每组最终检查全库容量/有效身份/规划队列守恒全零。对消息链路先停初始正常消费者，再启故障进程；不会让容量扫描代替Kafka完成补位。恢复等待最长90秒，启动最长120秒，不无限重试。

两个用户竞争只是一条小样本正确性验证，不是吞吐压测；32个幂等请求也不是32笔新业务。Redis固定窗口允许窗口交界突发，测试不声称公平。默认提交offset代表下一条要读取的记录，因此目标offset必须严格小于最终committed offset，依据[Kafka官方消费语义](https://kafka.apache.org/39/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)。

## 输出证据

experiments/process-<timestamp>/：results.json包含逐组结果、真实PID/端口/退出时间/退出码；每进程log；outbox-audit.json和consumer-audit.json包含原eventId、故障marker、前后SQL及Kafka group offset快照。脚本断言失败时仍保存已运行结果，不能把失败文件夹当成功报告。

marker格式EVENTFLOW_TEST_CRASH；消费者marker另包含topic/partition/offset。没有实际marker及137退出不能算崩溃窗口命中。发送重试以原source event及attempts对账，不以重复消息数加库存。offset与Inbox配合检查，不声称跨Kafka/MySQL分布式exactly-once。

实验保留场次/事件/topic作为证据，不自动删除。Kafka消息有24小时保留期，需要长久复验应保存本轮对账及备份；反复运行会累积topic，定期确认后清理，不擅自批量删除。

## 未覆盖

Kafka 单机服务正常停机/恢复现已独立实测，见 [Kafka 报告](../experiments/process-1789727089055/README.md)。入口与容器停机影响见 [Kafka 实验说明](Kafka停机恢复实验.md)。下面的未覆盖项是四组初始实验的边界，不表示后续 Kafka 停机恢复仍未执行；强杀、多副本容灾、长时间积压仍未覆盖。

后续已新增独立入口 `bash scripts/local.sh redis-experiment`：专属 TCP 代理切断实验应用到真实 Redis 的连接，断言 5 个预约请求全部 503、数据库不产生预约且库存不变；恢复连接后同一 Java 进程重试成功。此入口只运行 Redis 连接实验，不重新运行上表四组。实测见 [Redis 连接故障报告](../experiments/process-1789726768095/README.md)。这是连接故障保护验证，不是 Redis 服务停机/重启、缓存性能对照或可用性降级。

这四组不等于完整B5。尚需Kafka服务停机/恢复、Redis故障/回填性能对照、MySQL备份恢复、更多确认/取消/过期竞争、持续多实例负载和真实模型对照。Planner worker失联目前有机制测试，未在此脚本中做独立进程故障。没有生产QPS、成功率提升、跨机房容灾或精确计费结论。
