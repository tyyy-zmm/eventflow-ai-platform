# EventFlow 后端完整设计与验收合同

设计版本：1.0，2026-09-18。范围：本地可复现的模块化单体活动预约平台，不是生产上线报告。

实施更新：B1及B2/B3/B4/B6主要链路代码已落地，B5已进入真实环境验证，见[迁移说明](迁移与验证.md)及 experiments 的原始报告。集中入口为 `bash scripts/local.sh pre-ai`；只有对应结果为 PASS 的报告才能作为完成证据。下文保留完整目标合同；“本轮只补设计”等历史描述指设计定稿轮次，不代表当前代码状态，也不代表所有生产级目标已验收。

本文件是后端后续实现的主合同；与上级《秋招项目设计与包装.md》冲突时，以本文件为准。本轮只补设计，不修改业务代码。文中的新表、正式API、监控和故障策略均为目标设计，不能据此宣称已实现。

## 1. 最终范围与技术取舍

主链路：查询活动详情 → 用户显式申请预约/候补 → 创建HELD → 用户确认或取消/系统过期 → MySQL释放名额 → Outbox经Kafka唤醒 → FIFO候补补位 → 用户查询补位预约。

MySQL是名额、身份、状态与任务的权威来源。Redis仅做目录缓存和入口限流。Kafka承载可靠唤醒，不承载库存账本。AI只读查询，用户确认才进入交易接口。

采用Java17、Spring Boot3.3.5、JdbcTemplate、TransactionTemplate、Flyway，保持现有工程模式。MySQL8.4、Redis7.4、Kafka3.9.x是本地验证版本线，首次容器实现时锁定具体补丁版本与镜像digest并记录兼容测试，不使用latest。两个应用实例共享同一MySQL、Redis与Kafka；单broker不声称副本容灾。

不做支付、选座、跨场次原子行程、微服务、Redis库存预扣、CDC、真实短信、开放式Agent交易工具。不会为简历增加没有业务必要的分库分表和多级缓存。

模块边界：auth处理身份；catalog处理目录与缓存；booking统一交易；delivery处理Outbox/Inbox与异常恢复；maintenance处理到期/扫描/清理；operations处理审计/监控；planning只能调用只读应用服务，不能直接写表。

## 2. 业务合同与时间

- 一个场次就是一个独立名额池，暂不增加独立event或capacity_pool表。人数1~20且不超过场次总容量。费用为整数分，无支付义务。
- 同一用户同一场次，最多一个有效预约或有效候补，两种身份互斥。取消后允许新意图重订，历史不删除。
- HELD与CONFIRMED占名额；CANCELLED与EXPIRED不占。过期尚未扫描的HELD仍占名额，不能提前从守恒统计中剔除。
- HELD期限为min(数据库当前时间+5分钟，开场时间)。确认要求DB now < deadline，过期要求DB now >= deadline。
- 开场前HELD/CONFIRMED可取消；到期未扫的HELD也可取消，但不能确认。开场后拒绝新的确认、预约、候补、取消预约。终态同操作重试可以返回既有结果，不重新变更。
- 场次下架只禁止新申请，不取消已持有预约；既有HELD仍可按原期限确认。售罄并不等于下架。
- 候补FIFO按场次内数据库sequence_no，不按客户端到达时间。队首大组不足则停止，不跳小组；主动登记候补允许在有余量时发生。
- 补位产生新的HELD，仍有5分钟确认期限。MATCHED候补不会自动再次排队；预约过期/取消后，新意图重新登记才排到队尾。
- 开场时WAITING变为CLOSED并删除有效候补身份；不补位。预约CONFIRMED历史保留，不因活动结束释放名额，守恒式仍成立。
- 已发布场次不调整开场/结束时间、容量、城市区域和价格。允许修改标题/介绍和下架；需要调整关键字段时新建场次。这避免历史预约费用和AI引用被静默改变。
- 场次正式发布必须有ends_at且ends_at > starts_at、price_cents >= 0。现有Demo数据缺失ends_at不能当可规划正式场次。
- UTC贯穿数据库连接、JVM与API，输出ISO8601带Z；前端负责展示当地时区。事务裁决只使用DB时钟，模型或客户端日期不能决定截止时间。

Outbox业务身份约束目标为(event_type,source_id,source_revision)，同一来源不同合法修订不能被误拒。CapacityRecheck使用独立UUID来源，不占用预约源身份。消息不保存电话号码、邮箱和模型对话。

约束包括capacity>0、0<=available<=capacity、quantity>0、状态白名单、必要FK。跨表互斥及字段匹配不能仅靠单表CHECK证明，依赖统一场次事务并以对账检查。

索引按查询定义：预约(user_id,created_at,id)、到期(status,deadline,id)、候补(session_id,status,sequence_no)、Outbox(published_at,next_attempt_at,created_at,event_id)、登录会话(token_hash)、待重放(status,next_attempt_at,id)。记录EXPLAIN/扫描行数后调整，不能承诺所有OR租约过滤都能充分走索引。

列表用(created_at,id)或(sequence_no,id)游标，默认20、最大100，限制条件白名单。游标绑定用户/过滤条件并签名，变化中列表不承诺完整快照。request_key仅接受小写ASCII `[a-z0-9_-]{1,128}`，token_hash/摘要用二进制或大小写明确的排序规则。

## 4. 正式API与身份

正式前缀/api/v1；现有/demo保留且默认关闭，不作为正式接口自动别名。正式接口需新controller和安全过滤链，正式模式拒绝X-Demo-User。资源归属在服务层再次核验，未知和不属于本人均返回404，减少ID探测。

| 方法与路径 | 合同 |
|---|---|

| GET /sessions | 城市/日期/发布状态查询，结构化分页检索直接查DB |
| GET /sessions/{id} | 目录详情，可陈旧，有revision与读取时间，不含权威余量 |

| POST /reservations | body含sessionId/quantity/requestKey，user来自身份；返回当前预约 |
| GET /reservations/{id}，GET /me/reservations | 本人详情与游标列表 |
| POST /reservations/{id}/confirm，/cancel | 状态幂等转换，返回当前状态/revision |
| POST /waitlists | sessionId/quantity/requestKey；稳定请求重试返回原登记的当前状态 |

| GET /admin/replays/{id} | 查看重放状态，不接受任意URL、SQL、offset或消息体 |

统一错误结构：code、message、requestId、retryable；429/503提供Retry-After（429基于窗口剩余时间，503初始1秒）。400参数、401无登录、403非ADMIN、404非本人/未知、409状态/幂等/候补规则冲突、429准入拒绝、503依赖/资源不可用。sold_out属于409业务拒绝，不计系统错误。

本地鉴权采用Spring Security与PasswordEncoder，预置普通用户和ADMIN。登录成功生成加密随机256-bit opaque Bearer token，客户端只收到一次，数据库仅存SHA-256 hash；绝对有效期8小时，不滑动续期，不做JWT+Redis双重会话体系。查询DB验证过期/撤销，DB不可用不放行。密码编码参数实现时通过安全库配置与测试固定，禁止自写密码加密。登录同错误文案，DB持久计数限制连续失败并设置有界冷却，Redis额度只能辅助，不是唯一防爆破机制。

Bearer放Authorization，不放URL/日志；本地绑定loopback，非本机部署需TLS。限制请求JSON 64KiB、候选列表50、介绍2000字符；日志/审计脱敏。管理员不能绕过状态机修改名额或直接删除Inbox。

## 5. MySQL事务与幂等设计

TransactionTemplate使用READ_COMMITTED；统一顺序为场次容量行FOR UPDATE → 当前预约/候补及有效身份 → 请求记录 → Outbox。同场次所有写入必须走该路径。目录发布/修改也取得同一场次行。单事务不操作多个场次；未来若批量写必须固定场次ID升序，不在本版承诺。

创建预约：身份/参数/准入 → 开启事务 → 锁场次 → 查询原请求（先于开场/下架拒绝，允许历史重放）→ 新意图检查发布/时间/身份/候补优先 → available>=quantity条件扣减且affectedRows=1 → 创建HELD及价格快照/有效身份 → 保存请求记录 → 写Outbox → 提交。事务内不调用Redis、Kafka、模型或HTTP。

确认/取消：先查本人对象以定位场次，事务内取得场次锁后重新读取与授权；确认仅未到期HELD；取消仅开场前HELD/CONFIRMED。revision+旧status条件更新必须恰好一行。取消和到期的名额释放、有效身份删除、状态修订、事件提交全部原子。重复目标状态不再释放/生成事件；曾确认后取消，重试确认返回409而不是重新确认。

新候补登记同样锁场次，先查ef_waitlist_request后校验新意图；原键不同人数409；原键已MATCHED/CANCELLED/CLOSED仍返回原登记，不能新建到队尾。新登记递增场次序号、插入身份及事件同事务提交。序号允许不连续，但不回退。

补位：锁场次 → Inbox检查 → 校验消息身份摘要 → 登记Inbox → 查当前发布状态/开场条件与最早WAITING → 足够则条件扣减并创建HELD → 固定MATCHED预约ID/删除有效候补 → 新Outbox。下架暂停新补位，不撤销候补，重新发布事件唤醒；开场后关闭候补。每事件最多补一组，仅下一队首可满足时再发CapacityRecheck，扫描也重新走相同事务。

数据库锁等待目标配置2秒、事务10秒上限，API总处理目标5秒；初始值需集成验证，不把Java事务timeout当所有JDBC语句硬中断。发生死锁/锁超时必须确认事务回滚后，最多重试一次，复用原请求键；未知提交结果不直接判失败重新生成意图，客户端用原键查询重试。增加SQL超时、连接池等待超时并记录等待，不能无限堆积。

请求记录保留到max(创建后30天，场次结束后7天)，有效业务关联未终结则不清理。幂等合同明确只覆盖保留期；过期场次拒绝新请求，所以删除历史键不会重新占旧场次。业务失败不缓存为成功结果；请求重试可能因余量变化而成功。

守恒：available + SUM(HELD/CONFIRMED.quantity) = capacity；有效身份与状态/quantity匹配；预约/候补身份交集为空；MATCHED只有一个固定预约ID。检查在暂停写入的实验检查点，或独立REPEATABLE_READ一致性快照中读多表，不拼接不同时间的读。报警只读，不自动猜测修复库存。

## 6. Redis缓存、回填与更新闭环

最终采用同步cache-aside + 跨实例令牌回填锁，不采用软过期异步线程池，也不增加L1缓存。现有TTL与锁实现保留，补齐超时/失效/响应元数据。没有实现的“异步重建收益”不得继续写目标简历。

Key：eventflow:catalog:{sessionId}，同slot的:lock。详情TTL随机55~65秒，JSON null负缓存5秒；锁TTL10秒。请求先GET → miss用随机token SET NX PX → 获锁后二次GET → 短超时读DB → Lua校验owner后SET详情 → owner条件DEL锁。竞争者以随机抖动做最多3次、总计约45~90ms的有界重查，命中胜者回填后直接返回，超出预算才返回503；不会绕过锁直接回源。锁过期允许重复读取，但旧owner不能覆盖/误删新owner。

回源查询目标超时2秒，只有读取耗时<=3秒且仍持有token才能回填；响应总预算3秒。数据库任务即使取消失败也不得继续回填。TTL从回填开始计，不宣称“提交后65秒必然新鲜”；更新失效故障加上读取延迟，初始保守陈旧预算68秒，需通过故障实验核验且明确适用请求截止/Redis正常计时假设。对资格/名额/预约截止/真实价格裁决全部绕过缓存。

管理员改目录：锁场次+expectedRevision检查 → 更新字段并catalog_revision+1 → 同事务upsert ef_cache_invalidation，generation+1 → 提交。提交后尝试失效；失败不撤销已提交目录，不返回“更新没生效”，返回新revision及cacheInvalidation=PENDING。

失效Lua同时DEL详情和:lock，阻止提交前读取的旧owner在删除后回填；新请求重新获取token读新目录。失效不会回填事件中的旧payload，因此乱序/重复失效最多降低命中率，不倒退目录。后台任务短事务领租约、事务外执行Lua、按owner+generation条件完成；新更新发生时旧任务不得覆盖新pending。Redis长期不可用时任务保留并告警，恢复后重试；TTL只是兜底，不是强一致性。

详情Redis故障默认明确503，不无限降级直查DB。可另设受控实验DB直查模式作基线，不能运行中自动切为无限回源。结构化搜索/余量直查DB，使用单实例并发上限与限量分页，保护连接池；Redis清空会丢失限流和锁，仍由DB保证交易正确性。

## 7. 准入与背压

当前依次执行每用户每接口60次/分钟、每用户每场次5次/10秒及每活动200次/秒三个固定窗口；最后一层专门限制大量不同用户同时竞争同一场次行锁。Lua返回count与PTTL，使Retry-After可计算。窗口从第一次请求开始，相邻窗口可突发，明确不叫令牌桶或严格全局公平。新预约/候补均计数，包括幂等重放；GET本人结果提供恢复路径，不把重放放行实现成可绕过流控入口。

补充每用户每接口60次/分钟聚合额度，防创建无穷sessionId键；两层脚本都在事务前执行，多key不声称联合原子扣费。任一拒绝均不进入预约事务。取消/确认不受新申请额度限制，但受独立高阈值防滥用并发保护。合法排队顺序由MySQL决定，不由Redis额度决定。

单实例交易并发门初始16、目录回源4、搜索/余量查询8；快速拒绝不排无界队列。Hikari初始max24、connectionTimeout1秒，worker独立并发池保持有界；应用实例之间不声称全局并发上限。参数用于初始预实验，之后冻结同配置对照，不预填吞吐。

## 8. Kafka交付与消费者合同

主题沿用eventflow-capacity，3分区/单副本本地配置，key为sessionId。本版只有预约/候补领域事件进入Kafka，目录失效使用独立DB任务，不再增加无实际消费者的catalog主题。Inbox消费者名称waitlist-v1；以后引入独立消费者时分别命名，不能共享单一去重标记。

消息：eventId/sessionId/eventType/schemaVersion/sourceId/sourceRevision/occurredAt。schema1当前只含四字段，升级schema2时先上线兼容读取schema1/2的消费者再升级生产者。要求UUID规范格式、ID>0、类型白名单、64KiB大小限制。schemaVersion不等于sourceRevision。相同eventId不同摘要属于身份冲突，不作为正常重复。

生产端acks=all、enable.idempotence=true、发送总超时10秒、应用等待最多12秒、租约30秒。领取短事务FOR UPDATE SKIP LOCKED，只适用于Outbox工作领取，不用于跳候补队首。事务外发送成功后按owner标记；即使租约过期旧发送者也可能已把消息送出，所以接受at-least-once，不能宣传exactly-once。

失败next_attempt_at按1/2/4/8/16/30秒退避加抖动，租约未到期不重领；实际重试时点同时受租约到期约束。租约被换owner后旧worker不覆盖状态。长时间失败不删除/永久停止源事件，超过20次或最老未发布>60秒告警。暂停worker不会丢记录。

消费者数据库事务提交后ack；默认同步按分区处理，不使用异步完成后跳offset。可恢复DB故障暂停处理、周期重试，max.poll.records=10、max.poll.interval.ms初始300000；使用容器支持的暂停/退避而非长sleep，并通过所锁定Spring Kafka版本集成测试核验再均衡。有限重试后自动ack丢业务被禁止。

正常重复返回已处理结果，不再写业务。格式错误/不支持schema进入持久隔离后才ack；DB不可用连隔离都不能提交时不ack。一致性错误暂停并告警，管理员核查后选择修复根因重试或明确隔离，不能自动把约束冲突当无害消息吞掉。未知session先检查源事件存在性，若外来无效消息可隔离；自有已提交源事件却缺场次是完整性事故。

## 9. 异常隔离、重放与通知

失败记录保留topic/partition/offset、受限消息体/摘要与原因，数据库中可定位原始证据；不只存一句错误。payload只允许业务事件字段，敏感未知字段脱敏；无法安全保留时只存摘要并明确不可自动重放。错误记录按源位置唯一，重复投递不会重复建异常工单。

管理员重放必须选择已有记录、填写原因、通过角色校验和审计；同requestKey只创建一个ef_event_replay。worker租约领取，在事务外发送已验证的原eventId，发送确认后标记。发送与标记窗口仍可能重复，由Inbox拦截。失败记录状态OPEN→REPLAY_REQUESTED→RESOLVED只能依据实际处理证据，发送成功不等于业务已完成。

已处理事件重放应无新业务效果，不能删除Inbox强行重跑。修正非法消息体需要管理员建立新事件身份并保留supersedes关联；只能从权威DB重建合法唤醒事件，不能编辑数量让消息直接加库存。不提供任意offset跳跃接口；Kafka超保留期依赖DB源记录与定时核对恢复。

原身份重放限定事件年龄90天内且未越过其去重保留合同；失败证据保留180天不等于180天内都允许执行。超出窗口仅可查看证据，必要时经审计生成新的CapacityRecheck并依据当前状态检查；不以“原始业务再执行”恢复。已有待重放或未解决异常保护关联Inbox不被时间清理。

补位结果通过MATCHED.reservation_id和本人查询持久可见，本版不新增短信服务。可以新增站内通知记录作为后续用户体验，但不是本版可靠性验收的必要依赖；通知失败不回滚补位，用户不确认则HELD正常过期。

## 10. 后台任务、清理与运维

过期扫描每5秒批量100，按deadline/id稳定推进，每笔重新锁场次并复查。多实例可能重复扫描但只一次转换，不依赖进程内锁保证正确性。

候补修复每15秒批量100，扫描开场前且队首可满足的场次；单次执行<=5秒，增加游标/轮转防止固定低ID热点饿死后面。开场清理每15秒关闭WAITING并删有效身份，在场次锁下每批最多100；不足一轮继续下轮，结束后不再生成补位。下架不关闭队列。

任务分别使用有界执行器，不与模型线程共享；健康状态暴露最近开始/完成/失败时间。消费者与扫描可重复触发，但触发来源MESSAGE/RECONCILE必须记录，不能拿扫描完成证明Kafka链路无丢失。

保留初始合同：Kafka7天、已发布Outbox30天、Inbox90天、异常/重放/审计180天；未发布Outbox、未解决异常、有效预约和候补不能清理。Outbox超过30天仍未发布时不得清其关联Inbox；Inbox清理必须额外检查是否存在未发布源事件/待重放/未解决失败，不能只凭processed_at删除。管理员重放仅支持保留证据窗口。

历史预约/候补先不删，后续匿名化单独设计；幂等记录按第5节保留合同清理。清理每天小批1000并记录数量，不TRUNCATE、不自动重置ID/序号。备份MySQL数据卷及逻辑备份，恢复后核验Flyway历史、守恒、积压和身份关联；Redis可重建，Kafka源可从保留Outbox对账，但不承诺超保留期无限恢复。

## 11. 可观测性与故障处理

采用Micrometer/Actuator/结构化日志，管理端口仅loopback；指标不带userId/sessionId/eventId高基数标签。requestId贯穿HTTP/Outbox日志，eventId/sourceRevision/consumerName用于日志追踪，不把API key/token/密码或整段模型对话写入日志。

指标：业务成功/售罄/候补优先/幂等冲突/429/503分开；HTTP P95/P99、DB连接等待/事务耗时/锁超时、回源次数/缓存命中/锁竞争/陈旧revision、Outbox pending/oldest_age/attempts、Kafka分区lag、Inbox重复、异常OPEN数、补位延迟与扫描兜底数、到期扫描延迟。补位延迟从DB释放事件occurredAt到补位事务完成，不用消费开始代替提交。

初始告警规则（目标，不是已达到SLO）：守恒偏差/身份交集>0立即；Outbox最老>60秒持续30秒；消费无进展且lag增长>60秒；到期扫描延迟>30秒；依赖503占比>5%持续1分钟；任务连续失败3次。阈值经低负载预实验调整后冻结。低流量告警须加最少请求数，避免单个请求制造比例假象。

| 故障 | 返回/处理 | 恢复与证据 |
|---|---|---|
| MySQL不可用/连接池满 | 权威查询/交易503，不凭缓存确认 | 原键重试；回查状态与守恒 |
| Redis停机 | 新申请和详情503；已持有预约确认/取消仍可DB处理 | 恢复限流/缓存，补执行失效任务 |
| Kafka停机 | 已提交交易仍成功，Outbox积压；候补扫描可推进 | 恢复原ID重发，分开统计扫描与消息 |
| 提交后HTTP断开 | 结果未知，不自动新键 | 原键返回同对象当前状态 |
| 消费提交后ack丢失 | 重投 | Inbox去重，无再次补位 |
| 旧回填晚到 | owner丢失则不写缓存 | Lua条件结果/交错时间线 |
| 毒消息/身份冲突 | 持久隔离或暂停告警，不静默吞掉 | 管理员审计处理/重放 |

liveness仅表示进程活着，readiness区分DB可用与功能依赖：Kafka不可用不把所有交易实例剔除；Redis不可用暴露新申请/目录降级状态，不能伪装全部就绪。关闭时先停止新流量、暂停任务领取，再等待有界在途事务/发送；未知发送允许租约后重试，不靠“优雅退出”消除崩溃窗口。

## 14. 设计自审与面试边界

自审结论：选定一套主方案，后端接口、事务、故障、恢复、鉴权和证据合同已补齐，可以按B1~B5实施；这是设计自审，不是第三方审查或生产可靠性证明。

- 名额权威单一，所有变更同锁序；瓶颈是热点场次行，Redis/Kafka不能消除它。
- 缓存令牌只保护回填所有权，不保护数据库库存；失效会打断旧回填，不承诺瞬时强一致。
- 原候补键永久映射保留期内原登记，MATCHED固定预约ID，避免历史重试误成新排队。
- Kafka事件只提示重查；库存释放已经完成，不按消息数量加库存；乱序正确性不依赖提交顺序。
- 不会自动ack数据库异常；持久隔离先于ack，管理员重放不靠删Inbox重新执行。
- 下架、开场、队首大组、到期未扫、幂等过期、待办不清理都有明确规则，不把难例留给实现随意解释。
- 本地两个实例/单broker证明应用机制，不证明跨机房容灾。Kafka低流量可以被扫描替代，选择它是为了及时解耦与失败窗口工程实验，不虚构业务规模。

三个后端点的叙述重点：MySQL讲状态机+守恒+响应丢失；Redis讲回填竞争+更新失效+背压的成本；Kafka讲双写窗口+消费事务+恢复对账。权限/监控是共同工程底座，不额外凑成第五条简历。

## 15. 官方技术依据

技术依据核对于2026-09-18；具体实现API需以项目锁定依赖版本集成测试为准。

- [MySQL锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)：用于场次串行化及工作领取；本设计不拿SKIP LOCKED跳候补队首。
- [Redis Lua执行模型](https://redis.io/docs/latest/develop/programmability/eval-intro/)：条件回填/解锁脚本依据；脚本保持短小，不在脚本中做目录扫描。
- [Kafka设计与交付语义](https://kafka.apache.org/40/design/design/)：外部数据库效果仍用业务事务处理，不声称producer幂等覆盖应用所有失败窗口。
- [Spring Kafka异常处理](https://docs.spring.io/spring-kafka/reference/kafka/annotation-error-handling.html)：重试/暂停与恢复行为需要版本级配置和故障验证，不采用默认行为猜测offset安全性。

## 16. AI规划的后端底座（不替代模型设计）

AI入口也需要持久任务和身份隔离。新增ef_planning_task：id/user_id/request_key/input_hash/constraints_json/status/result_json/error_code/lease_owner/lease_until/attempts/deadline/created_at/updated_at；UNIQUE(user_id,request_key)。输入与结果各限制64KiB，独立保留7天，API明确7天请求幂等期，含个人偏好的文本不进入日志。

POST /api/v1/planning-tasks需登录、requestKey和结构化时间/预算/人数；自然语言需求最多2000字符。新任务事务仅保存QUEUED并提交，返回202与任务ID；同键不同输入409，同键同输入返回原任务。GET /planning-tasks/{id}只读本人状态/结果；POST /{id}/cancel使QUEUED/RUNNING转CANCELLED，重复取消幂等，已成功任务不回退。结果不能直接触发预约。

QUEUED→RUNNING→SUCCEEDED/NEEDS_REFINEMENT/FAILED；用户取消或deadline到期分别CANCELLED/TIMED_OUT。READY是规划内容状态，SUCCEEDED是任务执行状态，不是预约成功。worker短事务领取租约（90秒），事务外调用模型，整个任务最长60秒，每次HTTP最多15秒，Agent调用最多5次、总工具调用最多20次、usage预算初始12000 tokens。usage未知标未知，使用请求输出限制和轮次限制，不能保证账单精确不超预算。

保存结果条件必须同时匹配RUNNING+owner且DB now < deadline，保证取消/超时后晚结果不覆盖；每5秒扫过期任务。进程崩溃中的模型调用费用可能已经产生，自动重执行会重复计费：本版租约失效后标FAILED（原因WORKER_LOST），不自动重跑模型，用户显式新键再试。HTTP取消只能尽力停止远端计算，不能承诺远端费用归零。

本地模型worker每实例2并发、待执行任务每用户最多2条，由用户行锁下计数与入队保证两实例不突破；全局QUEUED容量目标100，使用独立容量计数行事务预留/释放，不凭各实例COUNT猜测全局上限。资源拒绝429/503，无界executor队列被禁止。模型配置仅环境变量持有密钥，Provider白名单、固定HTTPS基址，不允许客户端指定任意URL以免SSRF。接入或发测试数据前确认Provider、费用和数据范围。

新增ef_planning_queue_quota单行记录queued_count/limit，CHECK 0<=queued_count<=limit。任务创建/领取/取消/超时统一锁序：quota行 → 用户行 → 任务行；创建前定位身份，其他操作可先非锁读取任务归属，但事务中必须重查。每用户2条限制包含QUEUED与RUNNING。QUEUED创建计数+1，离开QUEUED仅一次-1；领取后不重复释放，终态重试不改变计数。单行quota是本地小容量队列的刻意取舍，不宣称无热点无限调度。

input_hash按规范化结构化请求计算，时间统一UTC、预算统一整数分、字段固定排序；不能直接把任意JSON空白变化当新意图。B1~B5之外，规划底座作为B6实施，需先有正式鉴权和有界查询工具；模型权限/预算与效果评测是单独验收。

AI角色只拿受限只读工具和显式请求上下文；候选ID最多50、方案最多10场次，模型生成的SQL/用户ID/交易命令不执行。数据库工具走受控查询/并发门，不能持场次锁等待模型。最终规则验证重新查DB，返回observedAt和unknown项；即使通过也不占库存。

底座验收：跨用户404、相同键并发只一任务、两个实例限额、worker崩溃不自动重复计费、用户取消vs晚结果、超时终态不覆盖、结果7天清理与幂等期限。模型成功率、单/多Agent消融与费用收益另按上级实验合同验证，不混入后端正确性通过数。
