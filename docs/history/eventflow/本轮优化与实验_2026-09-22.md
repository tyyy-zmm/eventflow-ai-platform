# EventFlow 本轮优化与实验（2026-09-22）

## 结论

本轮按“预约入口过载保护、缓存过期体验、Agent 语义信息”三个优先级完成了代码、实验和材料更新。MySQL、Redis、Kafka、Multi-Agent 四条主线不需要推翻；新增内容补齐了原版本最容易被追问的三个缺口。

## 1. 活动级准入

原实现只有每用户每接口 60 次/分钟及每用户每场次 5 次/10 秒，能防单用户刷接口，但大量不同用户仍会同时竞争同一条 `ef_session` 行锁。

现增加可配置的每活动固定窗口，默认 200 次/秒，预约和候补在进入 `BookingService` 前执行。Redis 只做过载准入，最终名额仍由 MySQL 事务扣减。三个窗口不是联合扣费；前层计数后被后层拒绝属于保守消耗，不影响交易正确性。

真实本机实验使用默认关闭的 benchmark 入口，复用 `AdmissionGate` 与 `BookingService`，排除鉴权 SQL：

| 模式 | 瞬时请求 | HTTP 200 | HTTP 429 | 写入预约 | 成功 P95 |
|---|---:|---:|---:|---:|---:|
| 未启用 Redis 准入 | 200 | 200 | 0 | 200 | 1148.6ms |
| 活动窗口 20 次/秒 | 200 | 20 | 180 | 20 | 462.1ms |

两组均保持 `persisted + available = capacity`。该实验说明活动窗口能在 MySQL 行锁前削峰，不代表生产吞吐或默认 200 次/秒已经完成容量规划。证据：`experiments/process-1790007850902/results.json`。

## 2. 缓存竞争有界等待

原实现中，缓存未命中且未获得回填锁的请求立即返回 503。现改为随机抖动 15~30ms、最多 3 次重查；命中胜者回填后直接返回，超出约 45~90ms 预算才返回 503，且竞争者仍不会绕过锁直查数据库。

正式鉴权详情接口以 50 RPS 连续运行 70 秒，共 3500 次请求，跨过一次 55~65 秒随机 TTL：

- 3500 次均返回 200；
- 目录 SQL 回源 1 次，缓存命中 3499 次；
- P95 6.9ms，P99 8.6ms。

该结果证明本机单热点回填窗口可由有限等待吸收，不外推为多节点生产 SLO，也不改变正式接口仍有鉴权和发布状态 SQL 的事实。证据：`experiments/process-1790008010858/results.json`。

## 3. Agent 活动语义与评测

原候选只有 ID、城市、时间、价格和余量，无法可靠判断“看展、不要体育”等偏好；原 v2 评测主要比较最终状态及硬约束，也不能证明选中的具体活动符合偏好。

现将标题、描述和区域加入候选合同：Discovery 依据活动语义筛选，Planner 负责编排行程，Java 继续校验城市、时间、预算、余量、ID 白名单及冲突。候选文本仍按不可信数据处理，模型不能执行预约或创造 ID。

新增 `planning-semantic-v1.json`，评测器会核对具体活动 ID 组合。覆盖中英文偏好、多活动顺序、排除条件和候选文本提示注入：

| 数据集 | single | Discovery+Planner |
|---|---:|---:|
| 开发集 | 8/8 | 8/8 |
| 固定测试集（一次） | 8/8 | 8/8 |

固定测试 single 为 8 次调用、2852 Token、P95 932ms；双角色为 16 次调用、5133 Token、P95 1383ms。因此可以说“偏好选择已经按具体方案验证”，但不能声称这组语义任务中多 Agent 更准确。多 Agent 的已观察收益仍是 v2 复杂反馈场景中的输出契约稳定性（44/44 对 40/44）。

原始证据：

- `eval/runs/semantic-dev-2026-09-21T16-28-06.661274Z-5024320676426185825/events.jsonl`
- `eval/runs/semantic-test-2026-09-21T16-29-03.072285Z-15276224767116589694/events.jsonl`

## 4. 推荐简历口径

- Redis：`构建 Cache-Aside、随机 TTL、owner 回填锁与用户/活动级 Lua 准入；同机三轮热目录压测中，可持续档位由 MySQL 直读 1000 QPS 提升至 Redis 3000 QPS，3000 档成功率 100%、P95 不高于 18.2ms。`
- Agent：`拆分 Discovery/Planner，基于活动标题、描述和区域完成偏好筛选与行程编排，并以 Java 校验预算、时间冲突和余量等硬约束；规划只读，用户确认后才进入预约事务。`

活动级准入和语义评测数据优先用于面试追问，不必全部挤进一页简历。

- 双进程预约、响应丢失、Outbox 发送后崩溃、消费者提交后崩溃等进程级契约；
- MySQL、Redis、Kafka 30/120 秒停机及扫描器兜底恢复；
- 规划任务进程恢复、缓存负载矩阵、MySQL 备份恢复；
- 证据清单完整性检查。
