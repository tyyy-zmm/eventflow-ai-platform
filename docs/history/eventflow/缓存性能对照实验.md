# 热点目录缓存对照

## 重现与隔离

```bash
bash scripts/local.sh cache-experiment
```

使用现有私有 `.env`、隔离库 `eventflow_it`、新建已发布场次，HTTP 18191/18192 必须空闲。两个独立 Java 进程使用同一个构建和数据；18191 关闭 Redis，18192 开启 Redis。两者 Kafka、业务扫描及真实模型均关闭，不停止共享容器，不清库或批量删缓存，结束撤销本轮会话并停止自己的应用进程。

入口先 clean package 和常规测试，再执行四轮 ABBA（无缓存、有缓存、有缓存、无缓存）。每轮预热当前实例 100 次，随后以开环调度 100 请求/秒测 20 秒，客户端最多 128 个并发，5 秒请求超时。每轮固定读取同一目录详情；实际返回的 ID/title 也必须正确。至少 1900、最多 2100 次发送、零客户端丢弃、全部返回有效 200，才能通过本轮验收。

开环请求不能无限排队；记录 scheduled/sent/dropped、逐请求调度延迟与响应延迟。调度明显迟滞时不能把名义 100 请求/秒当作实际稳定到达率。脚本不会为了通过而降速或丢弃失败请求。

## 统计口径

`GET /api/v1/admin/catalog-statistics` 仅管理员可读，返回本进程累计 `databaseReads` 和 `cacheHits`。非管理员访问在实验中必须 403。没有重置接口，重启归零；测量通过预热后/所有请求完成后的差值，不依赖并发时两个计数的原子快照。

databaseReads 在 CatalogService.load 的目录详情 SQL 成功返回后增加，包括查询未找到；不统计失败查询或被信号量拒绝的请求。cacheHits 在缓存值成功解码后增加，包括负缓存；损坏 JSON 不增加。实验使用存在的场次，不混入负缓存。

这些不是全库 SELECT 计数。每个请求仍有鉴权及发布状态的 MySQL 查询；实时库存也不属于缓存详情。不能将目录读取减少比例说成全库负载减少比例。管理员统计查询本身不计入目录读取。

每轮归档 allP95/allP99、成功请求 P50/P95/P99、状态分布、调度延迟 P99 及逐请求原始记录。不是只报告成功请求延迟而隐藏失败。统计为 nearest-rank 分位数。

基线轮目录读取次数必须等于有效请求数；缓存轮已预热，目录读取差值必须为 0、命中数等于请求数，否则判为失败并保存结果。两轮连续缓存测量总时长约 40 秒，小于缓存最短 55 秒 TTL；预热命中不会续期，若机器暂停导致过期，本轮可能失败，不能删除证据或延长 TTL 来伪造热缓存。

## 解释与局限

ABBA 减少单向执行顺序偏差，但两种模式使用不同 JVM，仍存在 JIT、GC、操作系统调度、同机 Docker 竞争等干扰。预热不是严格保证 JIT 已完全稳定。本轮是一个热点、小数据、低至中等固定负载的短测，不是最大吞吐或生产容量测试。

不能仅比较两次 P95 的百分比就写普遍性能提升。需逐轮呈现；缓存若延迟更高，也要保留。减少目录查询不必然提高端到端延迟，因为 Redis 往返、解码和既有鉴权查询仍有成本。

本对照本身不覆盖冷缓存并发、TTL 到期风暴、多热点/随机访问、大目录数据集和不同负载阶梯。后续独立跨 TTL 实验已覆盖正式详情接口 70 秒、50 RPS：3500 次均为 200，目录回源 1 次、命中 3499 次，P95/P99 为 6.9/8.6ms；它仍只是单热点本机实验。本轮只读，不改变库存，也不检验缓存失效正确性，后者已有独立机制和真实中间件测试。
