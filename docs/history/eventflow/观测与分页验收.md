## 公共 Tracking API

Spring component `TaskTracking`：

```java
void started(Task task);
void succeeded(Task task);
void failed(Task task);
Progress get(Task task);
Map<Task, Progress> snapshot();
```

固定 `Task`：`CACHE_INVALIDATION, OUTBOX, REPLAY, CONSUME, EXPIRATION, RECONCILE, CLEANUP, PLANNING, MONITOR`。
`Progress(startedAt, succeededAt, failedAt, consecutiveFailures, inFlight)` 均 long；时间 UTC epoch 秒，0 表示尚未观察到。状态仅当前进程内存，重启重置，不证明数据库任务完成或跨实例全局状态。

每个 started 配一次 succeeded/failed。并发尝试按完成次序累计失败；成功重置连续失败。未开始即完成会抛 IllegalStateException。内部吞掉异常并保留重试的路径必须调用 failed；空 poll 不能充当实际任务成功。catalog 已由主 agent 在 CacheInvalidationService 实际 claim 层包装，请勿再包 CatalogWorker。建议 delivery 分开包装实际 OUTBOX、REPLAY 和 CONSUME 尝试，消费成功在事务提交/处理完成后；不能用 publish 外层正常返回覆盖内部失败。BookingMaintenance 分开 EXPIRATION/RECONCILE，PlanningWorker 仅实际领取尝试计 PLANNING。

本 agent 包装 Maintenance.cleanup 与 Monitor，前者保留旧两参构造，新三参 Autowired 构造注入 tracking；清理 SQL 保留主 agent 保护逻辑。Monitor 成功表示检查执行完成，不表示被检查系统无告警。

指标 `eventflow.task.last.started/succeeded/failed`、`eventflow.task.failures.consecutive` 只带固定 task；`eventflow.task.completed` 只带 task 和 success/failure。无 user/session/request/event ID 标签。

## Kafka 与告警

Kafka enabled 才创建 Admin client；每 30 秒主动采样。使用 Spring KafkaProperties 的 Admin 连接配置和 consumer group；各调用最多等待 2 秒，最坏三步约 6 秒，关闭 client 等待最多 1 秒。status/metrics 读缓存，不在请求或 scrape 中访问 broker。采样超过 90 秒视为 unavailable。

总 lag 指标及固定三分区 `eventflow.kafka.partition.lag{partition=0|1|2}`；`eventflow.kafka.lag.available` 明确可用性。三分区来自当前 capacity topic 合同，改拓扑需同步指标注册。禁用、失败、过期、非空分区缺 commit 均不伪装零 lag；空分区 end=0 无 commit 返回 0。status 保留最近成功样本、时间及 available 标记，消费者须先看 available。没有真实 broker/ACL/认证实测。

Monitor 每 30 秒检查：不变量立即；Outbox oldest>60 秒持续 30 秒；开放异常立即；任务连续失败>=3立即；Kafka unavailable 持续30秒。Kafka lag 首次增长且 commit 不推进开始60秒窗口，后续 lag 停止增长但仍无进展不会取消；commit 变化、lag清零或 unknown 重置窗口。commit offset 求和是本地固定拓扑近似，不是业务事务或跨分区进展证明；再均衡/offset reset 应结合分区样本人工判断。

每个规则首次 FIRING 才告警，持续越界不重复，正常后一次 RECOVERED。短暂越界无恢复通知，恢复后再次越界重新等待。状态进程内存；跨实例各自告警，重启重新累计窗口。监控读取失败只报告监控不可用，不批量把其他规则声明恢复。`StatusService.alerts` 保留旧即时候选字段，不是持续窗口已触发列表；日志转换由 Monitor 管理。

尚未验收设计中的依赖503比例/最少请求数、到期扫描延迟与补位提交延迟；需要相应业务采样定义及跨模块接入。此次不声称达到 SLO。

## 管理员分页

`GET /api/v1/admin/failed-events`、`GET /api/v1/admin/audits` 接受 `limit=1..100`、可选 cursor，返回 `{items,nextCursor}`，**原数组响应变为分页对象**，调用方需适配。异常按 created_at/record_id 升序，审计按 created_at/id 降序；保留受限字段投影，不返回原始 payload。取 limit+1 判断下一页，使用二元 keyset，同时间戳不漏不重复。

复用 QueryService HMAC-SHA256 游标、2048长度限制、用户及接口 scope、2秒查询 timeout 和实例内8个查询并发槽；无 offset 无限扫描。权限仍由既有 `/admin/**` 安全配置执行，本轮没有HTTP角色集成测试。多实例必须统一32+字节 EVENTFLOW_CURSOR_SECRET，否则默认进程随机密钥的游标不能跨实例/重启使用。

不是冻结快照：并发新增/删除和保留期清理可能影响后续页；不能以分页证明历史完整永久保存。无总数，分页上限可调整但不能换用户或接口。

**交接主 agent**：需迁移增加 `ef_failed_event(created_at,record_id)` 和 `ef_audit(created_at,id)` 索引；当前 V7 未包含这两个索引。按本轮模块限制未修改 migration；上线大数据量前应真实 MySQL EXPLAIN 和分页性能验证。H2测试只证明排序/签名/完整翻页机制，不证明生产规模查询成本。
