# Planning 后端底座验收

集成更新：常规机制测试已纳入全项目构建，真实 MySQL 同一契约与 OS 进程恢复由 `bash scripts/local.sh pre-ai` 串行运行。下方“本轮未运行”仅指该模块独立交付轮次；最新通过范围以集中结果文件为准。恢复后额外观察11秒，至少跨两个5秒扫描周期，不以stub数据证明模型效果。

本文件只描述真实模型效果测评之前的生命周期、身份隔离、并发配额和崩溃恢复。stub 是确定性 fixture，不调用真实 Provider，不产生模型费用；stub 成功率、零 tokens 和调用次数不能当作真实模型效果或成本测量。

## 修正与契约

- 创建、领取、取消、过期及结果提交统一先锁 quota，再锁用户，再锁目标任务。全局 quota 是数据库单行串行化边界，每实例 semaphore 仅控制该实例两个执行槽，不是全局 RUNNING 限额。
- 取消先锁定目标任务。领取更新同时校验 QUEUED 和有效 deadline，成功更新才释放一次 queued_count；成功领取 `attempts=attempts+1`。
- expire 的外部扫描仅筛选候选。事务内用 FOR UPDATE 当前读取 status/deadline/lease_until，并用 DB 当前时间重查：仍有效则不改变状态或配额；deadline 优先，RUNNING 较早 lease 到期才是 WORKER_LOST。QUEUED 退出只释放一次 quota。
- 结果提交必须同时满足 RUNNING、相同 owner、deadline 有效、lease 有效。取消、超时、失联或 owner 已变更的晚结果不写回。终态清空 lease_owner/lease_until。
- 不自动重新执行 RUNNING 或失联任务。新 requestKey 是显式重试；同键相同输入只返回原任务，同键不同输入 409。用户最多两个 QUEUED/RUNNING，跨实例由锁保护；全局队列满 503，用户限额 429。
- 默认 deadline 为创建后 60 秒，lease 为领取后 90 秒，保持不变。正常 crash claim 应先到 deadline，变为 TIMED_OUT/DEADLINE。WORKER_LOST 仅在 lease 较 deadline 更早到期的场景测试；不能为实验缩短正常 lease。

PlanningTaskService 新增 Spring 注入的 5 参构造器，最后一个参数为 FaultPoints；旧 4 参构造器保留并使用关闭的故障配置。FaultPoints 本身由主 agent 维护，本模块不修改它。主 agent 已通过 V9 增加 `ef_planning_task.attempts INT NOT NULL DEFAULT 0`；领取、测试和 runner 对 attempts 的断言依赖该迁移。

## Worker 与指标

`eventflow.planning.worker.enabled` 独立控制 PlanningWorker 的领取及 expire；未设置时继承 `eventflow.background.enabled`，两者均未设置则关闭。显式 worker=true/background=false 可运行规划恢复而不启用常规后台扫描。PlanningWorker 保留旧单参构造器，Spring 使用 tasks/tracking 双参构造器。

TaskTracking.PLANNING 的 started/succeeded/failed 记录 executor 内 runOne 调用：正常返回（包括空队列以及被服务转换为 FAILED 的业务失败）表示调用完成；未处理异常表示调用失败。任务业务成功必须读取 ef_planning_task.status，不能根据 runOne=true 或 last.succeeded 推导 SUCCEEDED。expire 不混入此 poll 指标。进程 halt 不执行 finally，旧进程内存指标不能代替数据库恢复证据。

## 测试入口

PlanningLifecycleTest 在 H2 上执行机制契约；PlanningLifecycleIT 在真实 MySQL 上执行同一契约。IT 必须显式选择执行（名称为 IT，默认 Surefire 未必包含），设置 EVENTFLOW_INTEGRATION=true、EVENTFLOW_IT_DB_URL、EVENTFLOW_DB_USER、EVENTFLOW_DB_PASSWORD。URL 只接受 localhost/127.0.0.1、显式端口和 eventflow_it，并检查 SELECT DATABASE()。

IT 使用 DriverManagerDataSource 的真实独立连接和独立服务对象，不模拟 SQL、锁或事务；engine 的阻塞/失败由 fixture 控制，不访问 Provider。另有实际 ModelConfiguration stub + PlanningEngine 路径验证只读完成、库存/预约/Outbox 不变。预筛选续 lease 测试仅拦截候选查询返回时机，实际预筛选和续 lease UPDATE 仍在数据库执行。

测试只清理自己成功插入的随机用户及其任务、随机 session ID 与随机城市匹配的 fixture，保留既有终态任务和实验数据。初始全局 QUEUED=0、RUNNING=0、queued_count=0 且 queue_limit>=2 才能执行；不满足直接失败，不清理、不修复既有数据。RUNNING 前置避免 expire 扫到遗留任务。不得与 HTTP runner 或其他生产者/worker 并行。

全局容量测试先取消自己的 QUEUED 任务，确认实际队列和计数均为 0 后才临时设置 queue_limit=1。原 queue_limit 在 setup 记录，并在 cleanup 的独立 finally 事务恢复，包括业务断言失败或清理事务失败的路径。清理先锁 quota 和自有用户，统计自有 QUEUED 数，只删除自有任务并扣除相应占额，再用全局 COUNT(QUEUED) 核验一致性，不以 COUNT 覆盖或归零计数。如果守恒失败，清理事务回滚并保留证据，仍尝试恢复原 queue_limit；数据库不可用等恢复失败会报告测试失败。

生命周期契约覆盖：并发同键与变更输入、跨用户 404、双实例用户/全局限额、双 worker 单次领取、运行中取消及其晚结果、deadline/lease 到期前后晚结果、owner 隔离、预筛选后 lease 恢复、双 expire 和 cancel/expire 配额守恒、关闭模式、安全错误、提交后故障 hook 与 attempts 保持。PlanningWorkerTest 覆盖开关继承/覆盖以及调用指标语义。

故障 hook 测试抛出 fixture Error 验证已提交的领取与 engine 前位置，不证明真实 OS 进程死亡。真实 halt(137)、独立恢复进程和真实 60 秒等待由主 runner 验证。本轮未运行 Maven、Docker 或测试，以上是新增可执行用例与待验证契约，不是已通过证据。

## Runner 启动与 API fixture

使用 external 的 MySQL 连接配置，数据库必须 eventflow_it。两 HTTP 节点做配额测试时都关闭 worker，防止领取与创建竞争使 QUEUED 观察漂移：

```text
--eventflow.planning.mode=stub
--eventflow.background.enabled=false
--eventflow.planning.worker.enabled=false
--eventflow.test-faults.enabled=false
```

故障进程和恢复进程在此基础上设置 worker=true。只在故障进程增加：

```text
EVENTFLOW_FAULT_POINT=planning-after-claim
--eventflow.test-faults.enabled=true
--eventflow.test-faults.session-id=<新 fixture userId>
--eventflow.test-faults.event-type=
```

FaultPoints 复用 session-id 参数匹配 claim.user；必须使用新用户并排除其旧任务。claim 事务提交后、engine 前执行 `faults.hit("planning-after-claim", claim.user(), "", claim.id())`，由 FaultPoints 校验隔离库并 halt(137)。其他用户不能命中。恢复进程必须关闭故障，仍开启 worker。

API 使用正式登录身份，POST /api/v1/planning-tasks body 示例：

```json
{
  "requestKey": "planning_fixture_1",
  "input": {
    "constraints": {
      "city": "Shanghai",
      "from": "2026-10-01T09:00:00",
      "until": "2026-10-01T18:00:00",
      "budgetCents": 10000,
      "people": 2
    },
    "preference": "fixture"
  }
}
```

runner 应以 DB 当前 UTC 时间生成未来窗口；示例日期仅说明结构。需要成功 stub 结果时，预置该城市、窗口内、PUBLISHED、库存至少 people 的场次。没有候选时允许 NEEDS_REFINEMENT/NO_MATCH，不要求虚构 SUCCEEDED。取消为 POST /api/v1/planning-tasks/{id}/cancel，查询为 GET 同路径。

先用同一新用户跨两个无 worker 节点发送三个不同键请求，预期 202/202/429；保存成功响应数组中的 id 和对应 requestKey，不依赖 SQL 未指定顺序。原键及完全相同输入并发重放 16 次只返回同一个任务，quota 不变；跨用户查询/取消 404；重复取消同一 QUEUED 任务只释放一次 quota，并允许新的不同键入队。

crash case 使用另一个新用户，故障进程成功 claim 后应见 RUNNING、attempts=1、quota 已释放、result_json NULL，并收到 exit 137 与包含 task id 的 EVENTFLOW_TEST_CRASH 日志。恢复进程不应执行此 RUNNING 任务；等原创建 deadline 及最多一个 5 秒 sweep 周期，默认参数预期 TIMED_OUT/DEADLINE、result_json NULL、attempts 仍为 1、quota 与实际 QUEUED 数一致。再观察至少两个 sweep 周期，状态和 attempts 不变。较早 lease 的 WORKER_LOST 分支由生命周期契约单独验证。
