# 客户闭环与候补验收

## 用户链路

```text
搜索/分类筛选
  -> 门店详情（营业时间、口碑摘要、使用须知、实时权益）
  -> 登录或注册
  -> Redis Lua 预扣并提交抢购请求
  -> Kafka 异步建单
  -> 订单页展示受理、库存确认、完成确认三阶段
  -> 确认订单，或取消/超时释放名额
  -> 售罄用户加入候补，释放名额后按 FIFO 自动补位
```

页面展示库存只用于帮助决策。最终资格仍由 Redis Lua 原子校验，MySQL 条件扣减与唯一约束兜底；因此“页面显示有库存”不等于承诺一定购买成功。

## 候补状态机

| 状态 | 含义 | 可执行操作 |
|---|---|---|
| `WAITING` | 已进入 FIFO 队列 | 用户可退出 |
| `PROMOTING` | Worker 已认领，正在预扣和创建请求 | 不允许重复操作 |
| `PROMOTED` | 已生成标准抢购请求 | 后续进入普通订单链路 |
| `CANCELLED` | 用户退出或已不具备资格 | 终态 |
| `EXPIRED` | 活动结束仍未补位 | 终态 |

`ux_waitlist` 以 `(activity_id, user_id)` 唯一约束防止重复排队。Worker 使用 `FOR UPDATE SKIP LOCKED` 认领队首记录，先置为 `PROMOTING`，再复用原有 Redis 预扣、Admission、Outbox/Kafka 和 MySQL 建单链路。Worker 在落库前崩溃时，30 秒租约回收会重新处理相同 `request_key`；原有幂等键保证不会生成重复订单。

订单取消或确认超时后，MySQL 事务先回补库存并记录 `RESTORE` 动作；Redis 恢复完成后，候补 Worker 才能成功预扣释放的名额。MySQL 可用库存和 Redis 可预扣库存共同避免提前补位。

## 接口

- `POST /v2/waitlists`：售罄后加入候补；仍有库存、活动关闭或已经购买时拒绝。
- `GET /v2/account/waitlists`：读取本人候补记录和实时位置。
- `POST /v2/waitlists/{id}/cancel`：仅允许本人退出 `WAITING` 状态。
- `GET /v2/catalog/shops/{id}`：返回门店详情、营业时间、亮点、口碑摘要、须知和实时权益。

## 自动化验收

### 本次验收结果

2026-09-25 在本机 MySQL 8.4、Redis 7.4 和 Kafka 3.9.1 环境完成验证：

- 后端单元测试：77 项，0 失败；其中 33 项真实中间件测试在默认测试集中按配置跳过；
- 客户 HTTP 集成测试：7 项全部通过，包含候补 FIFO 晋升、取消回补与库存不变量；
- 故障恢复实验：9 个场景全部通过，最终未应用补偿为 0、库存违规为 0、状态违规为 0；
- 前端生产构建通过；浏览器实测完成注册、详情、异步抢券、订单进度和确认闭环，控制台无错误或警告；
- 故障实验原始结果保存在 `backend/evidence/faults-1790266215582/`。

### 后端 HTTP 集成测试

`CustomerHttpTest.soldOutWaitlistPromotesInFifoOrderAfterCancellation` 使用三名真实测试账号和一份库存：

1. 第一名用户下单，占满库存；
2. 两名用户依次加入候补，位置分别为 1、2；
3. 第一名用户取消，库存只回补一次；
4. 第一位候补自动生成异步请求并进入 `PENDING_CONFIRM`；
5. 第二位候补保持 `WAITING`；
6. 最终 MySQL 可用库存为 0，待确认订单恰好一笔。

`frontend/tests/customer-flow.mjs` 覆盖目录筛选、详情信息、注册与会话恢复、Kafka 异步建单、确认、取消、重复购买拒绝、未知响应恢复、移动端布局、账号隔离和图片/按钮溢出检查。


### 故障与恢复

`backend/scripts/faults.mjs` 已覆盖以下与用户链路相关的故障：

- Redis 预扣后、MySQL 落库前进程退出；
- MySQL 接受请求后、HTTP 响应前进程退出；
- Kafka 发送成功但 Outbox 未标记，以及消费提交后未确认；
- Kafka 停机期间请求持久化，恢复后继续建单；
- 取消事务中断后回滚并可幂等重试；
- Redis 停机时拒绝新抢购，但保留订单查询和取消能力。

这些实验验证单机/单 Broker 环境下的恢复语义，不代表多可用区容灾或生产 SLA。
