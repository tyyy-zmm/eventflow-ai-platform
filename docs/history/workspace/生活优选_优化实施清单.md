`eventflow` 作为已有实现与实验设计的参考，保持独立；不直接继承它的性能数字。新前端联调与Agent增强放在后端验收之后。

当前源码检查发现：

- `ShopServiceImpl.queryById` 使用空值缓存路径，尚未使用已有逻辑过期路径。
- `CacheClient` 使用固定锁值和直接删除解锁，互斥查询递归等待，重建线程池队列无界。
- 商家更新方法在数据库事务提交前删除缓存，存在旧数据回填窗口。
- 当前生效秒杀路径执行Lua后返回订单ID；Lua内Stream写入及Java消费线程均被注释。
- `createVoucherOrder` 有 `stock > 0` 条件更新，但所读方法未建立扣库存与建单的有效统一事务。
- 已有Kafka依赖与配置；这些不等于可靠投递与消费流程已经实现。

## 2. 推荐架构与取舍

采用 Redis入口保护 + MySQL请求/Outbox原子受理 + Kafka异步建单。

```text
用户鉴权、参数和活动检查
  -> 已有requestId重放查询
  -> Redis用户/活动限流、售罄快速筛选
  -> MySQL短事务：请求记录 + Outbox
  -> 返回202：请求已受理，非抢购成功
  -> Outbox转发器发送Kafka，收到broker确认后条件标记已发送
  -> 消费者MySQL事务：请求判定、购买唯一约束、库存条件扣减、建单、终态
  -> 事务提交后确认消费
  -> 用户查询处理结果及订单
```

- MySQL是库存、订单和请求终态的权威来源。
- Redis本阶段不维护需与MySQL双向补偿的硬预扣库存；Lua用于原子限流。售罄标记采用有界TTL，库存释放后安排失效，误拦截最多造成暂时少卖，不改变最终库存。
- 每个通过准入的新请求仍会写MySQL受理记录；Kafka平滑后续建单压力，不能声称绕开全部数据库写入或天然提高总体吞吐。
- 先不引入Redis Stream、分库分表、分段库存、Canal或两级缓存；后续由瓶颈实验决定。
- Outbox采用至少一次投递，数据库侧保证重复处理无新增业务效果。不宣称跨系统Exactly-Once。

## 3. B0：业务规则、数据合同与基线

- [x] 盘点登录、商家、库存、订单、Kafka路径与已有测试，记录可运行入口。
- [x] 固定首版业务规则：每用户每场秒杀最多创建一张订单，取消或过期后该用户不能再次购买；释放名额可供其他用户购买。后续若改变规则，单独升级身份表设计。
- [x] 定义活动开始/结束时间及处理截止时间：截止前未成功的排队请求转为失败，不能在过期后悄悄建单。
- [x] 请求状态：ACCEPTED / SUCCEEDED / REJECTED / EXPIRED；未知结果保持待确认，不伪装失败。
- [x] 订单状态：PENDING_CONFIRM / CONFIRMED / CANCELLED / EXPIRED；确认是本地业务确认，不代表第三方支付。
- [x] 明确不变量：可用库存 + 未取消/未过期订单数量 = 活动容量；库存非负；每用户活动最多一张订单；请求终态不被迟到消息覆盖。
- [x] 定义requestId作用域与payload摘要；同键同参重放，同键异参拒绝；所有结果查询检查用户归属。
- [x] 建立独立开发/测试数据库、增量迁移与合成数据，不直接运行含DROP TABLE的原始初始化SQL覆盖现有库。
- [x] 已复现原版 Lua 扣库存后未投递的缺陷；原版空转不能作为完整下单性能基线，正式对照使用同约束的同步建单路径。

验收：API和状态转换表可评审，原版基线有结果，业务不变量可通过SQL核对。

## 4. B1：MySQL交易正确性

- [x] 为隔离新表增加请求记录、请求唯一键、订单用户/活动唯一约束、库存与查询索引。本轮未导入历史数据；接旧库时必须另做重复记录审计，不将建新表视为完成历史迁移。
- [x] 将库存条件扣减、订单创建和请求成功状态放在同一真实事务中，由独立Spring Bean公共方法提供事务入口。
- [x] 库存不足、重复购买等业务拒绝持久化；数据库异常回滚，不能吞异常后继续提交。
- [x] 同一请求先锁定/检查持久状态，统一锁顺序，处理重复消费和并发重试。
- [x] 确认、取消、过期均使用条件状态转换；订单状态与库存释放同事务，重复取消不重复释放。
- [x] 请求超时关闭与消费者使用相同请求状态协调；先锁定的合法操作决定终态，已EXPIRED请求不能建单。
- [x] 死锁采用有界整事务重试；事务内不调用模型、Redis或Kafka。

验收：并发争抢、相同用户不同请求、相同请求重放、扣库存后插单失败、取消/确认/过期竞争均满足不变量。

## 5. B2：可靠受理与Kafka异步建单

- [x] 请求与Outbox同事务写入；新增请求成功提交后返回202和requestId，客户端轮询结果。
- [x] Outbox支持领取owner、租约、退避及重试次数；事务外发送，broker确认后按owner条件标记。
- [x] 消息携带eventId、requestId、activityId、schemaVersion；不信任消息传入价格，以服务端规则生成订单价格快照。
- [x] 以activityId作为Kafka Key；同活动顺序处理减少竞争，但正确性依赖MySQL事务与约束，不能依赖消息顺序兜底。
- [x] 配置生产确认、幂等生产和关闭自动提交；事务提交成功后才提交消费位点。
- [x] 以持久请求终态保证建单消费幂等，避免无必要地重复增加去重表。
- [x] 发送成功但Outbox标记前崩溃，恢复后原eventId重投；落库后确认前崩溃，重投不重复扣库存。
- [x] 区分库存不足/已购买等业务结果、可重试基础设施错误和毒消息。
- [x] 非法消息持久隔离后才允许确认；提供鉴权后的查询、原事件重放和审计，暂不以自动跳过全部数据库错误解阻塞。
- [x] 扫描超过处理期限的请求，依据数据库状态关闭；消费者必须拒绝这些迟到请求。

验收：Kafka停机期间已持久受理的请求可恢复处理或按约定到期；重复投递、发送响应丢失及消费者崩溃不会重复建单；状态可查询。

## 6. B3：Redis入口保护与过载控制

- [x] 用户级防刷和活动级准入使用Lua原子窗口计数，返回明确429及Retry-After；不将限流拒绝计入成功业务吞吐。
- [x] 新请求限流前允许鉴权后的已有requestId查询/重放，配合查询侧独立限流，避免重试被当作新抢购。
- [x] 售罄标记只做快速拒绝提示，设置TTL，取消/过期回补后可靠失效；最终库存仍由MySQL校验。
- [x] Redis不可用时新秒杀请求保守拒绝，订单查询/确认/取消不依赖Redis库存；禁止无限回源。
- [x] 给入口线程、数据库连接、转发批量、消费并发设有界容量；积压或最老请求年龄超过阈值时收紧新请求受理。
- [x] 校验Lua键设计与潜在Cluster hash slot边界，不把本地单节点测试说成Cluster验证。

验收：多人同时请求时数据库压力有界，429/503与成功结果分开统计；Redis故障不破坏已受理交易的正确性。

## 7. B4：商家缓存重建与更新一致性

- [x] 区分可短暂陈旧的商家介绍与必须及时检查的券资格/库存；交易判断不使用逻辑过期数据。
- [x] 定义软/硬过期及TTL抖动；软过期返回有限期旧值并异步重建，硬过期与冷缓存使用有界等待/明确降级。
- [x] 保留短TTL负缓存，处理商家新建后旧空值的失效。
- [x] 重建锁使用唯一owner；Lua检查owner后回填与解锁，旧owner不得覆盖新worker结果。
- [x] 获取锁后重查缓存，配置有界线程池、队列、数据库超时与回源并发上限；取消递归等待。
- [x] 商家更新、revision递增与缓存失效任务同事务保存；提交后执行失效，失败持久重试。
- [x] 失效时同步使旧回填owner失效；任务generation避免旧worker清除新失效任务；TTL限制异常陈旧窗口。
- [x] 明确提供最终一致性，不把Cache-Aside描述为瞬时强一致；设置并验证业务可接受陈旧时间。

验收：热Key到期、冷启动、锁过期、慢回源、旧回填与更新竞争、新商家覆盖负缓存、Redis停机和线程池饱和均有测试。
