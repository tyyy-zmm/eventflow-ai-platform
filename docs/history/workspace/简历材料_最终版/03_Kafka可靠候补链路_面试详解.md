# Kafka 可靠候补链路 - 面试详解

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../README.md>)和[当前验收](<../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 1. 为什么需要 Kafka

预约取消或过期会释放名额，候补用户需要被唤醒。直接在释放名额的数据库事务里同步补位，会拉长锁持有时间，并让 Kafka/下游故障影响主交易。项目将“释放名额”与“尝试补位”解耦，但必须处理数据库提交和消息发送之间的失败窗口。

## 2. Outbox 解决什么

取消/过期事务同时完成：

1. 更新预约状态；
2. 释放名额；
3. 写 CapacityReleased Outbox。

转发器用短事务领取发送租约，事务外发送 Kafka，收到 broker 确认后再标记 published。发送失败保留租约并退避，租约过期后使用原 `eventId` 重发。因此系统接受消息重复，不接受业务事件丢失。

不能说这是 Kafka exactly-once。它是数据库 Outbox + Kafka at-least-once + 消费端业务幂等。

## 3. Inbox 与补位事务

消息按 `sessionId` 分区，使同一场次的释放事件有稳定顺序。消费者收到事件后，在同一个 MySQL 事务中：

1. 校验事件身份和 payload hash；
2. 登记 `(consumer, eventId)` Inbox；
3. 锁定场次并读取队首 WAITING 候补；
4. 队首人数足够时扣减名额并创建 HELD 预约；
5. 将候补置为 MATCHED，并记录固定预约 ID；
6. 提交事务后才确认 offset。

队首人数大于剩余名额时不跳过，避免小组插队。每个事件最多补一组，如果仍可能继续补位则生成后继检查事件；定时扫描只用于修复漏唤醒，不能拿扫描成功冒充消息从未丢失。

## 4. 异常消息治理

非法 schema 进入失败事件表，只保存受限字段、原 topic/partition/offset 和摘要；相同 eventId 不同 payload 会被识别为身份冲突，不能当成普通重复。管理员可以按原 eventId 重放或明确忽略，并记录审计。发送成功只表示重放消息已发出，必须等真实消费者写入同摘要 Inbox 后，失败事件才能变为 RESOLVED。

## 5. 故障实验

### Broker 停机

- 停机 30 秒：原应用不重启，恢复后发送和消费继续，补位一次；
- 停机 120 秒并积压 1000 条合成持久唤醒：恢复核验约 63 秒，1000 个 eventId 全部进入 Inbox，各分区最终排空，业务补位仍只生效一次。

这 1000 条是消息 fixture，不是 1000 个客户订单。

### 发送后进程退出

Kafka 已确认发送、Outbox 尚未标记 published 时注入 `halt(137)`。恢复后原 eventId 重发，attempts 从 1 变为 2，Inbox、补位和预约仍各一条。

### 消费事务提交后退出

Inbox 和补位业务已提交、offset 尚未前进时退出。恢复后消息重投，Inbox 去重使业务不重复，随后 offset 正常推进。

## 6. 高频追问

### 为什么不用 Kafka 事务

Kafka 事务可以协调 Kafka 内的 consume-transform-produce，但不能直接把普通 MySQL 业务事务变成同一原子事务。Outbox 明确接受重复发送，用数据库 Inbox 约束业务效果，更适合本项目边界。

### 为什么提交后才 ack

如果先 ack 再提交数据库，进程崩溃会导致消息已经越过、业务却没完成。先提交数据库再 ack 最多造成重投，重投可由 Inbox 去重。

### Inbox 已有记录就能直接跳过吗

要同时校验 payload hash。相同 eventId 但内容不同是冲突，静默跳过会隐藏上游篡改或错误复用。

### 单节点 Kafka 能证明高可用吗

不能。实验验证的是本机持久卷、应用不重启情况下的停机恢复、重投和幂等，不覆盖多副本、跨机网络分区和生产 SLO。

## 7. 一分钟回答

> 我把名额释放和候补补位用 Kafka 解耦，但不依赖 Kafka 提供跨 MySQL 的 exactly-once。释放事务同写 Outbox，转发器通过租约和原 eventId 重投；消费者把 Inbox 去重、场次锁、FIFO 补位和预约创建放在同一 MySQL 事务，提交后才 ack。实验覆盖了 broker 停机 120 秒积压 1000 条消息、发送确认后进程退出以及消费提交后退出，恢复后允许消息重投，但 Inbox、候补和预约的业务效果都只出现一次。
