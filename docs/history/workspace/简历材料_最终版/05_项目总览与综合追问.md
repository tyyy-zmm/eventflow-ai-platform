## 1. 两分钟项目介绍

> EventFlow 是一个活动预约、候补和智能行程规划平台。我基于点评类业务底座，重点重构了四条互相关联的链路。第一，MySQL 作为名额唯一真相，通过场次行短事务、有效预约身份和请求幂等维护预约状态机；第二，Redis 只缓存目录并保护入口，通过 owner 回填锁、revision 失效及用户/活动级准入降低热点回源和写入突发；第三，名额释放后写 Outbox，由 Kafka 异步唤醒候补，消费者把 Inbox 和 FIFO 补位放在同一事务，允许消息重投但保证业务只生效一次；第四，AI 只做只读规划，Discovery/Planner 生成候选方案，Java 做硬校验，用户确认后才进入真实预约事务。
>
> 我没有只写代码，还做了真实 MySQL/Redis/Kafka 故障实验和 DeepSeek 冻结评测。1000 用户竞争 100 个名额时没有超卖；200 用户同时争抢时，活动级准入把进入数据库的请求限制为 20；热目录三轮可持续档位由 MySQL 直读 1000 提升至 Redis 3000 QPS；Kafka 停机 120 秒并积压 1000 条消息后恢复，业务效果没有重复；Agent 固定测试中双角色 44/44、单 Agent 40/44，同时补充了核对具体偏好方案的语义测试。

## 2. 四条如何串成一个业务闭环

1. 用户通过 Agent 发现活动并形成只读行程方案；
2. 用户确认后访问预约 API，Redis 做身份后的入口准入；
3. MySQL 事务检查实时名额并创建 HELD 预约；
4. 取消或过期释放名额，同时写 Outbox；
5. Kafka 唤醒候补消费者；
6. 消费者在 MySQL 事务中按 FIFO 匹配候补；
7. Redis 目录只展示允许短暂陈旧的描述，实时余量始终回到数据库。

这样四条不是四个孤立技术点，而是围绕同一个资源生命周期分别解决交易正确性、读路径保护、跨系统失败窗口和自然语言交互。

## 3. 为什么采用模块化单体

项目规模有限，交易、候补和目录之间有明确的一致性关系。模块化单体可以保留 auth、catalog、booking、delivery、planning 的边界，同时避免为了“微服务”引入分布式事务、服务发现和远程调用复杂度。两个应用进程共享 MySQL/Redis/Kafka，已经足以验证跨进程幂等和锁语义。未来只有在团队独立部署、容量隔离或故障域确实需要时才拆服务。

## 4. 最难的三个问题

### 问题一：幂等和业务唯一不是一回事

请求键解决同一次请求重试，有效身份解决同一用户同场次不能同时拥有两份预约。取消后可以发起新意图，因此两种约束必须分开。

### 问题二：消息可靠不是“不重复发送”

发送和数据库无法天然原子，只能接受 Outbox 重发，在消费事务里用 Inbox 和业务状态吸收重复。故障实验关注的是每个提交窗口，而不是只看正常链路。

### 问题三：模型评测不能只看最终被代码兜底后的结果

如果 Java 拦住所有错误，就可能虚假得到“零违规”。因此同时记录模型输出、修订、协议失败、最终状态、调用数、Token 和延迟，并做 single/dual/adaptive 消融。

## 5. 面试官质疑“是不是包装项目”

回答结构：

1. 承认来源：业务背景和基础工程参考点评项目；
2. 指出新增：正式鉴权、预约状态机、有效身份、Outbox/Inbox、缓存失效、候补恢复、规划任务及评测；
3. 给出可复验证据：具体命令、测试数量、原始 JSONL、故障点和 SHA-256；
4. 主动说负结果：Redis 没改善 P95，Review 没改善正确率；
5. 说明边界：本地单机、单 broker、合成数据，不等于生产 SLO。

这种回答比声称“从零手写完整分布式系统”更可信。

## 6. 数据口径速记

| 模块 | 可以说 | 不能说 |
|---|---|---|
| MySQL | 1000 用户/16 线程竞争，1-7 人组共分配 100 名额 | 1000 QPS、生产抗压 |
| Redis | 正式接口矩阵回源约 -78%；热目录饱和实验三轮全通过档位 1000 -> 3000 QPS | 整个系统 3000 QPS、生产容量、正式接口 P95 提升 |
| Kafka | 停机 120 秒，恢复 1000 条合成唤醒，业务一次 | 1000 订单、exactly-once、生产高可用 |
| Agent | 44 条有效冻结测试，single 40/44，dual/adaptive 44/44 | 总体准确率提升 10%、Review 提升准确率 |
| 测试 | 最终集中验收 7 阶段全部通过：172 项 Java 单元测试、41 项真实中间件集成测试，以及进程崩溃、停机恢复、缓存矩阵和备份恢复 | 全部生产场景已覆盖 |

## 7. 30 秒收尾

> 这个项目最核心的能力不是会用三件套，而是我给每个组件划定了权威边界：MySQL 管交易，Redis 管读路径和背压，Kafka 管异步唤醒但由数据库吸收重复，模型管方案生成但由代码和事务兜底。每条都配了失败窗口实验，而且无收益的结果也保留，所以我能解释它为什么这样设计、验证了什么，以及还有哪些不能承诺。
