## 1. 简历最终四条

- **预约交易一致性：** 设计 `HELD/CONFIRMED/CANCELLED/EXPIRED` 预约状态机，以 MySQL 场次行短事务统一名额扣减、有效预约身份、请求幂等与 Outbox 写入；1000 用户争抢 100 个名额时分配总量严格为 100，响应丢失后原键重试不重复扣量。
- **Redis 热点治理：** 构建 Cache-Aside、随机 TTL、owner 回填锁与用户/活动级 Lua 准入；同机三轮热目录压测中，可持续测试档位由 MySQL 直读 1000 QPS 提升至 Redis 3000 QPS，3000 档成功率 100%、P95 不高于 18.2ms。
- **Kafka 可靠候补：** 基于 Transactional Outbox、发送租约、原 `eventId` 重投及 Inbox 去重解耦名额释放与候补补位；消费者按 `sessionId` 分区并在事务内完成 FIFO 补位，Kafka 停机 120 秒及生产者、消费者崩溃恢复后业务效果不重复。
- **Multi-Agent 规划：** 拆分 Discovery/Planner，依据活动标题、描述和区域完成偏好筛选与行程编排，并以 Java 校验预算、时间冲突、余量和候选白名单；规划只读，用户确认后才进入预约事务。

## 2. 30 秒项目介绍

> EventFlow 是我在点评类业务底座上扩展的活动预约与智能规划平台。MySQL 是名额唯一真相，Redis 负责目录缓存和入口保护，Kafka 通过 Outbox/Inbox 驱动候补补位，Agent 只生成只读行程方案并由 Java 硬校验。四个模块围绕同一个名额生命周期串联，并通过真实中间件、进程退出和停机恢复实验验证，而不是四个孤立的技术点。

## 3. 四条 STAR 回答

### 3.1 MySQL 交易一致性

**S：** 多人同时抢限量场次，取消、过期和候补补位也会并发修改名额；普通唯一索引还会阻止用户取消后重新预约。

**T：** 保证不超卖、名额守恒、同一用户同场次只有一份有效预约，并处理事务已提交但响应丢失。

**A：** 让 MySQL 成为库存唯一真相，所有名额变更统一锁定场次行；事务内完成条件扣减、状态转换、有效身份、幂等结果和 Outbox。同键同参数返回原结果，同键不同参数拒绝。

**R：** 16 线程下 1000 用户以 1 至 7 人组争抢 100 个名额，最终 27 组成功、人数总和严格为 100；事务提交后注入 `halt(137)`，另一进程用原键重试仍返回同一预约且不重复扣量。

一句边界：这是正确性与恢复实验，不是 1000 QPS，也不代表热点场次可无限扩展。

### 3.2 Redis 热点治理

**S：** 热门活动会产生目录热点读和大量用户同时竞争同一场次行锁；Redis 又可能出现穿透、击穿和缓存失效竞争。

**T：** 降低目录数据库回源，并在交易前削减无效写入突发，同时不让缓存成为库存真相。

**A：** 目录使用 Cache-Aside、负缓存、随机 TTL、owner 回填锁和有界等待；更新后通过 revision 与失效任务删除旧缓存。预约入口使用用户级和活动级 Lua 固定窗口，拒绝时返回 `Retry-After`，最终名额仍由 MySQL 判断。

**R：** 本机受控热目录链路三轮实验中，MySQL 直读最高稳定测试档位为 1000 QPS，Redis 为 3000 QPS，3000 档成功率 100%、最差 P95 18.18ms；200 用户瞬时争抢时，活动窗口把进入数据库的请求从 200 限制为 20。

一句边界：3000 QPS 只属于隔离后的热目录链路；正式详情接口的 P95 并未因 Redis 改善。

### 3.3 Kafka 可靠候补

**S：** 取消或过期释放名额后要唤醒候补；如果在交易内同步补位会延长锁时间，直接发消息又存在数据库提交与 Kafka 发送不原子的窗口。

**T：** 解耦主交易和补位，并在消息重复、进程退出及 broker 停机后保证业务效果不重复。

**A：** 释放名额时同事务写 Outbox；转发器以租约领取并使用原 `eventId` 重投。消费者按 `sessionId` 分区，在同一 MySQL 事务中登记 Inbox、锁定场次、执行 FIFO 补位并创建预约，提交后才确认 offset。

**R：** Kafka 停机 120 秒并积压 1000 条合成唤醒后全部恢复；另外覆盖发送确认后进程退出和消费事务提交后退出，消息可以重投，但 Inbox、候补状态和预约只生效一次。

一句边界：这是 at-least-once 加数据库幂等，不是 Kafka exactly-once，也没有证明单 broker 具备生产高可用。

### 3.4 Multi-Agent 行程规划

**S：** 用户会用自然语言表达城市、预算、时间和“看展、不要体育”等偏好；模型自由回答可能虚构活动、超预算或把规划误当成预约。

**T：** 利用模型处理软偏好和组合规划，同时把库存、权限和交易风险留在确定性系统内。

**A：** Discovery 从带标题、描述和区域的候选快照中筛选白名单 ID，Planner 组合行程；Java 再校验城市、时间、整组预算、余量、重复 ID 和冲突。规划全程只读，用户确认后重新进入鉴权和 MySQL 事务。

**R：** 44 条有效冻结测试中，单 Agent 为 40/44，Discovery+Planner 为 44/44，差异来自复杂反馈后的协议遵循；具体偏好语义测试两者均为 8/8，因此只主张职责隔离和这组任务中的协议稳定性，不主张普遍准确率提升。

一句边界：Review 在消融中没有提高正确率，只增加成本，因此不写进简历主结论。

## 4. 面试追问路由

| 面试官问什么 | 先回答什么 | 再展开什么 |
|---|---|---|
| 为什么不用 Redis 扣库存 | MySQL 是唯一库存真相，避免双写补偿 | 场次行短事务、条件扣减、名额守恒 |
| 行锁会不会扛不住 | 会成为热点瓶颈，Redis 只在入口削峰 | 活动级准入实验和扩展方向 |
| 缓存如何保证一致 | 最终一致，revision + 失效任务防旧值覆盖 | owner token、随机 TTL、有界等待 |
| Kafka 会不会重复消费 | 接受重投，用 Inbox 与业务事务吸收重复 | Outbox 租约、提交后 ack、payload hash |
| 为什么一定要多 Agent | 按职责和协议拆分复杂任务，不是为了数量 | 40/44 对 44/44及语义测试的负结论 |
| 项目是不是包装 | 承认点评底座，明确后续扩展边界 | 可复现实验、故障点、原始证据和负结果 |

## 5. 高风险措辞

- 不说“1000 并发”或“1000 QPS”，说“16 线程模拟 1000 个不同用户竞争”。
- 不说“系统达到 3000 QPS”，说“本机受控热目录链路的稳定测试档位达到 3000 QPS”。
- 不说“Redis 保证库存一致”，库存真相始终是 MySQL。
- 不说“Kafka exactly-once”，说“at-least-once 下业务效果幂等”。
- 不说“Multi-Agent 准确率提升”，说“冻结案例中减少协议失败”。
- 不把 1000 条 Kafka fixture 说成 1000 个订单。
