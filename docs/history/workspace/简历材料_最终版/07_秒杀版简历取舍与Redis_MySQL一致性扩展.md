## 1. 简历只保留一套业务

标题建议：生活优选：优惠券秒杀与智能推荐平台。

简介建议：面向本地生活场景，提供商家查询、优惠券秒杀与智能推荐功能。

删除混入的场次预约、候补补位、行程编排、有效预约约束等表述。不要同时列“秒杀流程”和“秒杀流程优化”；只描述最终采用的流程。

四条的职责：

1. Redis：在数据库前判断资格、预扣，减少无效请求进入数据库。
2. Kafka：异步建单，缓冲瞬时请求，配合可靠发送和幂等恢复。
3. MySQL：事务建单与订单生命周期，避免半完成写入、重复订单和重复释放。
4. Agent：辅助找店、查券和比较，不参与秒杀库存裁决。

目标版简历（预扣接入且验证后使用）：

- **秒杀防超卖与一人一单：** 使用 Redis Lua 原子校验购买资格、预扣库存，拦截售罄与重复购买请求，降低数据库压力。
- **秒杀流程优化：** 基于 Kafka 异步建单与削峰，结合 Outbox 发送重试和消费幂等，支持已受理请求的故障恢复。
- **订单事务与状态管理：** 将库存扣减与建单纳入 MySQL 事务，通过唯一约束防止重复订单，以条件状态更新实现取消、超时回补，避免库存重复释放。
- **智能推荐 Agent：** 基于 LangChain4j 构建推荐助手，结合多轮上下文与商家、优惠券查询工具，完成偏好筛选和店铺对比。

前三条各有一件主要事情，不都写“防超卖、幂等、一致性”。Redis 前置控制与 MySQL 最终约束可以同时存在，但第三条着重讲数据库事务和生命周期。跨存储补偿放面试扩展，不为塞术语让句子无限变长。

Agent 代码在旧应用中，不是已接到新 `/v2` 数据源的集成功能。当前旧版 `AgentServiceImpl.chat` 在异常时主要返回服务暂不可用，并附带此前已取得的工具结果；不能说异常后必然重新调用工具完成推荐。旧版 `ShopRecommendTools` 有查询商家、优惠券、营业时间和店铺对比工具，但本次未调用真实模型重测效果。旧 EventFlow 的 Discovery/Planner 是活动行程场景，不能改个标题就当成商家优惠券多 Agent 已实现。

## 2. Redis 应该写什么数据

建议有数据，但先选对测量对象，不预设提升倍数。

优先指标：同一请求负载和业务规则下，新增秒杀请求导致的数据库访问量下降比例。它能直接支持“Redis 前置过滤减轻 MySQL 压力”。区分进入 DB 的请求数、SQL 执行次数和写事务数，三者不能混写。

其次：真实 HTTP 秒杀入口实际完成 RPS、P95/P99、获得资格请求的受理延迟，以及受理到建单完成的延迟。成功建单用 TPS 单列。

不能沿用截图中的“目录 1000 -> 3000 QPS，P95 18.2ms”：那是 EventFlow 目录读实验，不是秒杀写链路。也不能把原话术的“1000 QPS、提升 64.8%”视为这次新版本实测结果。

实验分两类：

- 少量库存、海量用户：验证快速拒绝和减少查库，但售罄后的拒绝速率不等于成功订单吞吐。
- 足够库存、持续有效请求：验证受理写入、Kafka 消费和数据库建单的真实瓶颈。

对照组保持同一机器、资源配额、账号鉴权、限流策略、库存、流量分布和业务规则，至少多轮运行；分别报告正常成功、售罄、重复、429、503、超时及未完成请求。

当前鉴权每次查询 MySQL，入口还在 Redis 前查询数据库幂等记录，准入会查询积压。新增预扣时必须检查这些路径，不能一边每请求查库，一边声称“售罄请求不访问数据库”。会话缓存或本地验签若引入，要另外说明注销与撤销的时效边界；既有请求恢复也不能因 Redis 失效被当新请求重新执行。

## 3. 两种“Redis 和 MySQL 一致性”不能混淆

### 3.1 商家介绍缓存

MySQL 保存原始商家信息，Redis 保存可容忍短暂陈旧的副本。这里适合 Cache-Aside、提交后失效、持久重试与 TTL。

当前升级版把商家更新和失效任务同事务保存；后台删缓存、使旧回填 owner 失效，按任务 generation 条件确认。软过期可返回旧介绍，硬 TTL 限制缓存寿命。这是最终一致性，不是瞬时强一致。

### 3.2 秒杀预扣库存

Redis 中的数值是“尚可发放的资格”，MySQL 中的库存是“尚未由有效订单占用的库存”。异步处理中两者可以有意不同。

例如容量 100：Redis 已预扣 10 份，但数据库还没建单，Redis 可用资格是 90，数据库可用库存仍是 100。这不是直接需要修成相等的脏数据。

如果这时删 Redis 库存并用数据库的 100 重建，就可能重复发放这 10 份资格。不能把普通商家缓存的删除/回源方案照搬到预扣库存。

在一致的核对时点，且成功结果、释放结果已完成同步时，可用下面的关系辅助理解：

```text
数据库可用库存 = Redis 可发放资格 + 尚未转成订单的有效预扣
```

这不是运行中任意两次读取都成立的断言。实际对账还要识别已建单但 Redis 状态未更新、数据库已释放但 Redis 尚未回补、补偿执行结果未知等在途状态，不能单凭计数差自动加库存。

## 4. 可以直接讲的面试回答

### 当前已实现版本

“目前运行版本的库存和订单由 MySQL 事务管理，Redis 做限流、售罄提示和商家缓存。扣库存和建单同事务提交，取消和到期由订单状态条件控制，只释放一次。Redis 数值库存预扣还在升级设计中，不能把售罄提示失效说成库存补偿。”

### 目标方案完成后

“我把一致性分成两层。数据库内部，扣库存、建单和请求结果放在一个事务；跨 Redis 和 MySQL，不追求每时每刻数值相等，而是按同一个请求追踪预扣、受理、建单和释放。Redis 先过滤请求，获得资格后才保存数据库请求与 Outbox，后台通过 Kafka 建单。遇到超时先核对数据库结果，不能直接回补；只有持久关闭请求或取消订单后，才用带请求身份的幂等操作释放资格。异常恢复时暂停新资格发放，核对在途请求后再恢复。”

这段第二版是目标话术，不是目前完成状态。

## 5. 目标协议需要哪些记录

以下是设计要求，字段与具体表结构仍需实现评审。

| 记录 | 主要作用 |
|---|---|
| Redis 预扣记录 | 保存 requestId、用户、活动、活动代次、预扣状态与期限；同键重放不再扣减 |
| Redis 用户资格映射 | 用户与活动关联到实际请求，避免仅用一个布尔标记无法查询原请求 |
| 可扫描的预扣索引 | 使后台能找到预扣后应用退出、尚未持久受理的请求，不能只等用户重试 |
| MySQL 请求记录 | 保存请求参数摘要与不可逆终态，区分已受理、拒绝、过期、已建单 |
| MySQL Outbox | 与请求同事务记录建单事件；业务结果需要 Redis 同步时，也要有持久任务 |
| 补偿身份与代次 | 让释放操作只作用于对应预扣一次，阻止旧任务修改重建后的库存 |

预扣记录与扫描索引必须和扣减在同一受控 Lua 操作中维护。脚本短小且写入前检查必要参数和键类型，不把 Lua 当作支持任意错误回滚的数据库事务。

只有请求与 Outbox 已提交，才返回“持久受理”。Redis 预扣完成不表示订单成功，单独预扣也不是数据库级持久受理。

## 6. 关键失败窗口怎么解释

### 6.1 预扣后、MySQL 写入前退出

Outbox 尚不存在，所以它不能修复这个窗口。后台根据预扣索引发现悬挂请求；按原请求身份重试受理，或在超过期限后持久关闭，再安排释放资格。

重点：不能查一次“数据库没有订单”就释放。原线程可能只是慢，还会继续提交。

必须让“受理”和“关闭”竞争同一个请求唯一身份。关闭若先成功，留下不可逆终态，后来的受理/消费者不能继续建单；受理若先成功，关闭者必须检查并按同一请求状态机处理。当前代码并没有完整实现这种预受理关闭协议，不能只加一个定时 INCR 就说完成。

### 6.2 数据库受理成功，HTTP 响应丢失

客户端用原请求键查询/重试，返回数据库已有请求；不重新预扣。不能因为 Redis 的本地显示还未更新，就重新分配资格。

### 6.3 请求和 Outbox 已提交，Kafka 尚未发送

后台继续发送持久消息。程序重启仍有记录可重试。Kafka 发成功、Outbox 标记前退出可能重投，因此消费端必须按数据库请求终态去重。

### 6.4 建单事务失败或结果未知

库存扣减与订单插入同事务，失败整体回滚。瞬时故障进入有界速率重试/积压保护，不立即退预扣。连接断开导致提交结果未知时先查询实际结果，不能认定失败。

超过业务处理期限后，先把请求持久转入终态，并使迟到消费者无法建单，再生成释放任务。数据库无法确认结果时，宁可临时少放资格，也不盲目补库存。

### 6.5 订单已提交，Kafka 位点尚未提交

重投后查询请求终态，不再扣库存或建单；业务事务提交后才确认消费。幂等生产者不能代替 MySQL 业务幂等。

### 6.6 取消或到期

MySQL 中只有 PENDING_CONFIRM 能转换。订单状态与数据库库存释放同事务；重复取消看到终态直接返回。目标预扣版还要同事务写出 Redis 释放任务。

Lua 检查请求身份、活动代次及预扣状态，未释放才加回资格并标记已释放。释放成功但任务确认丢失时，重试不再加库存。

本项目规则是每用户每场最多创建一张订单，取消/过期后不能再次购买同场。因此释放库存给其他用户，不意味着删除本人的“已购买”身份。建单前失败是否允许新意图重新申请，要与已建单后关闭区分并明确实现。

### 6.7 Redis 不可用或丢失部分数据

新抢购保守拒绝，不能全量回源压垮数据库。已持久受理的请求仍以数据库为准，最终订单通过事务约束兜底。

恢复不能直接把数据库 remaining 写回 Redis 然后放开：要暂停该活动新预扣，隔离旧在途写入，基于一致核对点处理生效订单、已受理未建单请求和可恢复预扣，切换活动代次后才开放。旧补偿必须拒绝写入新代次，不能将重建已包含的释放再加一遍。

只存在 Redis 且已经丢失的预扣记录无法凭空还原，不能承诺每个这类请求都可恢复。未返回持久受理的请求按未知结果/重试契约处理；已返回持久受理的请求必须能在数据库中查到。恢复时的冻结、代次校验与旧写入隔离是一整套待实现协议，不是仅加一个 version 字段。

## 7. 常见追问

**有 Redis，为什么数据库还要防超卖？**

Redis 主要筛选资格、保护数据库；数据库条件扣减和唯一约束保证最终记录不会因为重复消息或 Redis 状态异常而突破业务规则。两层职责不同。

**加了 Outbox，是否就没有 Redis/MySQL 双写问题？**

没有。它解决 MySQL 请求记录与待发送消息的一起提交；Redis 预扣到持久受理之间仍需要恢复协议。

**是不是每个请求还是要写数据库？**

目标是无资格请求在 Redis 返回，获得资格者才进入受理事务。但实际还必须优化当前会话查库、入口幂等查库及积压检查，实验要统计整条 HTTP 路径，而不是只数某一个业务方法的 SQL。

**为什么不每次定时把 Redis 库存改成数据库库存？**

数据库库存包含尚未落单的预扣份额，直接覆盖会重复发放；还可能与取消、建单、补偿并发。要按请求核对，而不是定时覆盖一个数字。

**开 AOF 就能绝对不丢吗？**

不能。持久化策略影响损失窗口，Redis 配置、故障方式和复制切换都要说明；持久化也不会自动解决两个系统之间的原子提交。

**Cache-Aside、延迟双删能用在这里吗？**

商家介绍副本可以采用缓存失效策略；预扣库存是有业务含义的可变状态，不能套用“删除后读数据库重建”来绕过在途资格。

## 8. 必须完成的实验，不预写结果

1. 预扣后、持久受理前退出；后台找回请求，或先关闭再补偿。
2. 预扣补偿与迟到受理竞争；必须只存在一种最终结果。
3. 受理提交后响应丢失；同键重试不重复预扣与建单。
4. Kafka 发送确认后退出、数据库建单提交后退出；允许重复消息，不允许重复业务效果。
5. 重复释放、释放响应丢失、取消与到期竞争；库存最多回补一次。
6. Redis 丢失/重建后旧事件到达；代次隔离和核对过程不能多放资格。
7. Redis/MySQL/Kafka 暂停与恢复；分别验证新请求拒绝、已有请求恢复和积压保护。
8. 少库存突发与足库存持续负载，分别测入口 RPS、数据库访问、成功订单 TPS 和端到端延迟。

当前已有 B0–B6 测试支持数据库订单状态机与可靠投递，不等于以上新增跨存储预扣协议已验收。

## 9. 技术依据

- [Redis Lua 官方说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)：Redis 内脚本原子执行及显式键传参规则，不包含外部数据库或 Kafka。

- [Kafka 官方设计文档](https://kafka.apache.org/41/design/design/)：投递/处理语义和外部存储协调边界；业务效果仍需应用及数据库配合。

上面是本项目的设计推导，官方资料并不意味着已经替本项目完成实现或测试。
