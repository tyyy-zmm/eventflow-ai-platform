# MySQL 预约交易一致性

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 设计思路

限量预约的核心不是“把库存减一”，而是在创建、取消、过期和候补补位并发发生时，仍然保证名额守恒、有效预约唯一和请求重试幂等。该模块以 MySQL 作为库存唯一真相，通过场次行短事务串行化同一场次的状态变化，并把条件扣减、状态机、有效预约身份、幂等结果和 Outbox 放进同一事务。

## 简历上的亮点

**预约交易治理：** 基于 MySQL 短事务、条件扣减与请求幂等实现预约状态机；1000 用户竞争 100 个名额，最终无超卖和重复扣减。

## 话术/逐字稿

### a. 背景阐述

#### 这条简历讲了什么

它讲的不是“用了事务和锁”，而是如何在限量名额业务中维持三个不变量：

1. `available >= 0`，不能超卖；
2. `available + 有效预约占用量 = capacity`，名额不能凭空增加或丢失；
3. 同一用户、同一场次最多存在一份有效预约，但取消后允许新意图重新预约。

预约具有 `HELD`、`CONFIRMED`、`CANCELLED`、`EXPIRED` 四种状态。`HELD/CONFIRMED` 占用名额，`CANCELLED/EXPIRED` 释放名额。确认、取消、过期扫描和候补补位都可能并发修改同一个场次，因此必须统一进入同一套事务和锁顺序。

### b. 问题剖析

#### 为什么不用 Redis 预扣库存

Redis 预扣后仍需写 MySQL，会产生“Redis 成功、MySQL 失败”或反向双写窗口，需要补偿、对账和过期处理。项目目标先保证正确性，因此 MySQL 是唯一库存真相，Redis 只负责限流和目录读取。

#### 为什么使用场次行短事务

复杂性不只在 `available >= quantity`，还包括候补优先、有效预约身份、状态转换、请求幂等和 Outbox。以场次容量行为串行化点，可以让所有同场次变更遵循统一锁序，牺牲热点场次的极限并发，换取更容易验证的业务不变量。

#### 为什么不能只给预约历史表加唯一索引

如果直接对全部历史记录建立 `(user_id, session_id)` 唯一索引，用户取消后也不能重新预约。项目单独维护有效预约身份，只在 `HELD/CONFIRMED` 生命周期内占据唯一身份，进入终态时同事务释放。

### c. 方案构思与实现

创建预约：

1. 从登录会话取得用户身份，不信任请求体中的 userId；
2. 校验 `requestKey`、场次、人数和发布状态；
3. 锁定场次容量行，检查候补优先规则；
4. 以 `available >= quantity` 为条件扣减名额；
5. 写预约记录和有效预约身份；
6. 写请求幂等结果与 `ReservationHeld` Outbox；
7. 同一事务提交后返回。

取消/过期同样重新锁定场次和预约，只有当前状态允许转换时才释放名额。重复取消只返回当前结果，不再次增加库存。

幂等键按“用户 + 操作作用域 + requestKey”生效。同键同参数返回同一预约的当前状态，同键不同参数返回冲突；用户产生新业务意图必须换新键。这样能处理事务已经提交、HTTP 响应却丢失的窗口。

### d. 实验结果

#### 1000 用户竞争

- 真实 MySQL；
- 两个 `BookingService` 对象、独立数据库连接；
- 16 个执行线程；
- 1000 个不同用户和请求键；
- 每次预约人数按 1-7 循环；
- 共同争抢 100 个名额。

结果：27 组成功，其余 973 次只允许返回售罄；成功人数之和严格等于 100，`available=0`，有效预约身份数、请求记录和 Held 事件数一致，没有超卖或重复有效预约。

#### 响应丢失

在预约事务提交后、响应返回前注入 `halt(137)`。另一进程使用相同请求键重试，返回同一预约，名额只扣一次。这证明的是“提交后响应丢失可重放”，不是所有进程崩溃都自动恢复。

#### 锁超时和连接池耗尽

真实持锁制造 MySQL 1205，验证预约、请求记录和事件均不落库；释放锁后由调用方使用原键重试成功。连接池上限 2、等待 250ms 时，池耗尽返回可重试错误且不产生半订单。

### e. 复盘总结

这个方案优先保证正确性和可验证性。它没有把 Redis 包装成库存真相，也没有声称单机场景等同于生产高并发。代价是同一热点场次最终会竞争一行数据库锁，因此后续若要继续扩展，需要围绕分片、排队削峰或库存分段展开，而不能简单增加应用实例。

## 面试话术完整版

### 1. 先讲业务背景，不要一上来背技术名词

> 我做的不是一个单纯的库存扣减接口，而是一套活动预约状态机。用户申请以后先进入 `HELD`，在截止时间前可以确认成 `CONFIRMED`，也可以主动取消；没有确认的预约会被系统扫描为 `EXPIRED`。取消和过期都会释放名额，释放后还可能触发候补补位。所以创建、取消、过期、确认和补位都会并发操作同一个场次，不能各写一套互不相关的逻辑。

这里建议先把面试官带到真实问题上：库存不是只有“减”，还会被多个入口“加回来”；请求也可能因为响应丢失而重复执行。后面的事务、锁和幂等才有存在的理由。

### 2. 接着说明任务目标

> 我先把正确性要求定义成几个不变量。第一，余量不能小于零；第二，余量加上 `HELD/CONFIRMED` 占用的人数必须等于总容量；第三，同一用户同一场次最多存在一份有效预约；第四，同一次请求重试不能重复扣量，但用户取消以后要允许发起新的预约意图；第五，预约、库存、有效身份、幂等结果和后续事件必须一起提交或一起回滚。

这一段的意义是说明你不是“看到 Redis、MySQL 就往上堆”，而是从业务约束倒推实现。

### 3. 完整方案怎么说

> 实现上我让 MySQL 成为库存的唯一真相。所有会改变名额的入口都先按统一顺序锁定场次容量行，再在一个短事务里完成业务变化。创建预约时，事务会检查请求幂等记录、锁定场次、校验候补优先规则和有效身份、执行 `available >= quantity` 的条件扣减，然后写入 `HELD` 预约、有效预约身份、请求结果和 `ReservationHeld` Outbox。事务中不访问 Redis、Kafka 或模型，避免持锁期间等待外部网络。

> 取消和过期也走同一套场次锁。只有预约当前状态仍允许转换时才释放名额并写 `CapacityReleased` Outbox；如果请求重复到达，看到预约已经处于终态，就只返回当前结果，不再增加库存。

### 4. 为什么“行锁 + 条件扣减”都需要

> 行锁负责让同一场次的状态变化串行进入临界区，条件扣减负责在 SQL 层表达库存谓词。更新语句带 `available >= quantity`，影响行数为零就说明余量不足。保留两层是为了让业务判断和数据库写入都不允许负库存，但我不会说一条 SQL 就解决了整个交易问题，因为有效身份、状态转换和事件仍然需要同一事务维护。

### 5. 幂等与一人一单要分开讲

> 请求幂等解决的是同一次业务意图的网络重试，作用域是用户、场次、操作和 requestKey。同键同参数返回原预约，同键不同参数返回冲突。业务唯一解决的是同一个用户即使换了 requestKey，也不能同时持有两份有效预约。

> 我没有直接在预约历史表上给 `(user_id, session_id)` 加永久唯一索引，因为用户取消后还要允许重新预约。项目单独维护 `ef_active_booking`，只有 `HELD/CONFIRMED` 才占据有效身份，进入 `CANCELLED/EXPIRED` 时在同一个事务里释放。这样历史可以保留，业务唯一性也成立。

### 6. 提交成功但响应丢了怎么办

> 最危险的窗口之一是数据库已经提交，但服务在返回 HTTP 响应前退出。客户端不知道结果，如果换新 requestKey 再发，就可能被当成新意图。因此客户端必须复用原 requestKey。服务端查询到原请求记录后，返回同一预约的当前状态，不再次扣量。即使那份预约后来已经取消，也返回它的 `CANCELLED` 状态；真正重新预约必须换新键。

### 7. 实验结果如何完整表达

> 我使用真实 MySQL，创建两个独立的 `BookingService` 和数据库连接，用 16 个线程模拟 1000 个不同用户。每次预约人数按 1 到 7 循环，共同竞争一个容量为 100 的场次。最终 27 组成功，成功人数之和严格为 100，数据库余量为 0，其余请求只能得到售罄；有效身份、请求记录和 Held 事件数也与成功预约一致。

> 我还在事务提交后、响应返回前注入 `halt(137)`，另一进程用相同 requestKey 重试，返回同一预约且库存只扣一次。另外真实持有场次行锁制造 MySQL 1205，以及把连接池限制为 2 制造获取连接超时，失败时预约、身份、请求记录和 Outbox 都不会留下半状态。

### 8. 面试中一定要主动说明的边界

> 这组 1000 用户实验是竞争正确性实验，不是 1000 QPS。它证明当前事务和约束在这组并发调度下没有超卖，不代表单个热点场次可以无限横向扩展。场次行是明确的串行点，Redis 活动级准入只能减少无效竞争，不能消除数据库写上限。

## 实现细节拆解

### 创建预约事务

1. 从登录会话取得用户身份，拒绝信任请求体中的 userId；
2. 校验 requestKey、人数、发布状态和场次时间；
3. 查询幂等记录，同键已有结果时校验参数摘要；
4. 锁定场次容量行；
5. 检查实时余量、候补优先和有效身份；
6. 执行带余量条件的扣减；
7. 插入 `HELD` 预约和确认截止时间；
8. 插入有效预约身份；
9. 写入请求结果和 `ReservationHeld` Outbox；
10. 提交事务后才返回。

### 取消和过期事务

1. 先锁场次，再锁预约，保持所有入口锁顺序一致；
2. 校验当前状态是否允许转换；
3. 只有本事务成功把有效状态改为终态时才释放人数；
4. 删除有效预约身份；
5. 写 `CapacityReleased` Outbox；
6. 重复请求看到终态时直接返回，不重复释放。

### 为什么统一锁顺序

如果普通预约先锁预约表、候补补位先锁候补表，最后都来锁场次行，就容易形成循环等待。项目把场次作为同一名额池的串行化入口，再处理预约、候补、身份和事件。统一锁序不能保证数据库永远不出现死锁，但能够避免业务代码主动制造明显锁环。

## 反方案比较

### Redis 预扣库存

优点是可以把大量竞争挡在内存层；缺点是形成 Redis 和 MySQL 两个状态源，需要处理 Redis 成功、MySQL 失败及反向窗口，还要补偿、对账和过期回收。当前项目优先正确性，所以 Redis 只做准入。

### 单纯乐观锁

版本号适合冲突较少的更新，但热点场次下会出现大量失败重试。本项目一次事务还要协调候补优先、多人数量、有效身份和 Outbox，整链路重试会放大数据库压力，因此选择场次行短事务。

### 只使用唯一索引

唯一索引可以阻止重复行，却不能表达“只有有效状态唯一、历史终态允许保留”。有效身份表把生命周期内唯一性显式化，更符合取消后重新预约的业务。

## 进一步追问

### requestKey 应该保存多久

> 至少覆盖客户端可能重试和业务结果查询的窗口，不能事务刚完成就删除。清理应按 `retain_until` 异步执行；在记录过期前，同键必须稳定指向原业务结果。

### 如果数据库死锁怎么办

> 统一锁序和短事务减少死锁，但不能承诺绝对没有。数据库返回死锁或锁超时后，事务整体回滚，接口返回可重试错误。调用方仍使用原 requestKey 重试，不能在异常分支生成新键。

### 如何对账

> 核心对账式是 `available + HELD/CONFIRMED 的 quantity 总和 = capacity`。还要检查有效身份必须指向有效状态、同一用户同场次不能同时拥有有效预约和有效候补、MATCHED 候补关联的预约人数和用户必须一致。发现异常先告警和隔离，不能直接猜测性修改库存。

### MySQL 故障为什么不降级到 Redis 创建预约

> 因为 Redis 不是交易权威。故障期间写入 Redis 会让恢复后的合并语义不确定。项目选择新预约返回可重试 503，数据库恢复后复用原 requestKey；查询类功能可以按陈旧容忍度降级，但不能伪造交易成功。

## 常见面试题

### 有行锁为什么还要条件扣减

行锁负责串行化，条件扣减表达库存谓词，并防止实现变化或遗漏检查时直接写成负数。但它不是“锁 + SQL 就绝对安全”，所有交易入口仍必须遵循同一锁序和事务边界。

### 为什么不是乐观锁

单纯预约可以使用版本号，但本项目还要协调候补优先、多人名额、有效身份和状态事件。热点下乐观重试会放大负载，初版使用场次行短事务更容易解释和验证。它的缺点是热点场次行成为瓶颈，不能宣称无限横向扩展。

### 事务提交了但客户端超时怎么办

客户端必须复用原 requestKey 查询或重试。服务端返回同一预约的当前状态，不能自动生成新键，否则无法区分重试和新意图。

### 数据库挂了怎么办

返回可重试 503，不在数据库状态未知时改用 Redis 创建预约。真实 MySQL 停机实验中，恢复后同一应用、同一请求键能返回既有预约。

## 一分钟逐字稿

> 我先定义名额守恒和有效预约唯一性，再让预约、取消、过期和补位统一锁定场次容量行。事务里完成条件扣减、预约状态、有效身份、幂等结果和 Outbox，事务外不访问 Redis、Kafka 或模型。真实 MySQL 下用 16 线程让 1000 个用户以 1-7 人组争抢 100 个名额，最终只成功 27 组但人数总和严格为 100；另外在提交后注入进程退出，另一进程用原键重试仍返回同一预约且不重复扣量。这个方案偏正确性，热点场次吞吐是我明确承认的边界。
