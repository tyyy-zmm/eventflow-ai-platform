# Redis 热点缓存与准入治理

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 设计思路

Redis 在项目中只承担“减少可容忍短暂陈旧数据的数据库回源”和“限制预约入口的写入突发”两类职责，不参与最终库存裁决。缓存侧使用 Cache-Aside、随机 TTL、负缓存和带 owner token 的回填锁治理穿透、集中失效与击穿；准入侧使用 Lua 原子执行用户级和活动级限流，在流量进入 MySQL 热点行锁前完成削峰。

## 简历上的亮点

**热点缓存优化：** 采用 Cache-Aside、随机 TTL、回填锁与用户/活动级 Lua 准入治理缓存击穿和写入突发；热点 100 RPS 下目录 SQL 回源减少约 78%。

## 话术/逐字稿

### a. 背景阐述

#### 业务问题

Redis 在项目中承担两类职责：

- 加速允许短暂陈旧的活动目录详情；
- 在预约入口过载时保护数据库。

它不裁决库存，也不决定预约是否成功。实时余量和最终交易仍进入 MySQL。

### b. 问题剖析与缓存方案

目录采用同步 Cache-Aside：命中时解码返回；未命中时竞争带 owner token 的回填锁，锁持有者查询数据库并写入带随机抖动 TTL 的缓存，其他请求有界等待或返回可重试错误。不存在的数据写短 TTL 负缓存，防止穿透。

目录修改时，在 MySQL 事务中递增 revision、写元数据和缓存失效任务。事务提交后执行 Lua 删除缓存及旧回填锁；generation 防止旧 worker 确认删除后来生成的新版失效任务。回填前后校验 owner 和剩余租约，避免失去锁的旧线程覆盖新值。

这仍然是最终一致，不承诺瞬时强一致。正式详情接口还会访问数据库检查发布状态；库存等硬时效数据走实时接口。

### c. 活动级准入方案

Lua 分别执行三层固定窗口：

- 每用户每场次 5 次/10 秒；
- 每用户每接口 60 次/分钟。
- 每活动默认 200 次/秒，用于限制大量不同用户同时竞争一条 MySQL 场次行锁。

拒绝时通过 PTTL 计算 `Retry-After`。三个窗口不是一次联合扣费，前层通过后仍可能被后层拒绝；这属于准入计数的保守消耗，不影响库存正确性。Redis 故障时，新预约入口返回 503，避免无保护流量冲击数据库；已存在预约的确认和取消不依赖新的准入额度。

固定窗口在边界处允许突发，不是令牌桶，也不保证严格公平；限流更不是鉴权。

### d. 实验结果

#### 真实接口目录矩阵

缓存矩阵使用 1 万条固定种子的合成目录，比较关闭 Redis 和开启 Redis 的两个 Java 进程。覆盖热点 80/20、均匀分布，以及 10/100/300 RPS，每组交替运行三轮并校验返回内容。

热点 100 RPS 的短窗口三轮合计：

- 基线目录读取：2400；
- Redis 目录读取：529；
- 回源减少约 `(2400-529)/2400 = 77.96%`。

180 秒热点 100 RPS：基线 17,988 次目录读取；Redis 模式 3,492 次读取、14,508 次命中。

但 Redis 模式成功 P95 没有改善：长窗口基线 4.49ms，Redis 5.67ms。原因是本机 Redis 往返、解码和每次仍存在的鉴权/发布状态查询抵消了目录 SQL 减少。因此该矩阵只证明“减少目录回源”，不能证明正式详情接口延迟提升。

#### 热目录 QPS 饱和实验

为了单独测量缓存层而不混入鉴权和发布状态 SQL，增加默认关闭、只由本地实验进程启用的 `/benchmark/sessions/{id}`。它复用同一个 `CatalogService`，但不执行外围查询。实验采用一个预热热点，开环调度，正确响应率、实际目标达成、P95、调度延迟和客户端丢弃门槛均在运行前冻结。

正式复验覆盖 1000/1500/3000 QPS，每档 6 秒、三轮、窗口前冷却 3 秒并交替顺序。某档位必须三轮全部满足：正确率≥99%、实际正确 QPS≥目标95%、P95≤100ms、调度P99≤100ms、零客户端丢弃且错误只允许503。

- MySQL 直读三轮全通过的最大测试档位为 1000 QPS，实际正确吞吐中位数 996.15 QPS；1500 QPS 有一轮正确率 98.97%，不接受该档。
- Redis 在 3000 QPS 三轮均 100% 内容正确，实际吞吐中位数 2998.02 QPS，最差 P95 18.18ms，零丢弃、零目录 SQL 回源。

结论只能说“本机受控热目录链路的可持续测试档位由 1000 提升至 3000 QPS”。3000 是最高正式测试档，不是绝对极限；该结果不代表带鉴权、发布检查和交易写入的整个系统 QPS。

#### 活动级准入与缓存过期实验

- 200 个不同用户同时预约同一场次时，关闭 Redis 准入后 200 个请求均进入数据库，成功 P95 为 1148.6ms；设置活动窗口 20 次/秒后，20 个请求进入数据库、180 个返回带重试时间的 429，名额守恒保持成立。该实验使用真实 `AdmissionGate` 和 `BookingService`，但默认关闭的 benchmark 入口排除了鉴权 SQL。
- 正式鉴权详情接口以 50 RPS 连续运行 70 秒，共 3500 次请求并跨过一次 55~65 秒随机 TTL：3500 次均为 200，目录 SQL 回源 1 次、缓存命中 3499 次，P95/P99 为 6.9/8.6ms。它证明有界等待能覆盖本机单热点回填窗口，不代表多节点生产 SLO。

### e. 复盘总结

该模块真正解决的是目录热点回源和写入口过载保护，而不是用 Redis 替代数据库事务。正式接口实验可以支撑“目录 SQL 回源减少约 78%”，不能写成“总 SQL 减少 78%”或“接口延迟下降 78%”。3000 QPS 是隔离目录读取链路后的本机稳定测试档位，也不能外推为完整预约系统吞吐。

## 面试话术完整版

### 1. 先把 Redis 的两项职责分开

> Redis 在项目里做两件互相独立的事。第一是缓存活动标题、描述、区域和价格等允许短暂陈旧的目录数据，减少热点详情的重复 SQL；第二是在预约请求进入 MySQL 之前做用户级和活动级准入，限制单用户滥用以及大量不同用户同时竞争同一条场次行锁。Redis 不保存最终库存，也不决定预约是否成功。

如果一上来只说“解决缓存三大问题”，很像八股。先说明目录读热点和交易写突发两个真实场景，再引出对应机制。

### 2. 目录缓存的完整故事

> 目录采用同步 Cache-Aside。命中时反序列化返回；未命中时，请求竞争带 owner token 的回填锁。获锁者查询数据库并写入 55 到 65 秒随机 TTL 的正缓存，不存在的数据写 5 秒负缓存；其他请求有界等待缓存出现，超时则返回可重试错误，而不是全部穿透数据库。

> owner token 是为了防止旧锁持有者误删新锁。比如线程 A 的锁过期以后，线程 B 获得了新锁，如果 A 直接 `DEL`，会把 B 的锁删掉。因此解锁和回填都通过 Lua 校验 owner；回填前还检查剩余租约，避免失去锁的旧线程覆盖新值。

### 3. 随机 TTL、负缓存和回填锁分别解决什么

> 负缓存解决不存在 ID 被反复查询造成的穿透；随机 TTL 降低一批 Key 在同一时刻集中失效的雪崩风险；回填锁解决单个热点 Key 到期时大量请求同时查数据库的击穿。这三个机制解决的问题不同，随机 TTL 不能代替击穿治理，回填锁也不能代替负缓存。

### 4. 数据修改后的缓存一致性

> 目录修改时先在 MySQL 事务里更新数据、递增 `catalog_revision` 并写失效任务。事务提交后由 worker 用 Lua 删除缓存和旧回填锁。失效任务带 generation，旧 worker 不能把后来生成的新任务误确认；回填请求也校验 owner 和 revision，避免拿着旧 snapshot 的线程在删除之后重新覆盖新缓存。

> 这仍然是最终一致，不是强一致。目录允许短暂旧读；库存、预约资格和发布状态在正式业务链路中重新检查，不能拿目录缓存裁决交易。

### 5. 为什么还要活动级准入

> 用户级限流只能防止一个用户重复刷，无法处理 200 个不同用户同时抢同一场次。MySQL 交易最终都会竞争该场次容量行，因此我增加活动级窗口，在请求进入数据库之前限制单活动的写入速率。它不是库存扣减，只是一层背压。

> Lua 原子完成计数、首次设置过期时间和返回 PTTL。当前有每用户每场次 5 次/10 秒、每用户每接口 60 次/分钟、每活动默认 200 次/秒三层窗口。拒绝时返回 429 和 `Retry-After`，让客户端抖动重试。

### 6. 正式接口实验怎么讲

> 我准备了 1 万条固定种子的合成目录，用 Redis 关闭和开启的两个 Java 进程做对照，覆盖热点 80/20、均匀分布和 10/100/300 RPS，每组交替运行三轮，并逐字段校验每个 200 响应。

> 热点 100 RPS 的三轮短窗口里，MySQL 直读模式发生 2400 次目录读取，Redis 模式为 529 次，目录 SQL 回源减少约 77.96%。但正式接口 P95 并没有改善，长窗口基线为 4.49ms，Redis 为 5.67ms，因为本机 Redis 往返、解码和仍然存在的鉴权及发布状态 SQL 抵消了目录查询节省。因此简历只写目录 SQL 减少约 78%，不写延迟提升。

### 7. 为什么还有 3000 QPS 的实验

> 正式详情接口每次仍会查询鉴权和发布状态，无法隔离目录缓存本身的容量贡献，所以我增加了一个默认关闭、只在本地实验启用的 benchmark 入口。它复用同一个 `CatalogService`，但排除外围 SQL。

> 正式复验对 1000、1500、3000 QPS 各跑三轮，提前冻结内容正确率、实际吞吐、P95、调度延迟和零丢弃标准。MySQL 直读三轮全通过的最高档位是 1000 QPS；Redis 在 3000 QPS 三轮内容正确率均为 100%，实际正确吞吐中位数 2998.02 QPS，最差 P95 18.18ms。这个结果只属于本机受控热目录链路，不是完整系统 QPS。

### 8. 活动准入实验怎么讲

> 200 个不同用户同时预约同一场次时，关闭活动准入后 200 个请求都进入数据库，成功请求 P95 为 1148.6ms；把活动窗口设为每秒 20 后，只有 20 个请求进入数据库，180 个请求返回带重试时间的 429，名额守恒仍然成立。这个实验说明限流保护了数据库临界区，不是通过拒绝请求来虚构业务吞吐。

## 实现细节拆解

### Cache-Aside 读路径

1. 根据场次 ID 读取 Redis；
2. 命中正缓存则反序列化并返回；
3. 命中负缓存则返回不存在；
4. miss 后尝试取得带 owner token 的锁；
5. 获锁者查询 MySQL，并写正缓存或负缓存；
6. 未获锁者有界等待胜者回填；
7. 等待超出请求预算时返回可重试 503；
8. 解锁时使用 Lua 比较 owner 后删除。

### 目录更新和失效

1. MySQL 事务更新目录并增加 revision；
2. 同事务写缓存失效任务；
3. 提交后 worker 领取任务；
4. Lua 删除目标缓存和属于旧 owner 的回填锁；
5. generation 防止旧 worker 确认新一代任务；
6. 失败任务退避重试，最终依靠 TTL 兜底收敛。

### Lua 准入链路

1. 用户身份在鉴权后确定，不能信任请求体 userId；
2. 用户场次窗口防止同一用户重复点击；
3. 用户接口窗口限制账号级滥用；
4. 活动窗口限制不同用户同时冲击同一资源；
5. Lua 返回剩余 TTL，接口转换为 `Retry-After`；
6. 通过准入后仍必须进入 MySQL 事务检查真实名额。

### 三层窗口的一个诚实边界

当前三层是逐层执行，不是一次联合扣费。请求可能通过前层后被后层拒绝，前层计数不会回滚，因此准入会略保守。这不影响库存正确性，但不能声称计数完全公平。若合并为一个 Lua，又要考虑 Redis Cluster 跨 slot 和脚本复杂度。

## 反方案比较

### 逻辑过期

逻辑过期可以直接返回旧值并异步刷新，适合优先可用且允许陈旧的内容页。项目选择同步回填和有界失败，是为了不主动返回已知过期目录。两者没有绝对优劣，但库存无论如何都不能使用旧缓存。

### 本地 Caffeine + Redis 两级缓存

两级缓存可以减少 Redis 往返，但会引入每个应用实例独立失效、多节点广播和版本管理。当前项目没有观测到必须增加这一层的业务必要，因此没有为了简历继续堆技术。若线上 Redis 网络成为瓶颈，再基于 revision 增加本地缓存更合理。

### Redis 库存预扣

预扣可以提升热点写入能力，但会产生 Redis 与 MySQL 双写、补偿和对账问题。当前项目选择 Redis 只做准入，交易结果仍由 MySQL 决定。

## 进一步追问

### 为什么固定窗口而不是令牌桶

> 固定窗口实现简单、Lua 原子且容易返回重试时间，足够完成数据库保护目标。缺点是窗口边界可能出现双倍突发，也不保证严格公平。如果生产要求平滑速率，会改成令牌桶或滑动窗口。

### Redis 故障为什么不全部放行

> 预约准入是数据库保护层，故障时放行会把 Redis 故障扩散到 MySQL。项目对新预约失败关闭，但确认和取消已有预约仍走数据库，避免用户无法释放资源。这个策略是可用性与保护性的明确取舍。

### 78% 为什么不是总 SQL

> 计数器统计的是 `CatalogService` 完成的目录加载，正式接口仍可能执行鉴权和发布状态查询。所以只能写目录 SQL 回源减少约 78%，不能写整个数据库压力降低 78%。

### 为什么一次 5000 QPS 通过却不写

> 探索测试中短暂跑到过 5000，但连续高压后出现低档延迟异常，说明负载器和机器存在残留影响。我加入固定冷却并重新跑三轮，最后只采用稳定通过的 3000 档，避免挑最好看的一次结果。

### 回填锁过期是不是仍会重复查库

> 会。租约过期后 successor 可以获得锁，旧线程可能已经完成数据库查询，因此短时间存在重复读取。owner 和 revision 保护的是不误删新锁、不让旧值覆盖新值，而不是承诺全局永远只有一次 SQL。

## 常见面试题

### 为什么不用逻辑过期

逻辑过期允许主动返回旧值，更适合可接受陈旧的内容页。但本项目还要明确处理发布状态和目录修改，最终选择同步回填和有界失败，边界更清楚。无论哪种方案都不能拿旧缓存裁决库存。

### 回填锁过期怎么办

租约过期后可能出现重复查询，这是可接受的降级；owner token 和条件解锁避免旧线程删除新锁，回填时再次核验 owner/revision，避免旧结果覆盖新版本。它减少击穿，不保证全局永远只有一次查询。

### Redis 挂了为什么不放行

预约入口的限流是数据库保护层。如果 Redis 故障时全部放行，故障会扩散到 MySQL。项目选择新申请保守失败，但确认/取消已有预约继续走数据库，避免用户无法释放资源。

### 78% 是总 SQL 降低吗

不是。它只表示目录详情 SQL 的计数变化，每次请求仍可能执行鉴权和发布状态查询，不能包装成整个数据库负载降低 78%。

### 为什么 QPS 实验不用正式详情接口

正式接口每次都查鉴权和发布状态，命中 Redis 后也会访问 MySQL，无法隔离目录缓存的容量贡献。benchmark 入口只在实验参数开启时注册，默认关闭，并复用同一目录服务。这样测得的是目录读取链路，不是绕过安全后的生产接口成绩。

### 为什么只写 3000，不写探索时跑到的 5000

一次 5000 QPS 短测通过，但连续高压后出现低档延迟异常，说明负载器和机器存在残留影响。加入固定冷却后重新做三轮正式测试，最高冻结档位选择 3000；简历只采用三轮稳定数据。

## 一分钟逐字稿

> Redis 只负责可缓存目录和入口保护，不做库存真相。目录使用 Cache-Aside、随机 TTL、负缓存和 owner 回填锁，竞争请求有界等待胜者回填；预约入口以用户窗口防刷、活动窗口限制不同用户的写入突发。200 用户同时请求的本机实验中，活动窗口把进入数据库的请求从 200 限制到 20；MySQL 仍负责最终扣减和名额守恒。
