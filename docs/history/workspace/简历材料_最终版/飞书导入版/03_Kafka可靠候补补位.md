# Kafka 可靠候补补位

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 设计思路

取消或过期释放名额后，需要异步唤醒候补用户，但数据库提交和 Kafka 发送无法组成普通本地事务。该模块使用 Transactional Outbox 消除“业务已提交但事件未发送”的丢失窗口，使用发送租约支持故障接管和原事件重投，再由消费者 Inbox、同场次分区顺序和 MySQL 补位事务保证重复消息不会产生重复预约。

## 简历上的亮点

**候补可靠补位：** 基于 Kafka Outbox/Inbox、发送租约和事件重投实现 FIFO 补位；停机 120 秒并积压 1000 条消息后恢复，业务效果无重复。

## 话术/逐字稿

### a. 背景阐述

#### 为什么需要 Kafka

预约取消或过期会释放名额，候补用户需要被唤醒。直接在释放名额的数据库事务里同步补位，会拉长锁持有时间，并让 Kafka/下游故障影响主交易。项目将“释放名额”与“尝试补位”解耦，但必须处理数据库提交和消息发送之间的失败窗口。

### b. 问题剖析

取消/过期事务同时完成：

1. 更新预约状态；
2. 释放名额；
3. 写 CapacityReleased Outbox。

转发器用短事务领取发送租约，事务外发送 Kafka，收到 broker 确认后再标记 published。发送失败保留租约并退避，租约过期后使用原 `eventId` 重发。因此系统接受消息重复，不接受业务事件丢失。

不能说这是 Kafka exactly-once。它是数据库 Outbox + Kafka at-least-once + 消费端业务幂等。

### c. 方案构思与实现

消息按 `sessionId` 分区，使同一场次的释放事件有稳定顺序。消费者收到事件后，在同一个 MySQL 事务中：

1. 校验事件身份和 payload hash；
2. 登记 `(consumer, eventId)` Inbox；
3. 锁定场次并读取队首 WAITING 候补；
4. 队首人数足够时扣减名额并创建 HELD 预约；
5. 将候补置为 MATCHED，并记录固定预约 ID；
6. 提交事务后才确认 offset。

队首人数大于剩余名额时不跳过，避免小组插队。每个事件最多补一组，如果仍可能继续补位则生成后继检查事件；定时扫描只用于修复漏唤醒，不能拿扫描成功冒充消息从未丢失。

### d. 异常消息治理

非法 schema 进入失败事件表，只保存受限字段、原 topic/partition/offset 和摘要；相同 eventId 不同 payload 会被识别为身份冲突，不能当成普通重复。管理员可以按原 eventId 重放或明确忽略，并记录审计。发送成功只表示重放消息已发出，必须等真实消费者写入同摘要 Inbox 后，失败事件才能变为 RESOLVED。

### e. 实验结果

#### Broker 停机

- 停机 30 秒：原应用不重启，恢复后发送和消费继续，补位一次；
- 停机 120 秒并积压 1000 条合成持久唤醒：恢复核验约 63 秒，1000 个 eventId 全部进入 Inbox，各分区最终排空，业务补位仍只生效一次。

这 1000 条是消息 fixture，不是 1000 个客户订单。

#### 发送后进程退出

Kafka 已确认发送、Outbox 尚未标记 published 时注入 `halt(137)`。恢复后原 eventId 重发，attempts 从 1 变为 2，Inbox、补位和预约仍各一条。

#### 消费事务提交后退出

Inbox 和补位业务已提交、offset 尚未前进时退出。恢复后消息重投，Inbox 去重使业务不重复，随后 offset 正常推进。

### f. 复盘总结

这套链路追求的是“消息至少投递一次，业务效果只发生一次”，而不是 Kafka exactly-once。停机实验中的 1000 条是持久化唤醒消息 fixture，不是 1000 笔真实订单；单节点实验也不证明 Kafka 集群高可用。它能证明的是，在已覆盖的发送、消费和 broker 停机窗口中，系统允许重投但不会重复补位。

## 面试话术完整版

### 1. 从业务问题开始讲

> 活动预约取消或到期以后会释放名额，候补队列中的用户需要被唤醒。如果我在释放名额的事务里同步完成候补查询、创建预约和通知，不仅会拉长场次行锁持有时间，下游故障也会拖垮主交易。直接在事务提交以后发 Kafka 又有丢消息窗口：数据库已经释放名额，但进程还没来得及发消息就退出。

这段话先说明为什么要异步，也说明“直接发 Kafka”为什么不够。Kafka 的价值是解耦和削峰，但数据库与 Kafka 之间没有天然原子性。

### 2. 任务目标怎么说

> 我的目标不是做到消息绝不重复，而是做到业务事件不丢、重复消息不产生重复业务效果、同一场次尽量按稳定顺序处理，并且在生产者、消费者或 broker 故障后能够继续恢复。

这里要主动使用“at-least-once + 业务幂等”，不要使用 exactly-once。普通 MySQL 事务和 Kafka 事务不能直接组成一个跨系统原子事务。

### 3. Outbox 如何关闭发送前丢失窗口

> 当预约取消或过期时，事务同时更新预约状态、释放名额并写入 `CapacityReleased` Outbox。这样只要数据库提交，待发送事件就一定存在；如果事务回滚，库存和事件一起不存在。

> 独立转发器用短事务领取 Outbox 的发送租约，然后在事务外发送 Kafka。收到 broker 确认后，再把 Outbox 标记为 published。发送失败会记录错误并退避；租约到期后其他 worker 可以接管，并使用原 `eventId` 重发。

### 4. 为什么发送租约不能包着 Kafka 调用

> 如果领取任务以后一直持有数据库事务再等待 Kafka，发送延迟会占用连接和锁。项目只在短事务中写 owner、lease deadline 和 attempts，随后释放数据库资源，在事务外调用 broker。代价是发送成功到标记 published 之间可能崩溃，因此系统必须接受重复发送。

### 5. Inbox 如何吸收重复

> 消费端不能依赖“我应该只收到一次”。收到事件以后，会在同一个 MySQL 事务里登记 `(consumerName, eventId)` Inbox、锁定场次、读取 FIFO 队首、执行补位并创建预约。数据库提交以后才确认 offset。

> 如果事务提交后、offset 前移前进程退出，Kafka 会重投；第二次处理发现 Inbox 已经存在，就不再补位。为了防止上游错误复用 eventId，Inbox 还校验 payload hash：同一个 eventId、相同内容是重复，不同内容是身份冲突，不能静默跳过。

### 6. FIFO 补位如何实现

> 候补在同一场次内使用数据库 `sequence_no` 排序，Kafka 按 `sessionId` 分区，使同一场次的释放事件进入同一分区。消费者在事务中锁定场次并读取最早的 `WAITING` 候补。如果队首人数不超过当前余量，就扣减名额、创建新的 `HELD` 预约，并把候补改为 `MATCHED`；如果队首人数太大，则停止，不跳过它去匹配后面的小组。

> 每个事件最多补一组，避免一次消费持锁过久。如果补完以后仍可能继续匹配，就生成后继检查事件。定时扫描只做漏唤醒修复，不能把扫描最终成功当作 Kafka 消息从未丢失的证据。

### 7. 三个关键故障窗口

#### 数据库提交后、Kafka 发送前退出

Outbox 已存在，恢复后转发器继续发送，所以事件不会因为进程退出而永久丢失。

#### Kafka 已确认、Outbox 尚未标记 published 时退出

恢复后租约到期，原 eventId 会再次发送。消费者 Inbox 吸收重复，因此允许消息重复但业务不重复。

#### 消费事务已提交、offset 尚未确认时退出

恢复后 Kafka 重投。Inbox 已经和业务在同一事务提交，第二次处理不会重新创建预约，然后 offset 正常推进。

### 8. 故障实验完整话术

> 我首先做了真实 broker 停机实验。创建一个已占满的场次和一个候补用户，停止 Kafka 后取消原预约。数据库取消和名额释放仍能提交，Outbox 保持未发布，候补仍是 WAITING。恢复同一个 Kafka 后，原应用不重启，转发器重试发送，消费者完成一次补位。

> 在加强版实验里，Kafka 停机 120 秒，并积压 1000 条持久化合成唤醒消息。恢复后约 63 秒完成核验，1000 个 eventId 全部进入 Inbox，各分区最终排空，真实候补补位的业务效果仍只发生一次。这里 1000 条是消息 fixture，不是 1000 笔订单。

> 我还分别在 Kafka 确认发送后、Outbox 标记前注入进程退出，以及在消费事务提交后、offset 前移前退出。两种情况下恢复后都会重投，但 Inbox、候补和预约都只有一份业务结果。

## 实现细节拆解

### Outbox 记录至少包含什么

- 稳定 `event_id`；
- 事件类型和业务来源；
- `source_revision` 或等价业务修订；
- 发生时间；
- owner、lease deadline、attempts；
- `next_attempt_at` 和受限错误码；
- published 时间。

事件 ID 必须在首次写入时固定，重试不能每次生成新 ID，否则消费端无法把重发识别成同一事件。

### 转发器的处理步骤

1. 短事务领取到期且未发布的 Outbox；
2. 写入 owner、租约和尝试次数后提交；
3. 事务外发送 Kafka，并等待 broker 确认；
4. 成功后以 owner 和代次条件标记 published；
5. 失败时记录错误并设置退避时间；
6. worker 崩溃后由租约过期触发接管。

### 消费事务的处理步骤

1. 解析 schema，校验 eventId 和 payload hash；
2. 尝试登记 `(consumerName, eventId)` Inbox；
3. 重复且 hash 相同则幂等结束；
4. eventId 相同但 hash 不同则进入失败治理；
5. 锁定场次，读取 FIFO 队首；
6. 条件满足时扣减名额、创建 `HELD` 预约并更新候补；
7. 必要时写后继检查 Outbox；
8. 提交数据库事务后再确认 offset。

### 为什么按 sessionId 分区

分区键使用 `sessionId`，使同一场次事件落到同一分区并由一个消费者顺序处理；不同场次仍可以分区并行。Kafka 分区顺序只约束消息消费顺序，最终正确性仍依赖 MySQL 场次锁，因为普通预约、过期扫描等入口不一定都来自同一个 Kafka 分区。

### 异常消息如何闭环

非法 schema、缺字段或 eventId 冲突不能无限重试阻塞分区。项目将受限 payload、topic、partition、offset、摘要和失败原因写入失败事件表。管理员可以明确忽略或使用原 eventId 重放，并记录操作人和原因。

重放“发送成功”不等于业务恢复完成。只有真实消费者写入相同摘要的 Inbox 后，失败事件才能标记为 `RESOLVED`，避免控制台点了重放就提前宣布成功。

## 反方案比较

### 事务内同步补位

实现直观，但会延长取消或过期事务的场次锁时间，并把下游处理失败传导给主交易。候补数量和通知逻辑增加后，主链路延迟不可控。

### 数据库提交后直接发 Kafka

代码少，但数据库提交到发送之间存在进程退出窗口；反过来先发消息再提交数据库，会产生消息存在而业务回滚的幽灵事件。

### Kafka 事务

Kafka 事务适合协调 Kafka 内的 consume-transform-produce，不能自动把普通 MySQL 更新纳入同一个原子事务。这里选择 Outbox 明确接受重发，再由 Inbox 和业务状态保证效果幂等。

### 只依赖定时扫描

扫描可以最终发现余量与候补，但会带来延迟和重复数据库负载，也无法证明事件链路可靠。项目保留扫描作为 repair path，但主链路仍由 Outbox/Kafka 驱动。

## 进一步追问

### 为什么提交数据库后才 ack

> 如果先 ack，再提交业务事务，进程在两者之间退出会导致 Kafka 认为已完成，但补位没有落库，事件永久越过。先提交再 ack 最多产生重投，而重投可以由 Inbox 吸收。

### Inbox 为什么要带 consumerName

> 同一个事件可能被不同业务消费者各处理一次。如果只用 eventId 做全局主键，第一个消费者会错误阻止第二个消费者。所以幂等作用域是 `(consumerName, eventId)`。

### Kafka 停机期间主交易还能用吗

> 可以提交预约、取消和 Outbox，因为主交易不等待 Kafka 同步确认；但候补补位会延迟，不能说系统所有功能完全不受影响。恢复后转发器会继续处理积压。

### 同一分区就能保证严格 FIFO 吗

> 它保证该分区消息的消费顺序，但候补业务还受到普通预约、取消等数据库并发影响，所以最终仍以数据库 sequence_no、场次锁和状态条件为准。队首大组无法满足时明确不跳过，保持业务定义的 FIFO。

### 为什么每个释放事件只补一组

> 如果一个消费事务循环补很多组，会长时间持有场次锁，也可能让单条消息处理超时。每次只处理一组，把剩余工作转成后继事件，牺牲少量消息开销换取更短事务和更清晰的失败边界。

### 单 broker 实验能证明什么

> 只能证明本机持久卷、正常停止与恢复、Outbox 重试和 Inbox 幂等这些机制。它不覆盖多副本 leader 切换、磁盘损坏、跨机网络分区或生产高可用，因此简历不写“Kafka 高可用”。

## 常见面试题

### 为什么不用 Kafka 事务

Kafka 事务可以协调 Kafka 内的 consume-transform-produce，但不能直接把普通 MySQL 业务事务变成同一原子事务。Outbox 明确接受重复发送，用数据库 Inbox 约束业务效果，更适合本项目边界。

### 为什么提交后才 ack

如果先 ack 再提交数据库，进程崩溃会导致消息已经越过、业务却没完成。先提交数据库再 ack 最多造成重投，重投可由 Inbox 去重。

### Inbox 已有记录就能直接跳过吗

要同时校验 payload hash。相同 eventId 但内容不同是冲突，静默跳过会隐藏上游篡改或错误复用。

### 单节点 Kafka 能证明高可用吗

不能。实验验证的是本机持久卷、应用不重启情况下的停机恢复、重投和幂等，不覆盖多副本、跨机网络分区和生产 SLO。

## 一分钟逐字稿

> 我把名额释放和候补补位用 Kafka 解耦，但不依赖 Kafka 提供跨 MySQL 的 exactly-once。释放事务同写 Outbox，转发器通过租约和原 eventId 重投；消费者把 Inbox 去重、场次锁、FIFO 补位和预约创建放在同一 MySQL 事务，提交后才 ack。实验覆盖了 broker 停机 120 秒积压 1000 条消息、发送确认后进程退出以及消费提交后退出，恢复后允许消息重投，但 Inbox、候补和预约的业务效果都只出现一次。
