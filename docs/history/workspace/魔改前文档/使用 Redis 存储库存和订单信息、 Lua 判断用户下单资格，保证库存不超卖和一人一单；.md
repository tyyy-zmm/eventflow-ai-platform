## 1. 定位与范围

限量活动预约与候补平台，提供自然语言活动发现和多活动行程规划。业务链路：发现活动→查询详情→用户确认预约→确认/取消/过期→释放名额→候补补位。

不做真实支付、选座、跨库事务、微服务拆分、Redis预扣库存、开放式Agent群聊。主版本不要求ES或向量数据库，先通过结构化属性与已有文本标签检索；语义检索是可选增强，不是第五个核心模块。

采用Java 17与现有Spring Boot底座，模块化单体、两个应用实例、一个MySQL、一个Redis和单节点Kafka。代码版本与容器镜像实现时固定。Agent可用真实模型API；无API时Mock只验证协议，不能声称验证了模型理解效果。

四条的区别：MySQL讲交易不变量，Redis讲读路径与准入性能，Kafka讲数据库与消息的失败窗口，多Agent讲复杂需求拆解与校验收益。基础事务/幂等会交叉，简历不重复强调同一个实现。

## 2. 先固定业务合同

- 一个活动可以有多个场次，各场次有固定名额池；初版不允许售出后随意减小容量。
- 预约可含多个名额，人数和总费用必须明确；不是把“每人预算”当整组预算。
- 每用户每场次最多一份有效预约；取消后允许新意图重新预约。幂等重试与新业务意图分开。
- HELD占名额，CONFIRMED继续占名额；CANCELLED/EXPIRED不占名额。确认是无支付的预约确认，不包装成支付成功。
- 取消HELD或允许取消的CONFIRMED预约才释放名额；活动开场后的取消规则固定为不允许。
- 候补按数据库场次序号选择，不按HTTP到达时间宣称绝对公平。队首人数无法满足时暂停该场次补位，不让小人数插队；这是明确业务取舍。
- 有有效候补队列时普通新预约不能抢占队列资源，转入候补或返回队列优先提示。
- 多活动行程的预约独立提交，不保证整个行程原子成功；部分售罄后让用户调整，不能隐含跨场次事务保证。
- AI不自动创建预约或候补。用户确认后使用鉴权接口，userId来自登录身份，不采信模型或客户端自报身份。

## 3. 第一条：MySQL预约交易一致性

### 3.1 含金量与设计

解决最后名额争抢、重复预约、确认/取消/过期竞争及重复释放。核心不是UNIQUE这个词，而是名额守恒和完整状态转换。

拟定表：event、event_session、capacity_pool、reservation、active_booking、waitlist、request_dedup、outbox、consumer_inbox。容量池保存capacity/available与场次队列计数器；reservation保存quantity/status/deadline/revision与历史；active_booking以(user_id, session_id)唯一绑定有效预约。

active_booking在创建有效预约时插入，最终取消/过期时同事务删除。不要对全部历史订单直接加(user_id, session_id)唯一索引，否则合法重新预约被拒。有效候补身份也需约束，并与预约身份在场次锁下协调，避免同人同时候补与已占名额。

初版以场次容量行作为短事务串行化点，各变更遵循容量行→用户有效身份→预约/候补的统一锁顺序；按需使用FOR UPDATE，名额扣减仍带available>=quantity条件。所有涉及该场次的预约、确认、取消、过期、候补登记与分配遵守同一入口，不存在另一条绕过锁的更新路径。

这选择正确性和可解释性，热点场次行会成为瓶颈，不宣称无限横向扩展。实验中与更细粒度条件更新方案比较，不能将持有容量锁的方案包装成无锁高并发。

正常创建：身份鉴权/参数校验→固定请求身份→短事务取得场次锁→检查场次与候补优先规则→扣名额→创建HELD/有效身份→保存请求结果与Outbox→提交→返回。事务内不调用Redis、Kafka或模型；Spring事务必须通过代理生效，避免私有方法或自调用造成事务失效。

确认/取消/过期：按统一锁顺序读取最新订单，检查归属、状态与截止时间，合法转换才生效；释放数量、删除有效身份、状态更新、Outbox在同事务提交。明确确认条件为数据库时间<deadline，过期条件为>=deadline，避免边界重叠。重复取消返回既有结果，不再加名额。

幂等键包含用户和操作作用域；同键不同参数拒绝。新意图新键。成功结果与业务同事务保存；提交后响应丢失用原键查询重试。鉴权始终先于历史结果返回，不能通过重放读取别人订单。

核心不变量：每场次available+SUM(有效HELD/CONFIRMED.quantity)=capacity；available>=0；每用户场次至多一份有效预约。过期但未处理的HELD仍占库存，不在统计中提前移除。最终检查应在一致性快照或静止检查点内进行，不能拼接不同时刻的计数制造误报。

索引候选：(user_id, created_at, id)、(status, deadline, id)、(session_id, status, sequence_no)。按实际查询与EXPLAIN核验，不为了简历堆索引；订单列表用游标分页并稳定排序。

### 3.2 本地实验

1. 100名额、1000不同用户，每次1名额争抢；重复提交同请求身份。检查最终最多100有效名额，拒绝库存不足不计系统异常。
2. 加入2/3人组预约，验证quantity守恒，而不是仅数订单。
3. 重复取消、确认与过期竞争、取消与补位竞争；用屏障/故障点制造交错，不只靠随机sleep。
4. 在事务中抛异常；在提交完成后、HTTP响应前断开。检查回滚与幂等重放分别成立。
5. 对照隔离实验中的朴素读后写、条件更新、场次锁方案，解释吞吐与规则复杂度的取舍。错误基线不提供正常用户接口。

结果记录：超额分配名额数、守恒偏差、重复有效预约数、重复释放次数、成功预约吞吐、事务P95/P99、死锁/重试数。售罄拒绝、队列优先拒绝、限流拒绝、系统异常分别计数。

验收：设计的正确性场景均满足不变量；数据库异常不形成半订单。报告零异常必须注明任务、样本与注入窗口，不能推成所有故障下绝对保证。

### 3.3 面试讲法与追问

两分钟结构：限量资源有争抢→确定状态与守恒式→短事务统一转换→响应丢失重放→故障实验与场次热点瓶颈。

- 为什么不用Redis库存裁决？减少跨系统预扣/落库失败窗口；先保证正确性，用Redis保护入口，不声称这是极限吞吐方案。
- 已经有锁为什么还条件扣减？表达库存谓词和保护边界，不代表两层就能防绕过写；所有入口、事务和索引仍需检查。
- 为什么不只用乐观锁？复杂候补优先和多表身份规则初版更容易用短锁解释，乐观方案需重新核验整套谓词，热点重试可能放大负载。
- 超时后重新下单？原键查询/重试；新键可能是新意图，不由超时自动生成。
- 过期扫描怎么避免取消重复释放？重新进入统一转换事务，只有HELD且到期才改变状态与库存。
- 能否防所有超卖？只能说明经过验证的事务路径；绕过数据库、错误容量变更、配置/代码缺陷不由一次压测排除。

完成后的目标文案：**预约交易一致性：围绕限量名额分配设计预约状态机，基于MySQL短事务、条件扣减与有效预约约束，治理并发抢占及确认/取消/过期竞争，通过故障注入验证名额守恒与重复请求处理。**

## 4. 第二条：Redis热点查询与准入治理

### 4.1 含金量与设计

解决热点详情过期时的集中回源及开售入口过载。交易状态不放在缓存里裁决；库存显示附查询时间，不是预留承诺。

最终采用同步cache-aside、短TTL空值、TTL抖动和跨实例令牌回填锁。竞争者返回明确重试，不递归、不无界回源；没有软过期异步重建和L1缓存。动态预约状态走明确实时接口，不用缓存判断确认资格。

回填锁通过owner令牌条件写入/解锁，租约过期仍可能重复读取，不声称全局永远只读一次。使用独立eventflow实现，不修改或直接复用旧CacheClient。

数据库更新与独立缓存失效任务同事务，Redis Lua同时删除详情与回填锁，失效失败后台重试，TTL兜底。旧owner丢失后不能回填；回填受读取耗时和请求截止限制，数据携带revision/读取时间。异步失效仍不是强一致性，时效敏感字段绕过缓存，陈旧窗口必须实验核验。

限流独立用Redis Lua原子执行读/判断/扣减，按登录用户和接口定义额度；拒绝返回明确retry信息。Redis故障时预约入口保守拒绝并告警，不无条件放行压垮数据库；详情路径有限回源或明确降级。限流记录不等于持久账本，故障切换不宣传硬全球额度保证。

### 4.2 本地实验

- 固定种子生成1万场次；均匀分布与80%流量访问少量热点两组。
- 对照DB直查、普通TTL缓存、优化缓存。限流开启/关闭单独对照，不能把拒绝更多请求当缓存更快。
- 冷缓存、集中到期、慢数据库、重建池饱和、Redis停机、数据库更新与旧回填交错。
- 使用固定到达率负载，阶梯增加；同时记录客户端发出、服务端接纳、完成、超时、拒绝。固定并发闭环负载作为辅助，不掩盖排队延迟。
- 测回源QPS、命中率、端到端P95/P99、重建数、队列长度、拒绝率、错误率与revision陈旧窗口。负缓存也单列，不能用不存在数据的高命中率夸大正常查询效果。

验收：在固定负载下展示可复现回源减少；并发/等待有界，竞争拒绝单列；更新最终可见，硬时效路径不依赖陈旧缓存。性能差或无收益也保留，不预填“提升十倍”。

### 4.3 面试讲法与追问

两分钟结构：读热点和交易是两种时效需求→缓存负载合并与重建限额→故障时保护DB→公平性能对照→承认一致性与跨实例边界。

- 为什么不用两级缓存？初版没证据需要；新增L1会增加失效复杂度，不为技术名词引入。
- 逻辑过期适合所有数据？不适合库存成交判据；适合允许陈旧的详情，软/硬时效需合同。
- single-flight与分布式锁区别？前者同实例合并，两个实例仍可重复读取；后者另有租约/所有权问题。
- Kafka不通更新缓存怎么办？Outbox重试与TTL兜底，可能暂时陈旧；交易仍查DB。高时效字段绕过缓存。
- 限流提高QPS吗？保护吞吐和尾延迟，但拒绝率必须报告，不能把HTTP 429当成功业务处理。
- 压测平均快但P99慢？查重建、队列、连接池与GC；报告尾部与饱和点，不只平均值。

完成后的目标文案：**热点查询与流量治理：基于Redis设计活动详情缓存，结合空值缓存、过期抖动、令牌回填锁和可靠失效任务治理集中回源与更新竞争，通过原子限流及有界准入保护预约入口，量化验证尾延迟、拒绝率与数据库负载。**

## 5. 第三条：Kafka可靠事件与候补补位

### 5.1 含金量与设计

取消/过期事务写入CapacityMayBeAvailable事件。事件是重新检查提示，不是加库存指令。消费者按DB当前名额与队列状态尝试补位，消息旧/乱序也不能改变权威库存。

Outbox转发：短事务领取带owner/到期时间的事件→事务外发送Kafka→收到发送确认后条件标记已发送。发送成功、标记失败会重复发送，接受at-least-once。超时结果未知仍按原event_id重试，不生成新业务事件身份。领取到期后旧发送者可能晚到，owner条件写避免其覆盖新领取状态，但不能阻止重复消息。

消息包含event_id、session_id、类型、schema_version、来源业务修订、occurred_at，不含完整个人资料。按session_id分区；只说明分区内记录顺序，不声称所有生产者天然按DB修订提交，也不依赖顺序完成正确性。

消费者对同场次通过统一容量行事务推进：inbox唯一记录与一次补位业务效果同事务提交，领取最早有效候补，数量能满足才扣减并创建HELD、推进候补、写新Outbox。同用户已有效预约或候补已取消则按规则跳过。事务失败全部回滚，成功后提交offset。

初版每事件仅分配有限批次，仍有可分配候补时同事务生成新的检查提示；定期扫描“可用名额且存在候补”兜底。扫描进入同一业务事务，不旁路库存。不能把一个event_id标已处理后，又指望重放相同事件完成剩余分配。

消费者初版按分区顺序处理，数据库故障重试并暂停相应处理，不异步跳过失败消息后提交更高offset。永久不支持的schema等保存持久失败记录再按明确策略隔离；发送DLQ也要处理失败窗口，初版可先提供DB隔离记录与管理员重放，不吹完整DLQ能力。

过期由MySQL截止时间扫描触发，不把Redis过期通知当可靠任务源，也不把Kafka当延迟队列。通知初版为本地持久通知记录/页面查询，不虚构短信服务；通知失败不撤销已分配预约。

补位延迟拆成释放→Outbox发送、Kafka等待、消费→事务完成。记录触发来源，区分消息完成与扫描兜底完成，不让巡检掩盖Kafka链路失败。

### 5.2 本地实验

1. 固定名额、候补登记序号和取消序列；统计最终分配和违反队列策略的次数。
2. 提交Outbox后、发送前退出；发送确认后、标记前退出；发送超时未知。
3. 消费事务提交后、offset提交前退出；重复消息；旧事件晚到；候补退出与补位竞争。
4. Kafka停机30秒与120秒后恢复；MySQL短时不可用；消费者重启/再均衡。
5. 对照直接业务提交后发Kafka与Outbox方案，固定注入窗口；直接发送基线仅为对照，不成为正式路径。

指标：已提交源事件中最终入Kafka的比例、有效事件处理比例、重复业务效果数、积压峰值、补位P95/P99、恢复耗时、扫描兜底次数。发送尝试次数不是事件分母。重复事件允许，重复释放/重复有效预约不允许。

验收：规定故障窗口恢复后可对账闭环，名额不变量仍成立。单broker实验只验证应用层重试恢复，不宣称副本容灾或跨机房高可用。

### 5.3 面试讲法与追问

两分钟结构：取消后需要可靠唤醒候补→DB与Kafka双写窗口→Outbox接受重发→inbox与业务同事务→重查当前状态分配→停机实验与最终一致性。

- 为什么用Kafka而不是定时扫描？需要及时通知和独立消费者；扫描是兜底。低流量时扫描也合理，Kafka价值主要在异步解耦和实验，不吹现有业务体量。
- 开启幂等producer还会重复吗？应用重发/不同producer实例仍需业务身份；不能覆盖MySQL提交窗口。
- inbox先写了但订单没写？同一事务回滚；分两个事务会漏处理，因此不能分开。
- offset提前提交？可能漏业务；提交后再offset会重投，依靠DB幂等。
- 重放会再次释放库存吗？事件只提示重查，真正释放发生在订单状态事务；重放不按消息数量增加库存。
- 扫描都能做为什么还写可靠事件？作为方案取舍诚实回答及时性、解耦与成本；不得以单机低流量证明Kafka必要于任何规模。

完成后的目标文案：**可靠事件与候补补位：基于MySQL Outbox和Kafka构建名额释放事件链路，通过稳定事件身份、事务内消费去重及状态核对治理重发与重复消费，驱动候补分配，并以停机和崩溃注入验证补位完整性与恢复时延。**

## 6. 第四条：多Agent约束感知活动规划

本节记录早期四角色方案和拟定评测。当前实现是三角色只读编排、最多一次修订；本节“拟定80条”和四角色目标文案均非已执行测评或最终简历事实。

### 6.1 含金量与必要性

业务例：两人周六下午在同一区域参加两个活动，每人预算200元，时间不冲突，偏好安静，售罄可以候补。发现、组合取舍、事实审查是不同职责，不只是重复调用同一模型四次。

协调Agent提取RequestConstraints并调度；发现Agent取得CandidateSet；规划Agent提出PlanDraft；校验Agent提出软偏好/证据问题。固定Java orchestrator执行状态、预算、schema与调用上限，不由模型任意生成Agent或改权限。

共享结构包括request_id、constraints_revision、session_ids、候选字段与来源、读取时间、方案、已验证/未知项。每角色独立提示与工具集，使用显式上下文参数传递，不靠ThreadLocal跨异步线程。现有ThreadLocal只能在同线程边界使用，转线程必须显式传递并清理。

硬约束由Java校验：时间窗、场次存在、人数/总价、场次间冲突、截止时间。无地图接口时交通按同区域/可配置缓冲时间处理并标估算，不承诺真实路线。AI读取活动的Redis详情，动态状态再查DB；工具失败是unknown，不当售罄。

简单问题走协调/发现短路径；复杂组合才规划/校验，校验建议最多一次修订。限制总工具调用、模型轮数、总耗时，超预算返回有效部分或追问。Coordinator调用LLM也计费用与时延。

发现只调用查询工具；规划调用确定性的预算/时间检查；校验复查源数据与解释。所有角色只读业务工具，不能下单或登记候补。用户确认后跳到普通鉴权预约接口；多活动独立预约，售罄可选择候补。不把模型“审查通过”当交易权限或最终正确性。

SSE为可选交互配套，不列第五条。第一版先完成结构化方案及用户确认闭环，再做流式输出；不声称断线自动恢复，除非有事件协议与实验。

### 6.2 本地测评

拟定80条人工标注任务，30开发/50冻结测试，按模板/活动家族分组划分。简单查询、复杂组合、人数预算、模糊日期、无解、缺信息与过期数据分别统计；记录标注规则与争议，不临时改变分母。

对照A：单Agent，拥有同样查询/计算/事实工具和最终Java硬校验。
对照B：多Agent但无专职校验Agent，仍有同样最终Java硬校验。
对照C：完整多Agent，最终Java硬校验相同。

分别做相同最大预算与真实自然成本的对照，注明两种实验；不能给多Agent无限Token、单Agent极低轮次。固定模型、参数、工具数据快照、时间基准，交错执行，建议每题3次；真实Provider有随机性，记录每次原始轨迹。

指标：字段提取准确率、最终可接受方案率、复杂组合成功率、硬条件违规率、无依据事实率、正确追问/无解处理率、工具错误、P95、Token和调用数。动态场景另测推荐后售罄，不混入冻结静态题后篡改参考。软件会拦住硬错误，因此另统计生成候选违规率与被拦后的最终失败/拒绝，不能把全部拒绝包装成零违规且高成功。

Mock用于schema、调度、异常、权限与预算合同，不混入真实模型效果指标。没有真实模型结果时不能声称多Agent优于单Agent。人工盲评解释/软偏好，模型Judge仅辅助；保留分歧。展示逐例n/N与波动，不用小样本单次百分比推普遍效果。

验收：角色与工具边界可核验、异常/无解不造事实；复杂任务收益和成本都披露。多Agent无显著收益时保留路由策略与架构探索，不能预写提升效果。

### 6.3 面试讲法与追问

两分钟结构：复杂组合与简单查询不同→角色/工具分工→结构化交接和代码校验→用户确认进入真实交易→消融、成本与失败例。

- 单Agent也能做为什么拆？探索检索/组合/审查的职责隔离；以同工具对照解释收益，不靠架构图自证。
- 四个Agent需要四个模型？不需要；角色是提示、工具权限和输出契约，不是模型数量。
- 协调Agent一定并行吗？有依赖的发现→规划→校验串行；只有无依赖任务可并行，不为并行增成本。
- 校验Agent不同意就改到满意？最多一次修订；硬约束代码裁决，软争议/未知明确展示。
- 推荐还有票就能成功预约？不能，读写之间有竞争；最后由DB事务判定，售罄后用户选候补。
- 同会话并发怎么办？请求级上下文隔离，明确会话顺序策略，不让两个更新直接覆盖Redis整份history；实现时加合同测试，不把24小时TTL当并发控制。

完成后的目标文案：**多Agent活动规划：设计协调、发现、规划与校验Agent，采用结构化交接、工具权限隔离和有界修订，将自然语言需求转为可核验活动方案，并以同工具单Agent对照及角色消融评估复杂任务效果与调用成本。**

## 7. 统一实验与证据要求

所有数据为固定种子的合成活动与测试用户，不声称真实业务量。记录机器/CPU/RAM、Docker资源上限、JVM参数、版本、连接池、Kafka配置和commit。早期设计时环境尚未确认；当前本机环境与双进程/中间件实验已完成，具体规模和边界以集中报告为准，不据此承诺生产吞吐。

每组预热、重置数据/库存/队列/缓存/去重状态，再测量；至少重复3次。故障位置要有可控注入开关和超时，测试专用，默认关闭。过期使用可配置业务时钟或短测试deadline，测试与生产时间合同分开。

对性能报告吞吐/延迟/错误/拒绝一起，不把售罄、429、Mock响应纳入成功交易。同机压测器可能成为瓶颈，采集其CPU及实际发出速率；结论只覆盖本机资源环境。

实验输出建议：experiments/<date>-<commit>/<case>/config.json、原始请求结果、metrics.json、故障时间线、SQL核验、report.md。保留失败轨迹，不只保存成功截图。原始日志脱敏，不保存API key、token或完整私人对话。

指标定义在首轮正式测试前冻结；区分正确性验收阈值、性能目标、实际结果。目标不是结果。未实施的测试明确列待执行，未观察到错误不表示证明永不发生。

### 7.1 最小可复现实验矩阵（拟定，不是运行结果）

| 模块 | 数据与负载 | 对照与重复 | 核心证据 |
|---|---|---|---|
| MySQL | 100名额/1000用户，每次重置；另有多人组、状态竞争用例 | 正确方案每种故障至少重复3次；错误基线隔离 | 一致性快照核验、请求身份与订单对应、事务时间线 |
| Redis | 1万场次，固定均匀/热点分布 | 建议预热60秒、测量180秒，每组3次；先低速率再阶梯增加 | 客户端端到端原始延迟、回源计数、队列与拒绝数 |
| Kafka | 固定1000个源事件与对应预约/候补，重复/乱序序列独立保存 | 正常、30秒停机、120秒停机、两处提交后崩溃分别重置3次 | event_id闭环表、offset、inbox、订单与兜底触发记录 |
| 多Agent | 30开发/50冻结题；简单与复杂组均保留 | A/B/C同模型，每个冻结题建议3次，共450条实际轨迹 | 原始输入、角色输出、工具结果、最终校验、人工标签与usage |

负载速率以本机预实验饱和点确定，正式对照使用相同预先冻结速率，不能给慢基线更大负载。大组候补、无解AI等边界样本单列，不通过静默删难题提高通过率。实际模型失败和预算超限也纳入任务结果，usage不可取得时标未知，不估算为零。

Kafka主链路实验短时关闭兜底扫描，观察消息路径；随后恢复扫描做完整恢复实验，分别报告。扫描是业务可靠性的一部分，但不能用扫描完成的结果证明Kafka消息从未漏发。故障后恢复等待窗口固定，未收敛记录超时，不无限等待后挑成功截图。

如果本机无法承载上述规模，缩小规模并保留真实配置；先取得可重复的机制证据，再扩大负载。450条AI轨迹需要真实调用额度，执行前明确Provider、费用上限和发送数据范围；本轮未发送测试数据。

## 8. 设计Review与关闭记录

| 风险 | 修正后的合同 | 仍需实现验证 |
|---|---|---|
| 用Redis预扣制造双写补偿复杂度 | 名额只由MySQL裁决，Redis仅加速/准入 | 全部交易入口不旁路 |
| 历史订单唯一约束阻止重新预约 | 单独有效身份，取消/过期事务释放 | 重复取消与重新预约并发 |
| 多人行程却仅统计一单一名额 | quantity进入库存和预算；队首大组不跳过 | 组预约守恒与队列头阻塞 |
| 候补被普通请求绕过 | 统一场次锁下判断队列优先 | 登记候补/新预约/补位交错 |
| Kafka重复事件重复加库存 | 事件只唤醒，释放已经在状态事务完成 | 重放与乱序注入 |
| 一次事件处理后剩余候补没人推进 | 有界批次加新提示与定期扫描 | 消息/扫描触发分别统计 |
| inbox独立提交漏业务 | inbox与业务同事务，提交后offset | 崩溃窗口与再均衡 |
| Redis失效后旧值回填 | 承认有限陈旧、限定回填时间，动态校验查DB | 测陈旧窗口，不宣称零旧值 |
| 多Agent靠不公平基线取得提升 | 同工具/硬校验、固定模型、预算对照与消融 | 真实Provider重复测量 |
| 多Agent上下文串线 | 显式请求上下文与角色输出，不跨线程依赖ThreadLocal | 并发会话隔离 |
| 案例很完整就写成生产上线 | 来源与个人新增分开，合成负载/本机/无支付明确 | 每条关联代码与原始实验 |

结论：方案具备本地实现路径与面试可解释性；MySQL深度在交易不变量，Redis深度在受控回源与背压，Kafka深度在跨系统失败窗口，多Agent深度需由复杂任务对照证明。此为设计自审，不是实现验收或独立第三方审查。

## 10. 技术依据

- [MySQL锁定读取与SKIP LOCKED边界](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)：短事务锁定用于并发读取/更新；SKIP LOCKED不是通用一致性查询，也不用于绕过本方案队首公平规则。
- [Kafka交付与处理语义](https://kafka.apache.org/40/design/design/)：外部系统写入需要额外协调，本方案接受消息重投，用数据库事务治理重复业务效果，不宣称端到端exactly-once。
- [Redis限流与Lua原子操作](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)：用于请求准入，不等价业务库存或硬持久配额账本。
