核心解读：什么是 Cache Aside 模式？

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../README.md>)和[当前验收](<../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

Cache Aside，即“旁路缓存”模式。它的核心思想非常直观：应用程序直接负责与缓存和数据库进行交互。
这个模式包含两个标准操作流程：
1. 读操作流程 (Read Flow)
这是一个“懒加载”的过程：
1. 先查缓存：当应用收到一个读请求时，首先去 Redis 查询数据。
2. 命中则返回：如果缓存命中（Cache Hit），直接将数据返回给客户端，流程结束。
3. 未命中则查库：如果缓存未命中（Cache Miss），则去查询 MySQL 数据库。
4. 回填缓存：将从数据库查到的数据写入 Redis，并设置一个过期时间（TTL），然后返回数据。
2. 写操作流程 (Write Flow)
这是保证一致性的关键，也是面试的焦点：
1. 先更新数据库：当应用收到一个写（增删改）请求时，首先操作 MySQL，确保数据的持久化。
2. 再删除缓存：数据库更新成功后，立即删除 Redis 中对应的缓存项。
核心要点：写操作是“删除缓存”，而不是“更新缓存”。这样做的好处是避免了复杂的并发计算，让下一次读请求来“懒加载”最新的数据。

1. 为什么不“先删除缓存，再更新数据库”？
这种顺序存在一个致命的“脏数据回填”风险：
- 步骤1：线程A删除了缓存。
- 步骤2：在线程A更新数据库之前，线程B来读取数据。
- 步骤3：线程B发现缓存没了，于是去读数据库，此时数据库里还是旧数据。
- 步骤4：线程B将旧数据回填到缓存。
- 步骤5：线程A才姗姗来迟，更新了数据库。
- 结果：缓存里是旧数据，数据库是新数据，造成了不一致。
2. 为什么“先更新数据库，再删除缓存”是推荐做法？
这个顺序能极大降低不一致的概率：
- 步骤1：线程A更新数据库。
- 步骤2：线程A删除缓存。
- 步骤3：即使在这极短的时间窗口内，线程B来读取数据，它也会因为缓存被删除而触发“读未命中”流程，去数据库读取到最新数据并回填缓存。
- 结果：最终缓存和数据库都会是最新数据，实现了最终一致性。
🚨 进阶挑战：这个方案真的万无一失吗？
当然不是。Cache Aside 模式虽然优秀，但它只能保证“最终一致性”，在极端高并发场景下，依然存在时间窗口导致短暂的不一致。面试官通常会接着追问以下问题：
1. 如果删除缓存失败了怎么办？
这是一个非常现实的工程问题。网络抖动、Redis 服务异常都可能导致删除操作失败。
- 解决方案：异步重试机制。将删除失败的缓存 Key 发送到消息队列（如 Kafka、RabbitMQ），由一个独立的消费者服务不断重试删除，直到成功。
2. 如何保证更强的数据一致性？
如果业务对一致性要求极高，不能容忍任何短暂的不一致，该怎么办？
- 延迟双删 (Delayed Double Delete)：
  1. 先删除缓存。
  2. 再更新数据库。
  3. 休眠 N 毫秒（这个时间要大于一次读请求回填缓存的耗时）。
  4. 再次删除缓存。
  - 目的：第二次删除是为了清除在更新数据库期间，可能由其他读请求回填的旧缓存数据。
3. 有没有更自动化的方案？
除了应用层控制，还有没有更“优雅”的方法？
- 监听数据库 Binlog：
  - 使用像 Canal 这样的工具，伪装成 MySQL 的从库，实时监听数据库的变更日志（Binlog）。
  - 一旦解析到数据变更事件，就异步地去 Redis 删除对应的缓存。
  - 优点：将缓存一致性逻辑与业务代码解耦，非常优雅。
