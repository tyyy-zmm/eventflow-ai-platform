# 生活优选新版简历总览｜面试详解

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 1. 当前简历四条

1. 秒杀防超卖：Redis Lua 预扣库存与一人一单，入口削峰；
2. 交易一致性：MySQL 条件扣减、唯一约束、补偿任务、状态机与对账；
3. 异步建单：Kafka 解耦入口和数据库消费，处理重试与重复；
4. 智能规划 Agent：Discovery/Planner 拆分语义筛选和行程组合，Java 做硬约束裁决。

## 2. 理想业务链路

按当前简历语义，完整链路应是：

```text
抢购请求
-> Redis Lua 原子校验库存与用户资格
-> 生成稳定 requestId，写入待处理状态/事件
-> 可靠转发 Kafka
-> 消费者幂等创建 MySQL 订单并条件扣减
-> 更新受理结果
-> 失败补偿 Redis 预扣
-> 超时扫描与 Redis/MySQL 对账
```

这里 Redis 是高并发入口的“快速预判和预扣层”，MySQL 仍是最终订单与库存真相。Redis 判断成功不等于订单已经成功，只代表请求被受理进入异步链路。

## 3. 当前代码证据与简历差异

现有 EventFlow 主线代码采用更稳健但不同的架构：MySQL 场次行短事务直接维护权威库存与预约身份；Redis 主要负责目录 Cache-Aside 和用户/活动级 Lua 准入；Kafka 使用 Transactional Outbox/Inbox 驱动候补补位，而不是主订单异步创建。

因此必须明确：

| 当前简历 | EventFlow 当前主线 |
| --- | --- |
| Redis Lua 预扣真实库存 | Redis 做限流/准入和缓存，MySQL 扣权威库存 |
| Kafka 异步建单 | Kafka 主要驱动名额释放后的候补补位 |
| QPS 2000、MySQL 请求减少90% | 当前可复现实验更支持热目录缓存 1000→3000 QPS；不是秒杀建单 QPS |
| 并发与故障测试无超卖/重复 | MySQL 守恒与幂等实验有证据，但不能直接证明 Redis 预扣架构同样完成 |

面试前必须二选一：补齐当前简历描述对应的 Redis 预扣/异步建单实现和实验，或把简历改回与 EventFlow 代码一致的 MySQL 权威交易、Redis 准入缓存、Kafka 候补链路。本文会解释当前简历方案，但不会把缺失代码冒充已完成。

## 4. 一分钟项目介绍

> 生活优选是本地活动预约和智能规划平台。高并发预约入口用 Redis Lua 原子校验余量和一人一单，把售罄与重复请求挡在数据库前；请求进入异步链路后，由 Kafka 消费者在 MySQL 事务中用条件扣减和唯一约束完成最终建单，Redis 预扣失败则通过补偿任务、状态机和超时对账恢复，MySQL 始终是最终真相。规划侧把活动语义筛选和行程组合拆为 Discovery/Planner，模型只输出候选 ID，最终由 Java 校验预算、时间冲突和实时余量。需要说明的是，当前仓库主线后来演进为 MySQL 直接权威扣减、Redis 准入缓存和 Kafka 候补事件，和简历这版并不完全相同。

## 5. 四条如何串起来

- Redis 解决入口瞬时压力和明显无效请求；
- Kafka 削峰并把数据库写从同步请求中解耦；
- MySQL 和补偿对账保证最终业务正确；
- Agent 只做只读建议，不参与库存最终裁决。

这不是“Redis、Kafka、MySQL 各写一条”，而是同一个预约请求在准入、传递、落库和规划四个阶段的不同责任。

## 6. 最重要的面试边界

### Redis 防超卖不是最终绝对保障

Lua 在 Redis 内原子，能防止 Redis 视角库存变负；但 Redis 与 MySQL 是两个系统，故障、数据丢失或补偿失败仍可能不一致。最终订单正确性由 MySQL 条件扣减、唯一约束和对账兜底。

### Kafka 默认不是 exactly-once

生产和消费都可能重复。系统追求 at-least-once 传递下的业务效果幂等，不能说 Kafka 本身保证订单只创建一次。

### 异步受理不等于建单成功

入口应返回“排队中/已受理”，由 requestId 查询最终状态。不能在 Redis 成功后直接返回订单成功。

### Agent READY 不锁库存

规划是只读快照。用户确认时必须重新鉴权并进入预约事务检查实时余量。
