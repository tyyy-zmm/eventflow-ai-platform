# 秒杀防超卖｜面试详解

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 1. 当前简历原文

> **秒杀防超卖：**基于 Redis Lua 脚本完成库存预扣与一人一单校验，将售罄和重复购买请求拦截在数据库前；本地压测下系统入口 QPS 达到 2000，进入 MySQL 的请求减少 90%；并发与故障测试中无超卖、无重复订单。

## 2. 业务问题

活动只有 100 个名额，却可能在短时间收到大量请求。若每个请求都进入 MySQL 查用户订单、查库存、扣减再建单，热点行锁和连接池会成为瓶颈；先查后扣还存在并发窗口。

目标有三个：

1. 售罄后尽快拒绝，避免无效请求进入数据库；
2. 同一用户只能获得一次有效购买资格；
3. Redis 判断必须原子，不能在“查库存”和“扣库存”之间被其他请求插入。

## 3. Redis 数据结构

一种可讲清楚的设计：

```text
seckill:stock:{activityId}                 -> 剩余预扣库存
seckill:buyers:{activityId}                -> 已成功预扣的 userId Set
seckill:request:{requestId}                -> PENDING/SENT/SUCCEEDED/FAILED
seckill:reservation:{activityId}:{userId}  -> requestId 或预扣令牌
```

`requestId` 由客户端在同一次业务重试中复用；`activityId + userId` 用于一人一单资格。两个身份用途不同。

## 4. Lua 原子流程

Lua 在 Redis 单线程执行语义下完成：

1. 检查活动是否存在和是否开始；
2. 检查 requestId 是否已有结果，重复请求直接返回旧状态；
3. 检查用户是否已经预扣；
4. 检查剩余库存是否大于零；
5. 原子减库存；
6. 写入用户资格和 PENDING 受理状态；
7. 最稳妥的方案还应在同一 Lua 中写 Redis Stream 待转发事件，关闭“预扣成功但事件未记录”的窗口。

返回码应至少区分：成功受理、重复请求、用户重复、已售罄、活动不可用和系统错误。不能把所有失败都返回“无库存”。

## 5. 为什么 Lua 能防 Redis 侧超卖

若库存检查和扣减分两次网络命令，多个线程可能同时读到 stock=1 并都通过。Lua 把检查与扣减放在同一次原子执行中，只有一个请求能把 1 改为 0，后续看到 0 直接拒绝。

它保证的是 **Redis 预扣库存不为负**。Redis 不是最终订单数据库，因此不能单独证明系统最终绝不超卖。

## 6. 一人一单如何保证

Redis Set/键在 Lua 中做入口去重，快速挡住重复用户；MySQL 还应对活动或场次与用户建立唯一约束，防止 Redis 丢数据、绕过入口或补偿异常。入口与落库两层都要有。

## 7. Redis 预扣后的可靠性问题

### 7.1 预扣成功，应用在发 Kafka 前宕机

仅“Kafka send retry”无法解决，因为进程已经没有机会重试。需要同 Lua 写入可恢复的待发送记录，例如 Redis Stream；后台 bridge 按 requestId 转发 Kafka，成功后更新状态，扫描器处理长期 PENDING。

### 7.2 Kafka 已发送，状态未更新

可能重复发送。消费者必须按 requestId 幂等，重复事件不能重复建单或扣库存。

### 7.3 MySQL 建单失败

记录 FAILED/COMPENSATING，由补偿脚本原子恢复 Redis 库存并移除用户资格。补偿也必须幂等，避免重复加库存。

### 7.4 Redis 故障或数据丢失

不能以 Redis 恢复值覆盖 MySQL。MySQL 是权威真相，恢复后通过订单与库存对账重建 Redis 入口状态。

## 8. QPS 与 90% 数据如何解释

“入口 QPS 2000”必须明确：本机环境、压测工具、并发模型、持续时间、成功/拒绝响应如何计入、P95、错误率和硬件。QPS 只是吞吐，不等于同时在线用户数。

“进入 MySQL 的请求减少 90%”在千人抢百券场景中可以来自：1000 个请求只有约 100 个成功预扣进入建单，其他售罄/重复在 Redis 拦截。它不是所有业务 SQL 减少 90%，也不代表任意库存比例都固定减少 90%。

当前 EventFlow 可复现的 `1000→3000 QPS` 是热目录缓存独立入口，不是该秒杀链路；不能用它给当前简历的 2000 QPS 背书。

## 9. STAR 表达

### Situation

限量活动在瞬时高并发下，大量售罄和重复请求会竞争 MySQL 热点库存行，增加延迟并可能造成并发错误。

### Task

在数据库前快速完成库存和用户资格预判，降低进入 MySQL 的请求数量，同时保留最终一致性恢复能力。

### Action

- 用 Redis Lua 原子检查库存与一人一单并预扣；
- 用 requestId 处理同一请求重试；
- 保存 PENDING 状态与可恢复事件；
- Kafka 消费端按 requestId 幂等；
- MySQL 条件扣减和唯一约束最终兜底；
- 建单失败触发幂等补偿，对账修复跨系统漂移。

### Result

简历记录本地入口 QPS 2000、千人抢百券时进入 MySQL 请求减少 90%，并发与故障测试无超卖、无重复。当前仓库尚未定位与这组数字完全对应的 Redis 库存预扣报告，因此面试前必须补原始报告或调整简历。

## 10. 高频追问

### Q1：Lua 是事务吗？

它保证脚本在单 Redis 实例内原子执行，不是跨 Redis、Kafka 和 MySQL 的分布式事务。

### Q2：为什么 Redis 和 MySQL 都要校验一人一单？

Redis 用于快速拦截，MySQL 唯一约束用于最终事实兜底。缓存可能丢失或被绕过，不能只有 Redis。

### Q3：Redis 成功后能返回抢购成功吗？

只能返回已受理或排队中。最终订单成功要等 MySQL 事务完成，可通过 requestId 查询状态。

### Q4：为什么不直接用 Redisson 锁？

全局锁会串行化热点请求并增加网络开销。Lua 用常数次 Redis 操作完成简单原子状态迁移；复杂跨资源事务仍交给数据库。

### Q5：Redis Cluster 下 Lua 有什么限制？

脚本访问的 Key 必须在同一 hash slot，通常用 `{activityId}` hash tag 组织相关键。

### Q6：如何证明无超卖？

检查成功订单数量不超过初始库存、剩余库存不为负、`成功订单+剩余=初始`，并注入重复、超时、消费重放和补偿故障。单轮“没报错”不够。

## 11. 当前实现边界

EventFlow 当前 `AdmissionGate` 实现的是用户/活动固定窗口准入，不是简历所述的 Redis 权威库存预扣；权威库存由 `BookingService` 的 MySQL 短事务维护。若不补代码，面试时不能指着当前 `AdmissionGate` 说它完成了秒杀预扣。

## 12. 两分钟逐字稿

> 秒杀入口的问题是大量售罄和重复请求会直接竞争 MySQL 热点行。我用 Redis Lua 把库存检查、一人一单、预扣和受理状态放在一次原子执行中，Redis 侧库存不会因为并发检查窗口变成负数。同一业务重试复用 requestId，同一用户再用活动用户键做资格去重；MySQL 仍保留唯一约束和条件扣减作为最终兜底。Lua 成功只返回已受理，不代表订单成功。为了处理预扣后宕机，必须在同一原子链路保存待转发事件，由 bridge 可靠发 Kafka；消费者按 requestId 幂等，建单失败再用幂等补偿恢复 Redis，并通过超时扫描和对账修复漂移。简历里的 2000 QPS 和 90%是本地特定压测口径，当前仓库主线与这版架构不同，所以还需要补齐对应原始实验才能把数字讲实。
