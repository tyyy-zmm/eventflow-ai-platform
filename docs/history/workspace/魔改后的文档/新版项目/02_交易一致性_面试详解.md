# 交易一致性｜面试详解

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 1. 当前简历原文

> **交易一致性：**采用 MySQL 条件扣减与唯一约束兜底订单及库存正确性；在业务事务内记录补偿任务，结合幂等状态机与超时对账，处理 Redis 预扣后宕机、建单失败及订单取消等异常，保证 Redis 与 MySQL 最终一致。

## 2. 什么叫交易一致性

这里至少包含四个不变量：

1. MySQL 权威库存不能为负；
2. 一个用户在同一活动最多一个有效订单；
3. 同一 requestId 重试不重复扣库存；
4. 订单取消/失败后，MySQL 与 Redis 最终都能恢复相同可售语义。

“最终一致”不是每一毫秒两个系统数值都相同，而是短暂偏差可被状态机、补偿和对账收敛，且期间不会错误生成多个有效订单。

## 3. MySQL 事务内做什么

消费者收到建单事件后，在一个短事务中：

1. 查询 requestId 是否已经处理，重复则返回原结果；
2. 条件扣减库存：`UPDATE activity SET stock=stock-1 WHERE id=? AND stock>0`；
3. 影响行数为 0 则判定数据库无库存或活动不存在；
4. 插入订单；
5. 唯一约束 `(activity_id,user_id)` 防一人多单；
6. 写 request/result 状态；
7. 若需要跨系统补偿，在同一事务写 compensation/outbox task；
8. 提交后再执行外部 Redis 更新。

条件扣减防库存变负，唯一约束防重复身份，requestId 防同一请求重放。三者不是重复设计。

## 4. 为什么补偿任务要与业务事务一起写

如果先提交订单，事务外再临时创建补偿任务，进程可能在两者之间崩溃，后续不知道还需同步 Redis。将补偿意图与订单结果在同一 MySQL 事务落盘，至少保证“业务变化发生时，恢复线索一定存在”。

补偿 Worker 独立读取 PENDING 任务，执行 Redis Lua 修复，成功后标 DONE；失败记录重试次数、next_retry_at 和 last_error。状态更新用条件更新或锁避免多 Worker 重复执行。

## 5. 幂等状态机

可采用：

```text
ACCEPTED -> CREATING -> SUCCEEDED
                    -> FAILED -> COMPENSATING -> COMPENSATED
SUCCEEDED -> CANCELLING -> CANCELLED -> COMPENSATING -> COMPENSATED
```

每个转换必须定义允许的前态和幂等重复结果。例如已 `COMPENSATED` 再收到补偿请求应直接返回成功，不能再次加 Redis 库存。

## 6. 三类核心异常

### 6.1 Redis 已预扣，应用宕机

如果事件已持久记录，则恢复 bridge/消费者继续；若长时间停留 PENDING，扫描器根据 requestId 查询 Kafka/MySQL 状态，确认没有成功订单后再补偿。不能仅因超时就加库存，否则迟到消息可能随后建单。

### 6.2 MySQL 建单失败

事务回滚，不产生订单和库存扣减；更新请求为 FAILED，并生成或激活补偿任务，幂等恢复 Redis 预扣与用户资格。

### 6.3 订单取消

MySQL 事务内校验订单状态并回补权威库存，记录 Redis 补偿任务。事务提交后异步恢复 Redis；重复取消按旧结果返回。

## 7. 超时对账

对账不应直接比较两个 stock 数字，因为 Redis 可能包含合法 PENDING 预扣。应按业务状态核算：

```text
初始容量
= MySQL 可售库存
 + 有效订单占用
 + 合法待处理预扣
 + 待补偿数量
```

扫描长期 PENDING、FAILED 未补偿、CANCELLED 未回补和 Redis 孤儿资格；以 MySQL 订单、请求表和补偿任务为权威证据生成修复动作，并保留审计记录。

## 8. STAR 表达

### Situation

Redis 预扣提高入口吞吐，但跨 Redis、Kafka 和 MySQL 后，任何宕机窗口都可能造成预扣未建单、订单成功但状态未更新或取消后库存未回补。

### Task

保证订单、权威库存和用户身份正确，并让 Redis 偏差在故障后可以自动收敛。

### Action

- MySQL 条件扣减保证库存不为负；
- requestId 与用户活动唯一约束吸收重复；
- 业务事务内记录补偿意图；
- 状态机限制合法转换并使补偿幂等；
- 超时扫描结合 Kafka/MySQL 状态判断，不盲目回补；
- 对账按订单、PENDING 和补偿任务重建 Redis。

### Result

目标是并发与故障场景无超卖、无重复订单，异常状态最终收敛。当前 EventFlow 对 MySQL 守恒、request replay、Outbox/Inbox 和故障窗口有较强证据，但“Redis 库存预扣补偿”不是当前主线实现，需单独补证。

## 9. 高频追问

### Q1：为什么 MySQL 已经条件扣减，还要 Redis 预扣？

Redis 用于入口削峰和快速拒绝，MySQL 用于最终正确。若流量规模不高，直接 MySQL 短事务更简单，也是当前 EventFlow 主线最终选择。

### Q2：唯一约束失败后怎么办？

事务回滚库存扣减，按 requestId/用户身份查询原订单；若是同一请求重放返回原结果，若是不同请求重复购买则返回冲突并补偿 Redis。

### Q3：为什么不用分布式事务？

Redis、Kafka 和 MySQL 的统一强事务复杂且影响吞吐。业务允许短暂 PENDING，因此用本地事务、幂等消息、补偿和对账实现最终一致。

### Q4：超时多久补偿？

不能拍脑袋。要大于正常 Kafka 与消费延迟，并结合消费者 lag、重试状态和业务 SLA；补偿前必须确认事件没有正在处理。

### Q5：补偿失败怎么办？

任务保留 PENDING/RETRY，指数退避并告警；达到阈值进入人工处置，但不能标成功。对账会再次发现未收敛状态。

### Q6：MySQL 是唯一真相吗？

最终订单和权威库存是；但处于受理中的请求还需结合 durable acceptance log。不能只看订单表就立刻补偿所有 PENDING。

## 10. 当前代码映射

EventFlow `BookingService` 已实现 MySQL 预约状态、有效身份、request replay、短事务和 Outbox；`InvariantService` 检查容量与身份不变量；故障实验覆盖事务提交后响应丢失等窗口。这些能支撑数据库正确性方法，但不等于已实现当前简历的 Redis 预扣补偿链。

## 11. 两分钟逐字稿

> Redis 预扣只解决入口速度，最终订单和库存仍以 MySQL 为准。消费者建单时先按 requestId 查重，再执行 `stock>0` 的条件扣减、插入订单和用户活动唯一身份；任何一步失败整个事务回滚。因为 Redis 更新是外部副作用，我会在同一业务事务记录补偿任务，避免订单状态变化后没有恢复线索。请求按 ACCEPTED、CREATING、SUCCEEDED、FAILED、COMPENSATING、COMPENSATED 等状态幂等流转；超时扫描不能看到 PENDING 就直接加库存，而要先结合 Kafka 和 MySQL 判断消息是否仍在处理。取消订单也先在 MySQL 回补权威库存，再异步恢复 Redis。这样允许短暂偏差，但最终通过补偿和对账收敛。当前 EventFlow 的 MySQL 守恒和故障实验有代码证据，Redis 预扣补偿仍需要按简历描述补齐实现。
