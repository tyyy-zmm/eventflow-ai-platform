# 异步建单｜面试详解

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 1. 当前简历原文

> **异步建单：**基于 Kafka 异步建单，通过发送重试与消费幂等保障消息可靠处理，提高并发性能，保障已受理请求可恢复、订单不重复。

## 2. 为什么异步

同步链路需要请求线程等待数据库锁、插入订单和后续处理。高峰时连接池和热点行会把延迟传回入口。异步链路在 Redis 准入后快速返回 requestId，把数据库写交给消费者按能力处理，起到削峰和隔离作用。

代价是用户拿到的不是最终订单，而是“已受理”；系统需要状态查询、幂等、积压监控、失败补偿和对账。

## 3. 完整链路

```text
Lua 预扣成功并产生 durable pending event
-> bridge 读取并发送 Kafka
-> broker ack 后标记 SENT
-> consumer 收到事件
-> MySQL 事务：Inbox/request 去重 + 条件扣减 + 订单 + 状态
-> commit 后 ack offset
-> 更新结果查询状态
-> 失败进入补偿/重试/死信处置
```

只调用 `kafkaTemplate.send()` 再做内存重试不够，因为应用可能在发送前永久退出。要“已受理请求可恢复”，受理事件必须先持久化：可以是同一 Lua 写入 Redis Stream，也可以在数据库事务写 Outbox；当前简历的 Redis 预扣架构更自然地使用 Redis Stream/持久 PENDING 作为 acceptance log。

## 4. 生产端可靠性

### 4.1 稳定事件身份

eventId/requestId 在首次受理时生成，重试必须复用原 ID。新建 ID 会让消费者无法识别同一业务事件。

### 4.2 发送重试

对瞬时网络错误有限重试并退避。无法确认 broker 是否已接收时按 at-least-once 处理，即允许重复发送，由消费者幂等吸收。

### 4.3 待发送租约

多个 bridge 实例领取 PENDING 事件时使用 owner、lease_until 和条件更新，避免永久占用。网络发送不能持有数据库长事务或全局锁。

### 4.4 发送后宕机

broker 已收到但本地仍是 PENDING，租约过期后会重发，因此重复是正常路径，不能依赖“通常只发一次”。

## 5. 消费端幂等

消费者在 MySQL 事务中先登记 Inbox/request：

```text
UNIQUE(consumer_name, event_id)
```

首次事件完成条件扣减和建单；重复事件查询已有处理结果后直接返回。Inbox、订单和库存变化必须在同一事务，不能先写 Inbox 再在另一个事务建单，否则中途崩溃会把未完成事件误判为已处理。

用户活动唯一约束是另一层：eventId 去重防同一消息重放，`(activity_id,user_id)` 防不同请求绕过一人一单。

## 6. Offset 提交

数据库事务提交成功后才提交 Kafka offset。若先 ack 再写数据库，宕机会永久丢订单；若数据库提交后 ack 前宕机，消息会重放，但 Inbox 幂等能吸收。

这实现的是 at-least-once 下的业务效果一次，不是 Kafka exactly-once。

## 7. 分区与顺序

可按 activityId 分区，使同一活动事件进入同一分区，减少跨消费者乱序；但分区内顺序也可能被重试、业务并发和补偿影响。订单创建通常靠幂等与状态机，不仅靠消息顺序保证正确。

热点活动单分区可能成为瓶颈，需要在严格顺序与吞吐之间取舍。若每个请求独立且数据库条件扣减可裁决，可按更细粒度分区提高并行。

## 8. 失败处理

- 可重试错误：数据库短暂不可用、网络超时，退避重试；
- 业务失败：无库存、重复购买，不应无限重试，转补偿；
- 毒消息：schema 错、字段缺失，记录原事件和错误，进入隔离/死信并告警；
- 长期积压：监控 consumer lag、PENDING 年龄、最老未发送事件和失败率；
- 状态不确定：按 requestId 查询 Inbox、订单和 acceptance log 后再决定重放或补偿。

## 9. STAR 表达

### Situation

秒杀入口若同步等待 MySQL 建单，会把数据库锁等待和连接池压力传给请求线程，峰值流量下延迟和失败快速放大。

### Task

将入口受理和数据库建单解耦，同时保证进程崩溃、重复发送和重复消费后订单仍不丢、不重。

### Action

- Redis 准入后持久化 request/event 状态；
- bridge 使用稳定 eventId、租约和有限重试发送 Kafka；
- 消费者在同一 MySQL 事务完成 Inbox 去重、条件扣减、订单与状态；
- commit 后再提交 offset；
- 业务失败触发幂等补偿；
- 监控 lag、最老 PENDING 和失败事件并支持重放。

### Result

理论上入口能快速返回并由消费者削峰，at-least-once 重放不产生重复订单。当前 EventFlow 已实现 Outbox/Inbox、发送租约、原 eventId 重投和 Kafka 故障实验，但作用于候补补位；当前简历声称的主订单异步建单需单独实现和压测。

## 10. 高频追问

### Q1：发送重试为什么不能保证不丢？

进程可能在获得 Redis 成功后、调用发送前宕机，根本没有机会重试。必须先持久化待发送事件。

### Q2：Kafka 幂等生产者够吗？

只能减少同一 producer session 的重复写，不能替代业务 requestId、跨重启恢复和消费端幂等。

### Q3：为什么不说 exactly-once？

跨 Kafka 与 MySQL 的业务事务仍可能重放。系统通过 Inbox 和数据库事务实现效果幂等，而不是端到端消息恰好一次。

### Q4：消费失败后一直重试会怎样？

毒消息会阻塞分区。需要区分可重试和不可重试错误，达到阈值后隔离并告警，同时保留人工重放与补偿入口。

### Q5：Kafka 挂了还能抢吗？

若 acceptance log 可持久化且有容量上限，可以短时间继续受理并等待恢复；积压过大时应停止准入，防止 Redis 预扣长期占用。没有持久 acceptance log 时不能继续承诺可恢复。

### Q6：如何让用户查询结果？

入口返回 requestId；状态接口查询 ACCEPTED/PROCESSING/SUCCEEDED/FAILED/COMPENSATED，并在成功时返回 orderId。查询本身要鉴权，不能让用户枚举他人请求。

## 11. 当前代码边界

EventFlow 的 `OutboxDispatcher`、`KafkaDelivery`、`Inbox` 和 ReplayService 能支撑可靠消息机制的讲解，故障点覆盖 outbox-after-send 与 consumer-after-commit；但业务语义是候补事件，不是当前简历的主订单异步创建。不能只改名词就当作同一实现。

## 12. 两分钟逐字稿

> 异步建单的目标是把入口受理和 MySQL 写入解耦，但可靠性不能只靠 Kafka send retry。Redis Lua 预扣成功后必须先形成 durable pending event，例如同一脚本写 Redis Stream，bridge 再用稳定 eventId 和租约发送 Kafka。broker 已收到但本地没标记时会重发，所以按 at-least-once 设计。消费者在同一个 MySQL 事务里完成 Inbox 去重、库存条件扣减、订单和请求状态，提交后再 ack offset；数据库提交后宕机会重放，但 Inbox 返回原结果，不重复扣库存。无库存或重复购买属于业务失败，不能无限重试，要进入 Redis 补偿。当前 EventFlow 已有 Outbox/Inbox 和 Kafka 故障窗口实现，但用于候补补位；若简历继续写异步建单，还需要补齐主订单链路和对应实验。
