# 智能规划 Agent｜面试详解

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 0. 当前简历原文

> **智能规划 Agent：** 构建 Discovery/Planner 双 Agent 完成活动检索与行程编排，并由 Java 校验预算、时间冲突和余量，确保方案可执行。

## 1. 为什么项目需要 Agent

用户可能用自然语言提出城市、时间、人数、总预算和软偏好，希望组合多个活动。模型适合处理偏好和候选组合，但不能决定库存，也不能直接预约。因此系统将结构化硬约束与自由文本偏好分离：硬字段缺失直接拒绝，Agent 只在只读候选快照上生成方案，最终由 Java 校验。

## 2. 最终架构

### Discovery

从最多 50 条候选中读取活动 ID、标题、描述、区域、时间、价格和余量，依据自然语言偏好筛选候选 ID。只能选择已提供 ID，且不能删掉所有确定可行候选；否则失败关闭。候选文本按不可信数据处理，不能改变系统指令。

### Planner

基于结构化约束、偏好、Discovery 结果和上一轮校验反馈，返回最多 10 个场次 ID。最多修订一次，避免模型无限自循环。

### Java Validator

验证场次是否在允许集合、城市和时间窗是否正确、余量是否满足、整组总价是否超预算、ID 是否重复、场次是否重叠。Review 后重新读取目录并做一次权威校验，两轮最多复读 20 个场次。

### Adaptive Review

仅在以下风险出现时调用：

- `SUSPICIOUS_PREFERENCE`：偏好含绕过规则、立即预约/支付等可疑指令；
- `MULTI_SESSION_PLAN`：多场次组合；
- `CANDIDATE_WINDOW_PRESSURE`：候选达到 40 条；
- `VALIDATION_REVISION`：方案经过硬校验反馈后修订。

Review 只产生 advisory，不参与合法性裁决。Review 格式异常时降级到 Java 硬校验；真实 Provider 调用失败在正式评测中会停止整轮，防止降级结果掩盖实验故障。

## 3. 为什么不是让模型自由回答

模型不知道实时库存，也可能返回未知 ID、超预算、重叠方案或被偏好中的提示注入影响。项目采用四层约束：

1. 结构化请求合同；
2. 候选白名单和角色输出 JSON schema；
3. 调用次数、Token、时间和工具读取预算；
4. Java 硬校验与真实预约事务重新检查。

即使规划结果是 READY，也不占用名额。用户确认后必须进入正式鉴权和 MySQL 预约事务。

## 4. 评测设计

冻结 v2 包含 96 条合成案例，开发集/测试集各 48 条；每组有 44 条有效请求和 4 条本地拒绝输入。覆盖预算、余量、售罄、城市、时间窗、重叠、无解、提示注入、多场次和 40 候选压力。

对比三条路线：

- `single`：单 Agent 直接看到全部候选；
- `dual`：Discovery + Planner；
- `adaptive`：Discovery + Planner + 风险触发 Review。

三者使用同一 DeepSeek 模型、温度 0、同一候选快照和同一 Java 硬校验。固定测试集只在源码、测试和哈希冻结后运行一次。

## 5. 最终结果

44 条有效固定测试：

| 路线 | 匹配 | 调用数 | Token | P50/P95 |
|---|---:|---:|---:|---:|
| single | 40/44 | 42 | 22,503 | 567/1,223ms |
| adaptive | 44/44 | 96 | 52,362 | 1,232/2,880ms |
| dual | 44/44 | 72 | 30,162 | 1,070/1,668ms |

单 Agent 的四个失败全部是协议遵循问题：一次连续返回空方案；一次首轮返回 20 个 ID；两次收到重叠反馈后第二轮返回 20 个 ID。双角色两条路线都通过这四题。

最重要的消融结论是：adaptive 和 dual 都为 44/44，Review 没有带来正确率收益，却多 24 次调用、22,200 Token，P95 也更高。因此不能写“Review 提升准确率”，只能说它提供风险审计建议。

原 v2 主要核对最终状态和硬约束，并不能证明方案真的符合“看展、不要体育”等软偏好。补充语义冻结集后，评测器会同时核对具体活动 ID 组合；开发集和只运行一次的固定测试集各 8 题，覆盖中英文偏好、多活动顺序、排除条件及候选文本提示注入。结果如下：

| 数据集 | single | Discovery+Planner | 结论 |
|---|---:|---:|---|
| 开发集 | 8/8 | 8/8 | 两条路线均选对具体方案 |
| 固定测试集 | 8/8 | 8/8 | 未观察到角色拆分的语义收益 |

固定测试中 single 使用 8 次调用、2,852 Token、P95 932ms；Discovery+Planner 使用 16 次调用、5,133 Token、P95 1,383ms。因此语义测试支持“系统能依据活动内容落实偏好”，不支持“多 Agent 在所有任务上都更准”。角色拆分的已观察优势仍是 v2 中复杂反馈场景的输出协议稳定性。

## 6. 开发集发现的工程问题

扩展评测不是只为了得到分数，还发现了两个实现缺陷：

1. 原工作流每轮在 Review 前后各校验一次，10 场次、两轮修订最坏需要 40 次复读，与 20 次预算冲突。修复为每轮只在 Review 后做一次权威校验，两轮正好最多 20 次。
2. 离线 adaptive 遇到超长 Review 建议会失败，而生产环境会降级。统一后，Review 格式问题只产生安全 advisory，Provider 错误仍停止评测。

这比单纯报告 44/44 更有含金量，因为说明评测真正反馈到了系统设计。

## 7. 高频追问

### dual 已经 44/44，为什么还保留 Review

Review 的目标不是硬约束正确率，而是对提示注入、多场次和大候选窗口留下独立审计建议。它按风险触发且不参与业务裁决。若业务只关心本次冻结集的正确率和成本，应选择 dual；是否保留 Review 是审计需求与成本的产品取舍。

### 44/44 能说明 Multi-Agent 更好吗

只能说明在这 44 条合成冻结案例上，角色拆分比单 Agent 少了四次输出协议失败。样本不大、测试集本地可见、没有多模型多轮重复，因此不能外推成总体准确率提升。

### Agent 真的理解活动偏好吗

候选中已加入标题、描述和区域，Discovery 明确负责偏好筛选；语义评测不再只看 READY，而是比较具体活动组合。中英文固定测试 8/8，但 single 同样为 8/8，所以可以说“偏好选择已验证”，不能把它说成多 Agent 带来的提升。

### 为什么 Review 不直接拒绝错误方案

自然语言 Review 也会误判。硬约束已有确定性代码，若让 Review 拥有否决权，会把合法方案变成失败。Review 只提示风险，Java Validator 才是权威。

### 多 Agent 是不是多个模型

不是。角色表示提示词、工具权限、输入输出合同和职责边界，可以复用同一个模型。这里所有路线使用同一个 DeepSeek 模型，避免模型差异干扰架构对照。

## 8. 一分钟回答

> 我把自然语言行程规划拆成 Discovery 和 Planner。Discovery 根据活动标题、描述和区域筛选偏好，Planner 负责组合顺序，候选和方案都走结构化 ID 协议，最终由 Java 检查城市、时间、余量、整组预算和冲突。固定硬约束测试里双角色 44/44、单 Agent 40/44，差异来自复杂反馈后的协议遵循；另做的语义测试中两者都是 8/8，因此我只说多 Agent 改善了职责隔离和这组复杂任务的协议稳定性，不宣称所有任务都更准。
