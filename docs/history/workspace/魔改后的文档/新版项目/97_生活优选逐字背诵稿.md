## 使用方法

先掌握一分钟项目总述，再分别准备四条九十秒展开。后端三条必须作为同一请求链路讲，不能变成 Redis、MySQL、Kafka 三段互不相干的八股。数字只按实际实验口径回答；当前代码与简历架构的差异必须主动掌握。

## 一、30 秒版本

> 生活优选是一个本地活动预约与智能规划平台。高并发预约入口使用 Redis Lua 原子完成库存预扣和一人一单校验，Kafka 异步传递建单事件，MySQL 通过条件扣减和唯一约束保证最终订单正确，并用补偿任务、状态机和超时对账处理跨系统故障。规划侧使用 Discovery/Planner 双 Agent 完成活动筛选和行程组合，最终由 Java 校验预算、时间冲突和余量。

## 二、1 分钟版本

> 项目面向本地活动查询、限量预约、候补补位和智能行程规划。秒杀入口为了避免所有请求直接竞争 MySQL 热点库存行，我用 Redis Lua 在一个原子脚本里检查剩余名额和一人一单，并记录预扣和请求状态，把售罄及重复请求挡在数据库前。通过准入只代表请求已受理，事件随后交给 Kafka 异步处理；消费者按 requestId 幂等执行，在 MySQL 本地事务中通过 `stock > 0` 条件扣减和用户活动唯一约束创建订单。Redis 预扣后如果发生宕机、建单失败、取消或超时，由事务内补偿任务、条件状态机和定时对账让 Redis 与 MySQL 最终一致。智能规划侧把偏好筛选和行程组合拆成 Discovery/Planner，模型只输出候选 ID，Java 再检查预算、时间冲突和实时余量，避免模型直接决定库存或订单。

## 三、3 分钟完整版本

> 生活优选主要有两条线：一条是高并发活动预约，另一条是智能行程规划。预约链路最核心的要求不是单纯追求 QPS，而是在高并发、重复请求和依赖故障下同时保证库存不为负、同一用户不重复购买、受理请求不丢失。
>
> 第一层是 Redis 秒杀准入。旧做法如果每次都查 MySQL 是否购买过，再更新热点库存行，会消耗数据库连接并产生锁竞争。我把库存检查、一人一单、预扣和请求记录放到同一个 Lua 脚本里原子执行，大量售罄和重复请求直接在入口返回。这里 Lua 只能保证 Redis 内部原子，所以返回的是“已受理”，不能直接说订单创建成功。
>
> 第二层是 MySQL 交易一致性。Kafka 消费者落库时仍使用 `WHERE stock > 0` 的条件扣减，并建立用户和活动的唯一约束；库存扣减、订单写入和请求终态在同一个本地事务里完成。Redis 解决入口性能，MySQL 独立守住最终正确性，两者不是重复设计。
>
> 第三层是 Kafka 异步建单。入口和数据库写解耦后，Kafka 可能重复投递，消费者也可能在事务提交后、位点确认前宕机，因此消息携带稳定 requestId，消费者先检查持久状态，重复消息返回原结果。Redis 已预扣但消息未完成、建单失败或订单取消时，系统记录幂等补偿任务；超时扫描和对账比较请求、订单、库存与补偿状态，最终让两个系统收敛。Kafka 提供至少一次传递，业务幂等保证“重复处理没有新增业务效果”。
>
> 第四层是智能规划。用户偏好是自然语言，适合模型理解，但预算、时间、余量和库存属于硬约束。我让 Discovery 先从白名单候选中筛选活动，Planner 组合行程，模型只返回结构化 ID；Java Validator 检查城市、时间窗、总预算、场次重叠和余量。规划 READY 仍不锁库存，用户确认后必须重新进入标准预约事务。
>
> 简历里写的 2000 QPS 是秒杀入口吞吐，不等于每秒创建 2000 笔订单；MySQL 请求减少 90% 对应特定售罄比例的负载。当前仓库主线更偏向 MySQL 权威交易、Redis 准入缓存和 Kafka 候补补位，与简历的 Redis 真实预扣版仍有差异，完整新链路和同口径压测需要补齐后才能把数字视为当前可复现实验。

## 四、秒杀防超卖九十秒稿

> 这条解决的是高并发请求全部进入 MySQL 后的连接和热点行锁压力。入口用 Redis Lua 原子检查库存和用户集合，在同一个脚本里完成预扣、一人一单标记和请求受理记录，避免“先查后扣”被并发穿插。售罄和重复请求直接返回，不进入数据库。Lua 成功只表示 Redis 侧获得资格，不能证明 MySQL 订单已经生成，所以后续仍有 Kafka 和 MySQL 兜底。简历的 2000 QPS 是入口处理能力，不是订单 TPS；MySQL 请求减少 90% 来自千人抢百券这类多数请求售罄的负载，换成库存充足场景比例会变化。最终无超卖和无重复必须同时核对 MySQL 库存、有效订单和用户活动唯一性。

### 一句话收尾

> Redis Lua 负责在高并发入口快速、原子地筛掉不具备资格的请求，而不是取代最终订单数据库。

## 五、交易一致性九十秒稿

> Redis 和 MySQL 是两个独立系统，不可能用一个本地事务同时提交。我的设计是让 MySQL 成为订单和权威库存的最终真相：消费者在一个本地事务里执行库存大于零的条件扣减、用户活动唯一约束、订单创建和请求终态更新。Redis 已预扣但建单失败时，事务内记录补偿任务，由 worker 按 requestId 幂等回补；取消和过期使用条件状态转换，防止重复释放；定时对账扫描长时间停留的请求并比较 Redis 预扣、MySQL 有效订单和补偿记录。系统允许短时间不一致，但保证最终收敛。条件扣减防库存为负，唯一约束防重复订单，补偿和对账处理跨系统故障，三者职责不同。

### 一句话收尾

> 最终一致性不是“等一会自然一致”，而是每个异常都有可重试、可对账且幂等的恢复动作。

## 六、异步建单九十秒稿

> Kafka 的价值是把高并发入口与数据库建单解耦，让入口快速返回受理状态，并平滑后续 MySQL 写压力。可靠性不能只靠生产者 ack，因为发送可能重试、消费可能重复。消息携带 eventId 和 requestId，生产侧失败有限重试，消费侧关闭自动提交，只有 MySQL 事务成功后才确认位点。若订单已经提交但确认前宕机，消息会重投，消费者通过请求终态和唯一约束返回原结果，不重复扣库存。若 Kafka 长时间不可用，已可靠记录的受理事件恢复后继续发送或按截止时间转 EXPIRED，并触发补偿。系统追求 at-least-once 下的业务效果幂等，不宣称跨 Redis、Kafka、MySQL 的 exactly-once。

### 一句话收尾

> Kafka 负责削峰和传递，订单不重复依赖稳定业务身份、消费幂等和数据库约束。

## 七、智能规划 Agent 九十秒稿

> 用户会用自然语言描述城市、时间、人数、总预算和偏好，模型适合做语义筛选和组合，但不能直接决定库存。我把流程拆成 Discovery 和 Planner：Discovery 只从最多 50 条白名单候选中选择符合偏好的活动 ID；Planner 根据结构化约束组合最多 10 个场次，并在校验反馈后最多修订一次。最终 Java Validator 检查候选归属、城市、时间窗、总预算、重复 ID、场次冲突和余量。这样模型负责软偏好，代码负责硬约束。规划使用只读快照，READY 不锁库存，真正预约时重新校验实时余量。

### 一句话收尾

> 多 Agent 的目的不是增加模型数量，而是拆开候选筛选和行程组合，并把最终合法性留给确定性代码。

## 八、数据回答模板

> QPS、P95 和数据库请求减少比例都必须绑定测试接口和负载。2000 QPS 指秒杀入口请求吞吐，不等于订单 TPS；减少 90% 指特定库存与请求比例下，大量售罄和重复请求没有进入 MySQL。当前项目另有热点目录约 1000 到 3000 QPS 的缓存实验，它不能拿来证明秒杀入口。若原始秒杀报告不完整，我会说明这是简历历史记录或目标值，不补造机器、时长和峰值口径。

## 九、项目代码差异回答模板

> 当前仓库主线先实现的是 MySQL 权威预约、Redis 准入缓存和 Kafka Outbox/Inbox 候补链路；简历后来选择了更偏秒杀的 Redis 预扣和 Kafka 异步建单方案。两者共享条件扣减、唯一约束、幂等状态和故障恢复思想，但不是同一条完整实现。我会展示已经完成的代码，并明确预扣版仍需补可靠事件转发、补偿对账和同口径压测，不把设计稿说成已上线代码。

## 十、结尾总结

> 这个项目的核心不是简单使用 Redis、MySQL 和 Kafka，而是让三者在同一预约链路中分别承担高并发准入、最终交易正确性和可靠异步传递，再用状态机、补偿和对账把故障闭环。
