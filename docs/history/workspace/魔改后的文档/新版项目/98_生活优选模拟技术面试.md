## 评分方式

每题按 0～3 分自评：0 分只会复述名词；1 分能说目的；2 分能讲执行链路与异常；3 分能讲清取舍、故障窗口、实验口径和代码边界。

## 第一轮：项目总览

### Q1：介绍一下生活优选项目。

**参考回答：**

> 这是本地活动预约和智能规划平台。预约侧用 Redis Lua 做库存预扣和一人一单准入，Kafka 异步传递建单事件，MySQL 用条件扣减和唯一约束保证最终正确，并通过补偿、状态机和对账处理跨系统故障。规划侧用 Discovery/Planner 做活动筛选与行程组合，Java 校验预算、冲突和余量。

**追问：四条内容之间是什么关系？**

> Redis 解决入口高并发，Kafka 解决异步削峰和可恢复传递，MySQL 解决最终交易正确性，Agent 解决自然语言活动规划。前三条是一条订单链路，Agent 只提供建议并复用标准预约接口。

## 第二轮：Redis Lua

### Q2：Redis 如何防超卖和一人一单？

**参考回答：**

> Lua 在一个原子脚本里检查库存、用户集合和 requestId，然后预扣库存、记录用户和受理事件。其他命令不能在脚本中间插入，因此不会出现两个请求同时通过最后一份 Redis 库存或同一用户并发通过资格校验。

**追问 1：为什么不能说 Redis 百分之百保证不超卖？**

> Lua 只保证 Redis 内部原子，Redis 与 MySQL 之间仍有故障窗口。最终还要由 MySQL 条件扣减、唯一约束和对账守住业务事实。

**追问 2：Redis 预扣成功后能直接返回下单成功吗？**

> 不能，只能返回已受理或排队中。订单成功以 MySQL 事务提交为准，客户端按 requestId 查询终态。

**追问 3：Set 会不会形成大 Key？**

> 大活动可能形成大 Key。可以按 userId hash 分片，或在连续用户 ID 场景用 Bitmap；但会增加对账和 Cluster slot 复杂度，应由实际规模决定。

**追问 4：Lua 脚本太大会怎样？**

> Redis 执行脚本时会阻塞其他命令，因此脚本必须短小、固定复杂度，不能扫描大集合或做不可控循环。

## 第三轮：MySQL 交易正确性

### Q3：Redis 已扣库存，为什么 MySQL 还要再扣？

**参考回答：**

> Redis 是入口准入层，MySQL 是订单和库存最终真相。Redis 可能丢数据、恢复错误或补偿失败，所以 MySQL 仍用 `stock > 0` 条件扣减独立保证库存不为负。

**追问 1：条件扣减和唯一约束分别解决什么？**

> 条件扣减保证库存不能减到负数；`UNIQUE(user_id, activity_id)` 保证同一用户不能生成两张订单。一个控制资源数量，一个控制业务身份唯一。

**追问 2：为什么必须放在同一事务？**

> 如果扣库存成功但订单插入失败，会出现库存丢失；如果订单成功但请求状态未更新，重试难以判断。三者同事务可以一起提交或回滚。

**追问 3：唯一约束冲突后怎么办？**

> 回滚当前事务，再按用户活动或 requestId 查询已有订单并返回原结果。不能吞掉异常后继续提交部分状态。

## 第四轮：Redis 与 MySQL 一致性

### Q4：如何保证 Redis 和 MySQL 最终一致？

**参考回答：**

> 不做跨系统强事务，而是为每个请求保存状态。Redis 预扣后，MySQL 建单成功进入 SUCCEEDED；失败则记录幂等补偿任务，回补 Redis 并转 REJECTED/EXPIRED。取消或超时用条件状态转换避免重复释放，定时对账扫描悬挂请求并比较 Redis 预扣、MySQL 有效订单和补偿记录。

**追问 1：补偿执行两次怎么办？**

> 补偿任务有唯一业务键和状态条件，只允许从 PENDING 转 DONE；Redis 回补脚本检查 requestId 和当前 owner/state，已经补偿的请求不再次加库存。

**追问 2：如果补偿一直失败？**

> 按退避策略重试并告警，超过阈值进入人工处理队列；对账仍保留差异。不能把任务标完成来掩盖异常。

**追问 3：最终一致需要多久？**

> 由重试退避、扫描周期和业务 SLA 决定，应在实验中报告 P95/P99 收敛时间。没有数据时不能回答固定秒数。

## 第五轮：Kafka 异步建单

### Q5：Kafka 在项目中起什么作用？

**参考回答：**

> 把入口准入和 MySQL 建单解耦，削平瞬时流量，并允许已受理请求在消费者或数据库短时故障后恢复处理。它不直接保证业务 exactly-once。

**追问 1：如何避免消息丢失？**

> 生产端使用可靠事件记录、broker ack 和有限重试；消费者关闭自动提交，事务成功后再确认位点。真正关键是受理事件必须在 Redis 预扣后可恢复，不能只在内存里调用一次 send。

**追问 2：事务提交后、确认位点前宕机会怎样？**

> 消息重投。消费者根据 requestId、请求终态和唯一约束识别已经完成的订单，不重复扣减。

**追问 3：Kafka 停机两分钟怎么办？**

> 新事件在可靠待发送记录中积压，恢复后按截止时间处理；超过业务截止时间的请求转 EXPIRED 并补偿。入口根据积压量和最老消息年龄收紧准入，避免无限接受。

**追问 4：Kafka 堆积只需要扩消费者吗？**

> 不一定。如果瓶颈在 MySQL，扩消费者会放大锁竞争。要先区分消费者 CPU、外部依赖、分区数和数据库瓶颈，再决定扩容或限流。

## 第六轮：性能数据

### Q6：2000 QPS 是怎么来的？

**参考回答：**

> 它应表示秒杀入口在指定本机环境和固定负载下的吞吐，而不是订单 TPS。完整回答要包含机器、并发、库存、持续时间、稳定段或峰值口径、P95/P99 和错误率。当前原始报告若未完整保留，我只把它作为简历历史数据或待复现实验，不补造细节。

**追问 1：1000 个用户为什么能测出 2000 QPS？**

> 用户数不等于请求总数，也不等于一秒只发一次。压测线程可以在一个时间窗口内持续请求或重试，因此瞬时/短窗口吞吐可能超过并发用户数。必须说明脚本模型和统计窗口。

**追问 2：MySQL 请求减少 90% 为什么不是 100%？**

> 合法准入请求仍要落库。千人抢百券时理论上约 100 个有效请求进入 MySQL，其余售罄或重复请求被 Redis 拦截，所以约减少 90%；换负载后比例会变化。

**追问 3：无超卖如何验证？**

> 不能只看接口成功数。要检查 MySQL 库存非负、初始库存减有效订单等于剩余库存、用户活动无重复、Redis/MySQL 最终对账无悬挂补偿。

## 第七轮：智能规划 Agent

### Q7：为什么要拆 Discovery 和 Planner？

**参考回答：**

> Discovery 负责从候选中理解偏好并筛选活动，Planner 负责时间顺序和组合。拆分让输入输出合同更小，也方便分别限制候选 ID 和方案长度；最终硬约束仍由 Java 校验。

**追问 1：为什么模型不能直接校验预算和余量？**

> 这些是确定性且与实时数据相关的规则，代码更可靠、可测试。模型负责软偏好，Java 负责数值和合法性。

**追问 2：规划时余量充足，预约时售罄怎么办？**

> 规划只读快照，不占库存。用户确认时重新进入 Redis/MySQL 预约链路校验；失败后提示重新规划，不能把 READY 当成预留成功。

**追问 3：多 Agent 一定比单 Agent 更好吗？**

> 不一定。当前硬约束冻结集中双角色 44/44、单 Agent 40/44，主要差异是复杂反馈后的协议遵循；语义测试两者都是 8/8。可以说职责隔离和特定复杂场景更稳定，不能说所有任务都更准。

## 第八轮：代码真实性压力追问

### Q8：你简历写的架构和当前代码完全一致吗？

**参考回答：**

> 不完全一致。当前仓库主线更偏 MySQL 权威预约、Redis 准入缓存和 Kafka 候补 Outbox/Inbox；简历是后续设计的 Redis 预扣、Kafka 主订单异步建单版本。交易约束、幂等和恢复思想能复用，但预扣版仍需补齐可靠事件转发、补偿对账和同口径压测。我不会把设计方案冒充成全部已实现代码。

### Q9：如果只允许保留当前代码能证明的简历，你怎么改？

**参考回答：**

> 改成 MySQL 预约交易治理、Redis 热点缓存与活动准入、Kafka Outbox/Inbox 候补补位，以及 Multi-Agent 行程规划。这样每条都能与现有代码和实验直接对应。

### Q10：这个项目最大的技术难点是什么？

**参考回答：**

> 不是写 Lua 或接 Kafka，而是明确每个系统的真相边界和崩溃窗口：Redis 受理后如何可靠产生事件、消息重复如何不重复扣减、建单失败如何只补偿一次、迟到消息如何不覆盖终态。把这些问题用业务身份、状态机、数据库约束和对账闭环串起来，才是真正的可靠性设计。
