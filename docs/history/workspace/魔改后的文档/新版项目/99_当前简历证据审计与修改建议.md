## 1. 结论先说

当前简历的 4 条均已建立详解文档，但后端三条描述的是一套“Redis Lua 预扣库存 + Kafka 异步建单 + MySQL 最终兜底”的秒杀架构，而当前仓库主线实现更接近：

```text
Redis：缓存与入口准入
MySQL：预约权威事务、条件扣减和唯一约束
Kafka：Outbox/Inbox 驱动候补补位
```

因此，现有文档可以解释当前简历方案应该如何设计，却不能证明该方案已经全部在代码中实现。正式投递前必须二选一：补齐简历所述代码与实验，或把简历改回当前仓库已有实现。不能只靠面试话术弥合差异。

## 3. 数字的证据风险

当前简历写“入口 QPS 达到 2000、进入 MySQL 的请求减少 90%、无超卖、无重复订单”。现有仓库可找到的是热点目录缓存路径的压测材料，与秒杀订单入口不是同一接口；因此不能拿目录 QPS 直接证明秒杀 QPS。

要保留这些数字，至少需要一份可复跑的秒杀压测报告，记录：

- Git commit、机器配置、JVM/Redis/MySQL/Kafka 版本；
- 并发用户、请求总量、压测时长、库存量、优惠券/用户分布；
- 吞吐口径是平均、稳定段还是峰值 QPS；
- P50/P95/P99、错误率、Kafka lag 与数据库连接池状态；
- Redis 准入数、进入 MySQL 数、成功订单数、售罄数和重复数；
- 最终库存守恒、用户订单唯一性及 Redis/MySQL 对账结果。

在报告产生前，数字只能视为待验证目标，不能作为已复现实验结论。

## 4. 推荐的实现顺序

1. **先补 Lua 准入。** 原子完成库存预扣、一人一单标记和事件写入；明确 key、过期、回滚与脚本返回码。
2. **再补可靠转发。** 若事件先进入 Redis Stream，需要可靠桥接 Kafka；若走数据库 Outbox，则重新定义 Redis 只做准入、数据库接收已受理请求的边界。
3. **补 MySQL 幂等建单。** 以业务 requestId/用户券唯一键兜底，条件扣减只作为最终正确性防线。
4. **补补偿与对账。** 覆盖预扣后宕机、Kafka 不可用、消费失败、建单失败、取消和超时未支付。
5. **最后做压测与故障实验。** 先验证正确性，再测吞吐；故障注入必须覆盖进程崩溃、消息重复和依赖短时不可用。

## 5. 如果暂时不补代码，建议改回的简历口径

可以使用仓库当前更容易自证的三条：

> **预约交易治理：** 基于 MySQL 短事务、条件扣减、唯一约束与请求幂等实现预约状态机，解决超卖、重复扣减及确认/取消/过期竞争。

> **热点缓存优化：** 采用 Redis Cache-Aside、随机 TTL、Owner 回填锁与 Lua 活动级准入，治理缓存击穿并在数据库行锁前削峰；热点目录压测下稳定处理能力由 1000 提升至 3000 QPS，P95 不高于 18.2ms。

> **候补可靠补位：** 基于 Kafka Outbox/Inbox 解耦名额释放与候补补位，按场次分区并在 MySQL 事务内完成 Inbox 去重与 FIFO 多人补位，保证重复投递和故障恢复下业务效果一致。
