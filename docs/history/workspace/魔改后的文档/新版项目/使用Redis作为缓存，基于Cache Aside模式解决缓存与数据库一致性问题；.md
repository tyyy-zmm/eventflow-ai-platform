# Cache-Aside 与数据库一致性｜新版深挖

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 1. 先定义一致性目标

商家展示信息允许秒级短暂陈旧，因此目标是可解释、可界定的最终一致性，而不是 Redis 与 MySQL 每时每刻完全相同。秒杀库存和订单状态属于交易事实，不能直接套用普通 Cache-Aside；它们由专门的准入、事务和对账链路治理。

## 2. 基础 Cache-Aside

读流程：先查缓存，未命中查数据库并回填。写流程：在数据库事务提交后删除缓存。删除而不是直接更新缓存，是为了避免维护多个缓存形态时遗漏；下一次读取再以数据库当前值重建。

基础方案仍有三个窗口：缓存删除失败；删除后并发读回填旧值；旧异步重建晚于数据库更新并覆盖新值。新版分别用持久失效任务、事务后执行和 revision/generation 防护。

## 3. 持久失效任务

业务更新与 cache invalidation task 在同一 MySQL 事务内写入。事务提交后 worker 删除缓存，成功后把任务标记完成，失败则退避重试。这样即使应用在提交后、删除前崩溃，任务仍然存在。

任务消费本身需要幂等，重复删除缓存没有副作用；但旧任务不能清理新任务或误认为新版本已完成，因此任务带 entityId、revision 和 generation。

## 4. 防止旧值回填

重建 worker 获取数据时记录 revision，写回前确认数据库 revision 没有变化，或者把 revision 放入缓存值并使用 Lua 只允许较新版本覆盖。更新动作同时使旧 owner/generation 失效。即使旧线程在更新后才完成，也不能把旧快照重新写入。

## 5. 热点重建锁

锁值必须是唯一 owner，释放时执行比较并删除：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

获取锁后再次检查缓存，避免等待期间已有其他线程完成重建。锁 TTL 防止进程崩溃永久占用，但 TTL 过短会出现多个 owner 并发重建，所以最终仍靠 revision 防旧值覆盖。

## 6. 空值缓存

数据库不存在时写入短 TTL 空值，避免恶意或偶发不存在 ID 持续回源。创建新商家后必须主动删除对应空值；否则用户会在 TTL 内继续看到不存在。空值 TTL 不宜过长，也要限制非法 ID 和批量枚举。

## 7. 和秒杀 Redis 的区别

商家详情缓存优化的是读路径，允许短暂陈旧；秒杀 Lua 管理的是瞬时资格和预扣，要求原子操作并有 MySQL 最终兜底。不能因为两者都使用 Redis，就说它们使用相同的一致性方案。

## 8. 测试用例

1. 热 key 逻辑过期时只有一个有效 owner 回源；
2. owner 锁过期后旧 owner 不能删除新锁；
3. 数据库更新与慢重建竞争时旧值不能覆盖新 revision；
4. 缓存删除失败后持久任务能够重试；
5. 新建商家会清理旧空值；
6. Redis 停机时数据库回源并发保持有界；
7. 线程池饱和时明确降级，不无限堆积任务。

指标包括数据库访问量、QPS、P95/P99、重建并发、失败重试次数和陈旧持续时间。缓存命中率不是唯一目标，高命中但长期返回错误旧值同样不合格。

## 9. STAR 逐字稿

> **Situation：**商家详情访问集中，热点 key 到期会产生集中回源；同时更新与异步重建竞争可能把旧值重新写回。**Task：**在降低数据库访问量的同时，把允许陈旧时间和更新一致性控制在业务可接受范围。**Action：**我采用 Cache-Aside 和随机 TTL，热点数据使用逻辑过期与 owner 锁异步重建；更新时把失效任务与数据库修改同事务记录，提交后重试删除，并用 revision/generation 阻止旧 worker 覆盖。**Result：**热点目录实验中稳定处理能力由约 1000 提升到 3000 QPS、P95 不高于 18.2ms，同时通过更新竞争和故障用例验证旧回填不会覆盖新数据。这个数字只对应缓存目录链路，不用于证明秒杀订单吞吐。

## 10. 压力追问

### 为什么不用 Canal 监听 binlog？

当前项目规模用持久失效任务已经能形成闭环，引入 Canal 会增加部署和运维复杂度。数据源和缓存消费者更多时再评估 CDC。

### 为什么不用本地 Caffeine + Redis 二级缓存？

二级缓存会增加实例间失效和版本传播问题。现阶段瓶颈实验没有证明需要，所以先保持单层 Redis。

### 删除缓存失败会不会永久不一致？

失效任务持续重试，TTL 提供最终兜底，并对任务积压和最老年龄告警。这里仍是最终一致性，不承诺零时间窗口。

### QPS 为什么只能作为缓存数据？

因为测试接口、业务工作量和瓶颈不同。目录查询主要是读和序列化，秒杀还涉及 Lua、Kafka、事务建单与状态轮询，不能跨接口复用吞吐数字。

## 11. 事实边界

缓存模块有对应代码、验收与性能材料，但当前简历没有单列这一条。面试中把它作为 Redis 能力扩展即可，不要为了展示缓存而挤掉秒杀、交易一致性或 Kafka 主线。
