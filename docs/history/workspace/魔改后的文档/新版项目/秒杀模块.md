# 秒杀模块｜从旧版方案到新版可靠链路

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 1. 当前简历对应内容

> **秒杀防超卖：** 基于 Redis Lua 脚本完成库存预扣与一人一单校验，将售罄和重复购买请求拦截在数据库前；本地压测下系统入口 QPS 达到 2000，进入 MySQL 的请求减少 90%；并发与故障测试中无超卖、无重复订单。

> **交易一致性：** 采用 MySQL 条件扣减与唯一约束兜底订单及库存正确性；在业务事务内记录补偿任务，结合幂等状态机与超时对账，处理 Redis 预扣后宕机、建单失败及订单取消等异常，保证 Redis 与 MySQL 最终一致。

> **异步建单：** 基于 Kafka 异步建单，通过发送重试与消费幂等保障消息可靠处理，提高并发性能，保障已受理请求可恢复、订单不重复。

## 2. 背景

限量优惠券会在开放瞬间承受大量并发请求。系统不仅要快，还必须满足四个不变量：库存不能为负、同一用户只能购买一次、重复消息不能生成重复订单、已经受理的请求在进程或 Kafka 短时故障后仍能恢复。

旧版只强调“Redis Lua 原子，所以不会超卖”。这只能证明 Redis 视角的预扣和资格判断原子，不能自动保证 Redis、Kafka 和 MySQL 三个系统之间的一致性。新版需要同时设计准入、可靠传递、最终落库和补偿对账。

## 3. 完整链路

```text
客户端携带稳定 requestId
  -> 鉴权、活动时间和参数检查
  -> Redis Lua 原子执行
       检查库存
       检查一人一单
       预扣库存
       记录用户资格/待处理事件
  -> 返回“已受理”，而不是“订单成功”
  -> 事件可靠转发 Kafka
  -> 消费者按 requestId 幂等处理
  -> MySQL 事务内：条件扣减 + 用户活动唯一约束 + 创建订单 + 更新请求终态
  -> 成功后确认消费
  -> 失败时记录补偿，回滚 Redis 预扣
  -> 超时扫描与 Redis/MySQL 对账
```

Redis 负责挡住大量售罄、重复和超限请求；Kafka 把入口与数据库写解耦；MySQL 是订单和权威库存的最终真相。三层不是重复保障，而是分别解决性能、传递和正确性。

## 4. Redis Lua 为什么仍然需要

如果每个请求都先查 MySQL 是否买过，再执行带 `stock > 0` 的更新，会造成大量数据库查询、行锁竞争和连接占用。Lua 将资格判断前置到内存层，并在一个脚本中完成检查和写入，避免“先查库存、再扣库存、再记录用户”之间被其他请求插入。

典型键设计：

- `seckill:stock:{activityId}`：剩余准入名额；
- `seckill:buyers:{activityId}`：已通过准入的用户集合；
- `seckill:req:{requestId}`：请求受理状态和参数摘要；
- 待处理事件：可写 Redis Stream，或转入另一套可靠事件记录。

活动 ID 使用相同 hash tag，便于 Redis Cluster 中的 Lua key 落在同一 slot。实际项目是否已验证 Cluster，需要以部署和测试为准。

## 5. MySQL 如何兜底

Lua 成功不等于订单已经创建。消费者落库时仍执行：

```sql
UPDATE activity_stock
SET stock = stock - 1
WHERE activity_id = ? AND stock > 0;
```

并建立 `UNIQUE(user_id, activity_id)`。条件扣减保证 MySQL 库存不为负，唯一约束保证并发消费者无法为同一用户生成两张订单。扣减、建单和请求终态必须位于同一个本地事务中，任何一步失败都整体回滚。

这是一种双层校验：Redis 主要削峰，MySQL 负责最终正确性。Redis 与 MySQL 的库存短时间不同并不必然是错误，但最终必须通过补偿和对账收敛。

## 6. Kafka 如何保证可恢复

Kafka 采用至少一次语义，而不是宣传 exactly-once。发送可能重试，消费也可能重复，因此消息包含稳定 `eventId/requestId`，消费者先检查持久请求状态，已经成功或失败的请求直接返回原结果。

两个关键崩溃窗口：

1. **订单事务已提交、消费位点未确认：**消息会重投，消费者根据 requestId 或唯一约束识别已完成请求，不再次扣库存。
2. **Redis 已预扣、事件尚未进入 Kafka：**需要可靠事件记录和转发重试；若最终无法处理，由超时任务生成补偿并恢复 Redis 资格。

不能只说“Kafka 开启 ack 就不会丢”。Broker 确认只能解决 Kafka 内部的一部分可靠性，跨 Redis/MySQL 的故障仍需业务状态机和对账。

## 7. 取消、失败与对账

请求状态可设计为 `ACCEPTED -> PROCESSING -> SUCCEEDED/REJECTED/EXPIRED`，订单状态可设计为 `PENDING_CONFIRM -> CONFIRMED/CANCELLED/EXPIRED`。状态更新使用条件转换，终态不能被迟到消息覆盖。

补偿动作必须幂等。每个请求只允许一次 Redis 回补，取消订单时 MySQL 订单状态变更和权威库存释放在同一事务内，再由补偿任务同步 Redis。定时对账比较：Redis 预扣数、MySQL 有效订单数、请求终态和待补偿任务，发现差异后按 requestId 重放或人工介入。

## 8. 实验与数字口径

简历的 2000 QPS、MySQL 请求减少 90%、无超卖和无重复，必须来自同一个秒杀入口实验，不能拿商家目录缓存 QPS 替代。报告至少保存 commit、机器配置、并发、库存、时长、平均/稳定/峰值 QPS、P95/P99、错误率、Redis 准入数、MySQL 请求数、成功订单数和最终对账结果。

当前仓库主线已有 MySQL 权威交易、Redis 准入/缓存和 Kafka Outbox/Inbox 能力，但与“Redis 真实库存预扣 + Kafka 主订单异步建单”并不完全一致。因此数字在新链路完整实现并复跑前只能视为简历历史记录或待验证目标。

## 9. 两分钟逐字稿

> 这个模块解决的是秒杀场景既要扛住瞬时并发，又不能因为异步链路产生超卖、重复订单或请求丢失。入口先用 Redis Lua 原子检查库存和一人一单，并完成预扣，把售罄和重复请求挡在数据库前。Lua 成功只表示请求已受理，事件随后可靠转发到 Kafka。消费者在 MySQL 本地事务里通过库存大于零的条件扣减和用户活动唯一约束创建订单，并按 requestId 做消费幂等。Redis 预扣后如果进程宕机、消息长期未处理或建单失败，会生成幂等补偿任务；取消和超时也通过状态机及定时对账让 Redis 与 MySQL 最终收敛。Redis 解决入口压力，Kafka 解决异步削峰，MySQL 才是最终正确性的兜底。

## 10. 高频追问

### Redis 已经预扣，为什么 MySQL 还要条件扣减？

Redis 可能故障、丢数据、被误恢复或与 MySQL 暂时不一致。MySQL 是订单事实来源，必须独立守住库存不为负。

### 为什么不是百分之百请求都被 Redis 拦截？

合法成功请求必须进入后续建单链路；系统还可能有查询、状态恢复或补偿请求。所谓减少 90% 指特定“千人抢百券”负载下，约 100 个有效准入请求进入落库，其余售罄或重复请求被前置拒绝，不是任何流量下固定比例。

### 一人一单只靠 Redis Set 可以吗？

不够。Redis Set 用于快速准入，MySQL `UNIQUE(user_id, activity_id)` 才是最终约束。规则若变成一人 N 单，需要计数结构和数据库侧相应唯一/计数模型。

### Kafka 堆积怎么办？

先看 lag、最老消息年龄、消费者错误和数据库瓶颈；限制新请求准入，按活动分区并在安全范围扩消费者。不能只无限扩容消费者，否则会把压力重新打到 MySQL。

### 为什么不使用分布式锁？

Lua 原子脚本和数据库唯一约束可以直接表达资格与唯一性，锁会增加网络开销、租约和误释放问题。只有无法用原子操作或约束表达的复合临界区才考虑锁。

## 11. 事实边界

本文描述的是当前简历所需的完整可靠方案。当前仓库已实现的 EventFlow 主线更偏向 MySQL 权威扣减、Redis 准入缓存和 Kafka 候补补位；两套架构不能在面试时混成“同一条已全部上线的链路”。
