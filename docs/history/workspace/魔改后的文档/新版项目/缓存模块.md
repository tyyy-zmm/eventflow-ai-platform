# 缓存模块｜旧版能力在新版项目中的位置

> 历史材料（归档于 2026-10-03）：下文“当前”“最终”“待实现”等说法只指原记录日期，不代表合并版状态。请先读[生活优选当前入口](<../../../../../README.md>)和[当前验收](<../../../../合并验收.md>)。旧压测、预约体系和简历口径不可直接套用到合并版。标有 `_archive/` 的源码/原始实验仅保存在本地归档，不包含在本仓库。

## 1. 为什么保留这篇文档

当前简历四条没有单独写商家缓存，但缓存仍是生活优选实际项目的重要基础能力，也能支撑面试官对 Redis 的扩展追问。这篇不应抢占秒杀主线，而应作为“项目还有哪些后端优化”的补充回答。

## 2. 业务分类

不是所有数据都采用同一缓存策略：

- 商家名称、地址、介绍等可容忍短暂陈旧，适合 Cache-Aside、随机 TTL 和逻辑过期；
- 活动详情可缓存展示字段，但资格、库存和订单状态不能依赖陈旧缓存做最终判断；
- 不存在的商家可使用短 TTL 空值缓存防穿透；
- 秒杀库存采用专门的 Lua 准入模型，不与普通详情缓存混用。

## 3. 读取链路

```text
读取商家
  -> 查询 Redis
  -> 命中正常数据：返回
  -> 命中空值：返回不存在
  -> 逻辑未过期：返回
  -> 逻辑过期：尝试获取 owner 锁
       获取成功：有界线程池异步重建
       获取失败：在允许陈旧窗口内返回旧值
  -> 冷缓存/硬过期：有界等待或明确降级
```

随机 TTL 用于降低大量 key 同时失效；逻辑过期用于热点 key 在重建期间继续服务；两者解决的问题不同。

## 4. 为什么旧版互斥锁实现不够

固定锁值和直接 `DEL` 可能误删别人的锁：A 的锁过期后 B 获得新锁，A 重建完成直接删除 key，会删除 B 的锁。新版锁保存随机 owner，释放时通过 Lua 比较 owner 后删除。回填也要检查 generation/revision，旧 worker 不能覆盖更新后的新数据。

线程池必须有界。若热点 key 大量过期，无界重建任务会耗尽内存；数据库回源也要设置超时和并发上限。

## 5. 更新一致性

普通 Cache-Aside 的典型写法是先更新数据库，事务提交后删除缓存。它提供最终一致性，不是强一致。若删除失败，需要把失效任务与业务更新一起持久化，提交后重试；TTL 作为最后兜底。

项目进一步使用 revision/generation 防止旧回填覆盖：数据库更新时 revision 增加并记录失效任务；异步重建读取 revision，写回前确认仍为当前代次。这样可以处理“更新已经完成，但旧重建线程稍后把旧值写回来”的窗口。

## 6. 缓存三类经典问题

- **穿透：**请求不存在的数据。使用参数校验、短 TTL 空值缓存和必要的布隆过滤器；本项目规模下空值缓存已足够。
- **击穿：**热点 key 到期瞬间大量回源。使用逻辑过期、owner 锁、双重检查和有界重建。
- **雪崩：**大量 key 同时到期或 Redis 故障。使用 TTL 抖动、限流、熔断和有界回源，不能让所有请求直打数据库。

## 7. 性能与正确性怎么测

对比直读数据库、普通 TTL 和优化缓存三种模式，覆盖热命中、冷启动、跨 TTL、慢回源和更新竞争。记录 QPS、P95/P99、数据库查询数、重建次数、线程池拒绝和最大陈旧时间。

当前项目材料中更可信的缓存实验是热点目录稳定处理能力约 1000→3000 QPS、P95 不高于 18.2ms；它是缓存路径数字，不能拿来证明秒杀建单入口 2000 QPS。

## 8. 一分钟回答

> 商家详情属于读多写少并允许短暂陈旧的数据，我采用 Cache-Aside，并用随机 TTL 分散过期时间；热点 key 逻辑过期后先返回有限期旧值，再由持有唯一 owner 锁的线程异步重建。更新时先提交数据库，再通过持久失效任务删除缓存，并用 revision 防止旧重建结果覆盖新数据。交易资格和库存不使用这套陈旧缓存做最终判断，而是走 Redis Lua 准入和 MySQL 事务兜底。

## 9. 常见追问

### 为什么不先删缓存再更新数据库？

删缓存后数据库尚未提交时，另一个读请求可能把旧值重新写入缓存，形成更长脏数据窗口。更新数据库后删缓存更常见，但删除失败仍需重试任务和 TTL 兜底。

### 延迟双删是不是万能的？

不是。延迟时间难以覆盖不同事务和网络延迟，进程崩溃也会丢第二次删除。持久失效任务更容易审计和重试。

### 逻辑过期会返回脏数据吗？

会，所以只适用于业务允许短暂陈旧的展示数据，并设置最大陈旧窗口。库存、订单状态等强业务判断不能直接用旧值。

### Redis 故障是否全部回源 MySQL？

不能无界回源。应限流、熔断并只允许有界流量降级，否则缓存故障会进一步击穿数据库。
