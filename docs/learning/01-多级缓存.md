# 多级缓存：当前实现与讲解

更新：2026-10-03。代码依据：`ShopCache`、`ShopBloom`、`CacheCircuit`、`CacheOperations`。这是本项目实现说明，网络文章中的数字不作为本项目测试结果。

## 为什么做

商家基础信息读多写少。只查 Redis 会让每次请求都经过网络；不存在的商家 ID 还可能反复回源。Redis 故障时，如果直接把流量全放给数据库，会扩大故障。

## 查询流程

1. 先查 Caffeine，本地最多 10,000 条，正常可用时间最多 1 秒，并受原始数据硬过期时间约束。
2. Redis 读熔断时，使用仍在允许时间内的本地数据，否则进入限量数据库回源。
3. 本地 Bloom 判断商家 ID。判断可能存在则继续；判断不存在时，还要查共享新增 ID 集合，避免另一实例刚新增的商家被误拦。
4. 查 Redis。软过期可返回旧值，并抢分布式锁异步重建；超过硬过期不能继续返回。
5. 无缓存时抢锁回源。数据库读取最多 4 个并发；异步重建 2 个线程、队列 16，队列满会拒绝重建。

默认 Redis 软过期 5 秒，硬过期 15 秒并加最多约 10% 随机量；空值缓存 1 秒。保留物理过期，是为了限制旧数据存活时间，因此没有照搬“逻辑过期后永不过期”。锁带所有者标识，Lua 校验后才能写缓存或解锁，防止过期锁持有者覆盖新值。

## Bloom 为什么不能直接照文章写

按 100 万条、1% 目标误判率设置位数组，使用 7 次哈希探测。1% 是容量模型目标，不能理解成任意输入下的保证；误判为存在仍可能查数据库。

各实例持有不可变快照，每天凌晨 3 点重建。新建商家必须在数据库事务中先登记共享 Redis 集合，再写商家。重建和新增都锁定数据库中的 `ux_shop_index_guard`，防止 Redis 索引丢失时，重建漏掉尚未提交的新增商家。登记失败则拒绝新增；事务回滚遗留集合元素只造成误判为存在。

快照和共享集合通过 epoch 对应。集合丢失、epoch 改变或 Redis 不可用时放行到后续受保护的查询，不把故障解释为“商家不存在”。新建入口和演示数据入口都经过登记；外部绕过应用直接插表不在保证范围内。

共享集合目前不清空，否则仍持有旧快照的实例可能漏判；集合大小会随新增商家数增长，这是当前运维限制。本地 Bloom 判定不存在后仍需要一次 Redis 校验，不能声称“非法 ID 零网络开销”。重建持有互斥行锁，会短暂阻塞新增商家，适合当前低频新增场景，不能无限放大到高频商家写入。

## 故障降级与恢复

连续 5 次 Redis 读失败会熔断。另统计最近 60 秒、最多 1000 个读样本，至少 20 个样本后，错误比例超过 5% 或耗时超过 100ms 的比例超过 1% 也会触发。这里是慢调用比例，不是计算出的 HTTP P99。

熔断后，本地旧值额外允许最多 1 秒，仍不得超过原始硬期限。数据库降级每实例每秒最多 20 次，并受 4 并发限制，超限返回 503。这个上限不是整个集群的总上限。

每秒探测 Redis，连续 5 次健康探测后允许约 10% 请求试探；健康保持 10 秒再恢复。试探失败重新熔断。没有实现全量预热，也不返回伪造的默认商家。

## 更新与观测

更新商家时，数据库事务内写入失效任务。后台删除 Redis 值和重建锁，并广播本地失效；失效失败保留任务重试。代际校验防止旧回填跨过失效通知重新进入本地缓存。

管理员接口：`GET /v2/admin/cache`；`POST /v2/admin/cache/degradation`，JSON 为 `{"enabled":true}` 或 false；`POST /v2/admin/cache/bloom/rebuild`。管理员权限检查沿用现有 Auth。

Micrometer 暴露 `life.cache.events`、`life.cache.bloom`、本地条数、Bloom 就绪和熔断状态。当前只有指标及管理接口，尚未交付新的 Prometheus/Grafana 部署和看板。

## 面试时怎么讲

“我给商家基础信息加了本地缓存和 Bloom，并处理了多实例新增商家的漏判问题。Redis 异常时限制数据库回源，恢复时小比例放量。缓存保留硬期限，避免旧数据无限存活。”
