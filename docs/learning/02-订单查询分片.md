# 订单查询分片：保留交易本地事务

更新：2026-10-03。代码：`OrderProjection`、`OrderProjectionApi`、`Trading`，迁移 V8。

## 先说明实现范围

当前实现是**同一个物理数据库内的 32 张订单查询分表**，不是四个数据库，也未引入 ShardingSphere。按用户路由的查询已经实现；跨物理数据库连接、迁移切流与容灾还没有实现。现有交易订单不迁走、不删除。

选择显式 JDBC 路由，是因为当前只有一个固定的用户维度读模型，不需要解析任意 SQL。后续确需多数据源和复杂路由时，再评估 ShardingSphere；不能把它写成当前技术栈。

## 为什么不把库存与订单一起拆

库存扣减、订单建立和请求状态更新留在原数据库事务里。同一活动的行锁负责串行裁决。订单按用户拆库并不能消除这个库存热点，反而会使库存与订单跨库。

查询分表承接用户订单历史，关键状态和刚下单结果继续查交易库。读模型短暂落后不会影响确认、取消或库存裁决。

## 数据怎么过去

1. 建单、确认、取消和过期时，在同一个交易事务里写 `ux_order_projection`，增加版本号。订单回滚，任务也回滚。
2. 每秒取最多 100 个待同步订单，用同一条 SQL 读取源订单及对应版本。
3. 按 `floorMod(user_id,32)` 路由到 `ux_order_read_00` 到 `ux_order_read_31`。
4. 目标表按订单 ID 唯一；只有更高版本能更新状态。重复和迟到的旧版本都不能让状态倒退。
5. 目标写入成功后，按版本条件确认源任务。中途崩溃会重试；若源状态已经变化，不会误确认新版本。

当前同步器直接轮询持久化任务，不通过 Kafka。Kafka 仍用于秒杀异步建单，两条链路不要混为一谈。

## 接口与安全

`GET /v2/account/order-history?page=1`：从登录态取得 user_id，按用户定位一张表，每页 20 条，响应标明 `consistency: eventual`。用户不能指定别人的 ID。前端“我的订单”提供“查看历史查询”入口，并明确提示短暂延迟；确认、取消和待处理请求仍使用交易库实时列表。

`GET /v2/admin/order-projection`：查看积压量、最早变更时间、失败计数和当前物理库/表数量。

`POST /v2/admin/order-projection/replay?after=...`：按订单 ID 游标，每次最多标记 100 条重放。用返回的 next 继续，count=0 停止。V8 首次迁移也会给历史订单生成同步任务。重放不是删除交易数据，也不是完成数据归档。

## 能讲什么、暂时不能讲什么

可以讲路由、事务内同步意图、至少一次投递、版本防倒退、故障重试和游标补数。不能讲已完成四库八表、分布式事务、自动扩容或查询性能提升多少。

同步任务目前持续保留，每次查询待处理版本需要评估大数据量下的扫描成本。后台每 5 秒按订单 ID 游标核对最多 100 条源订单，检查查询分表是否缺失，或状态、价格、确认期限是否不一致；发现差异后提升投影版本并走正常幂等同步。扫描游标到末尾后重新开始，指标记录检查、修复和失败次数。

当前仍无独立冷归档、物理读写资源隔离；核对只覆盖订单事实字段，商家展示字段随下一次订单投影更新。将来改变分片数需要迁移方案，不能直接修改 32。

面试表达：“我先把订单查询拆成异步读模型，保留库存和建单的本地事务。按用户路由避免历史查询扫描所有分表，使用版本条件更新防止重复同步和旧消息覆盖新状态。目前验证的是同库分表与同步正确性，尚未证明大规模性能收益。”
