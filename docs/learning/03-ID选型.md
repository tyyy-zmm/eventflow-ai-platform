# 分布式 ID：当前保留 UUID

更新：2026-10-03。当前请求、订单和事件 ID 来自 `Trading.uuid()`，数据库列为 VARCHAR(36)。本轮未实现 Snowflake，也没有迁移历史 ID。

## 为什么查询分片没有强迫我们换 ID

当前订单 ID 已使用随机 UUID，数据库主键负责约束本表唯一性；查询路由依据 user_id，不依赖订单 ID 编码。UUID 不需要租赁 worker，也不依赖系统时钟严格递增。它的代价是字段和索引较大、主键写入缺乏时间局部性。

原文“原项目全靠自增 ID”不符合我们的现状，不能照讲。我们的改造目标优先是缓存与交易可靠性，因此暂时保留已验证的 ID 方案。

## 如果后续确实换成 Snowflake

需要同时处理 worker 租约失效、进程长暂停、时钟回拨、重启后的时间上界、不同机房编码以及号段降级的命名空间。Redis 不可用时继续复用已经失效的 worker，会有冲突风险；号段与 Snowflake 也不能直接混用同一数字空间。

必须先测试跨进程唯一性、时钟回拨和租约接管，再灰度写新 ID 并保持旧 ID 可读。当前没有这些实现和证据，不写进“已完成”的简历内容。

面试表达：“当前用 UUID，优先保证无中心生成和旧订单兼容。分片按用户路由，因此不需要为了路由先换 ID。紧凑有序 ID 是后续针对索引空间和写入局部性的优化，不能只换一个算法就说完成分布式 ID 服务。”
