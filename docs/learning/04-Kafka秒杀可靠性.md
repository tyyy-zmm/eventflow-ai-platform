# 秒杀可靠性：当前 Kafka 实现

更新：2026-10-03。按已确认选型保留 Kafka。相关代码：`Reservations`、`Trading`、`Delivery`、`KafkaErrors`、`Admission`。

## 一次请求的真实路径

Redis Lua 预占库存 → 当前入口限流及积压检查 → 数据库验 epoch 并写 ACCEPTED 请求和 Outbox → 后台发布 Kafka → 消费事务校验事件并建单 → 提交后确认消费 → 持久化动作将 Redis 预占转为确认。

当前限流位于预占之后，不要说已经把全部拦截前移。HTTP 接受成功只表示进入处理，SUCCEEDED 表示已经建单，不是支付成功。订单还需在 5 分钟内确认。

新增模拟支付和延迟关单流程见[第六章](06-延迟关单与模拟支付.md)。建单事务同时持久化关单任务，ZSet 到期触发、MySQL 到期扫描兜底；库存释放仍沿用本章的事务和补偿机制。Kafka 不负责延迟投递。

## 为什么需要 Outbox

请求和 Outbox 在同一数据库事务里提交，避免只落请求却忘发消息。发送成功后才标记 sent_at；发送后进程崩溃可能重复发，因此不能声称只发送一次。

生产者配置 acks=all 和幂等发送。消费端仍用数据库约束和请求终态判断去重，不能把生产者幂等当成业务恰好一次。消费事务提交后再提交 offset。

## Redis 与数据库之间的空隙

Redis 预占不与 MySQL 构成原子事务。预占后请求未成功落库时，后台按请求裁决是否释放；裁决与接收共用活动行锁。过期裁决留下持久化终态，防止延迟请求稍后又建立有效订单。

Redis 恢复使用 epoch 隔离旧预占。确认、取消和过期产生持久化 Redis 动作，补偿失败可以再执行。恢复不能简单扫描库存并覆盖后直接放行。

## 重复、乱序与补偿

数据库中活动与用户组合唯一，条件扣减保证 available 不小于零。订单取消/过期只有第一次状态转换归还库存。同一用户取消后也不能重买同场，这是当前业务规则。

格式错误的 Kafka 消息写入 ux_poison 后确认；基础设施错误保留重试。当前没有 RabbitMQ confirm/return、TTL 死信队列，也没有实现同等的有界业务死信主题；不要沿用原文章的这些术语描述代码。

Outbox 发布重试有退避，延迟最高 60 秒，但并非达到固定次数后永久丢弃。运维重放有审计记录。订单查询分表的版本同步属于另一条持久化任务链。

面试表达：“重点是各个失败窗口都有可恢复的数据库状态。Redis 负责快路径预占，数据库负责最终裁决；Kafka 允许重复投递，由业务幂等消除重复效果。”
