# 验证与压测：只讲自己跑出的结果

更新：2026-10-03。

## 本轮验证方法

在项目根目录执行 `bash backend/scripts/verification.sh package`。使用 life_choice_verification 库、Redis DB13 和验证专用 Kafka 配置，不连接业务库执行测试。不要同时启动另一台使用相同验证消费组的应用。

新增测试覆盖 Bloom 插入无漏判、固定样本误判率、共享新增 ID、索引丢失放行；熔断阈值和探测恢复；订单与同步任务共同回滚、目标写入后未确认的重试、重复/旧版本同步、按用户隔离和补数。MySQL 测试还检查实际 upsert 不让终态倒退。

最终回归执行 `bash backend/scripts/verification.sh package`，125 项后端测试全部通过，失败、错误和跳过均为 0。测试包括真实 MySQL、Redis、Kafka、Flyway V10 迁移和 HTTP 集成；正确性测试本身不等于吞吐量结论。

## 本轮缓存 A/B

2026-10-03 在同一台本机运行双 JVM，每个堆 384MiB，总并发 8；对同一热点商家分别测试数据库直读、Redis TTL 和多级缓存。三种模式交错运行，每种预热 100 次后持续 30 秒，共三轮。闭环请求下，吞吐会随响应速度变化，因此比较三轮中位数，并保留每个请求的原始样本。

| 模式 | QPS 中位数 | P95 中位数 | P99 中位数 | 三轮错误率 | 三轮数据库读取 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 数据库直读 | 6,223.60 | 2.392ms | 3.790ms | 0% | 568,875 |
| Redis TTL | 7,569.02 | 2.115ms | 3.761ms | 0% | 48 |
| Caffeine + Redis | 17,689.65 | 1.093ms | 2.256ms | 0% | 18 |

多级缓存相对数据库直读的 QPS 中位数为 2.84 倍，P95 降低 54.3%；相对 Redis TTL 的 QPS 中位数为 2.34 倍，P95 降低 48.3%。这是成功商家基础信息接口的本机热点结果，不是详情页、整站或秒杀下单吞吐。证据位于 `docs/verification/2026-10-03-final/`，本地保留约 171MiB 原始样本。

订单查询分表要在相同数据量和查询形态下比较；32 张表本身不等于 32 倍性能。当前同库也没有带来物理 CPU/IO 隔离。

## 原文数据怎么处理

网络文章的 18.99→7.45ms、5000 用户或其他截图只属于其作者的实验，不填进本项目简历。用户数不是并发数，也不是 QPS。库存未卖完可能与限流、Token 过期、压测脚本或处理能力有关，需要逐请求原因和受控实验定位。

本项目本轮没有实现新的 15 秒资格 Token。Bloom、熔断和恢复已通过自动化正确性与真实中间件回归，但没有通过停止共享 Redis 的方式重新做故障性能压测；不能据此给出故障期间 QPS 或恢复秒数。已有历史压测仍受原代码版本、接口、负载和环境限制，不能重新标成这次改造的结果。
