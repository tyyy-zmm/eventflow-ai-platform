# 延迟关单、CAS 支付和退款补偿

这章解释当前新增的后端实现。支付渠道是模拟渠道，不连接支付宝、微信等真实收单服务，不扣真实资金。默认关闭模拟支付接口，设置 `SANDBOX_PAYMENTS=true` 后开启。订单确认期限仍为 5 分钟。

## 解决什么问题

抢到优惠券后库存已经占用。如果订单一直未完成，库存必须能够释放；付款通知与关单同时发生时，不能把已完成订单取消，也不能重复回补。若订单已关闭后才收到付款通知，必须记录付款并进入退款流程。

## 一次完整流程

1. `Trading` 在建单事务里写入订单和 `ux_close_task`，截止时间来自数据库时间。任一写入失败，整笔建单事务回滚。
2. `DelayedClose` 每秒分批读取待投递任务，将请求 ID 和截止时间写入 Redis ZSet。写 Redis 失败时 MySQL 任务仍然存在；每 30 秒允许重新投递，便于恢复丢失的索引。
3. 每秒从 ZSet 查询到期任务，但不提前删除。调用关单事务，确认处理完成后再删除 Redis 成员。
4. 每 10 秒直接扫描 MySQL 到期未完成任务作为兜底。Redis 不可用或重启丢失 ZSet 时，依然可以关闭订单。每批最多 100 条，不承诺精确到毫秒关闭。
5. 用户创建模拟支付单，金额取订单记录，不能由客户端修改。模拟付款通知带固定渠道流水号，同一流水重复通知返回已有结果。
6. 支付确认与关单沿用活动行锁协调库存恢复，并执行带旧状态条件的订单更新。只允许 `PENDING_CONFIRM` 转换为 `CONFIRMED`、`CANCELLED` 或 `EXPIRED`。到期后收到付款，即使关单任务尚未执行，也会先关闭并退款。
7. 只有首次关单成功才能回补 MySQL 库存，并在同一事务写入原有 Redis 库存补偿任务；重复执行不再回补。
8. 关闭后的付款，以及已付款后另一笔不同流水的重复扣款，都生成 `ux_refund` 任务。退款失败退避重试，单次退避最高 60 秒，不直接丢弃。

## CAS 到底保证什么

`UPDATE ... WHERE state='PENDING_CONFIRM'` 是带条件的状态更新，依据影响行数判断是否首次转换成功。它保证本地订单状态不会被迟到操作覆盖。当前实现仍保留活动行锁，不能声称只靠 CAS 就完成所有库存恢复协调。

付款已在外部发生时，本地更新失败不会自动退钱。因此收到关闭订单的付款通知，必须在事务中记下收款流水和退款任务。模拟渠道通过 `ux_sandbox_refund` 唯一流水记录模拟退款效果；渠道退款与本地退款确认分别提交，测试覆盖渠道成功后本地未确认的重试，不会产生第二次渠道退款。

## 接口与演示

自动演示命令：`bash backend/scripts/verification.sh payment-demo`。使用隔离验证库、Redis DB13 和验证 Kafka 配置，演示正常支付、重复通知、取消后付款退款、后台超时关单后退款，并检查库存不变量。结果写入 `backend/evidence/payment-demo-*/results.json`。

接口沿用登录 Cookie、用户归属校验和 CSRF；不是可公开调用的第三方支付回调。

| 操作 | 接口 | 请求内容 |
| --- | --- | --- |
| 创建或读取已有支付单 | `POST /v2/account/payments` | `{"requestId":"已有建单请求ID"}` |
| 查看支付状态 | `GET /v2/account/payments/{id}` | 无 |
| 模拟付款成功通知 | `POST /v2/account/payments/{id}/sandbox-receipt` | `{"channelId":"sandbox_receipt_001","amountCents":990}` |

正常演示：先建单，再创建支付单，按真实订单金额通知付款，返回 `APPLIED`。重复使用同一 `channelId` 不重复建单或收款。取消后再通知付款，返回 `REFUND_PENDING`，后台完成后为 `REFUNDED`。已经创建支付单的订单不能再绕过支付接口直接调用旧确认接口。

为兼容旧页面，订单仍使用 `CONFIRMED` 表示完成，支付事实以 `ux_payment` 和 `ux_payment_receipt` 为准。旧页面的手动确认不能称为真实支付；本轮新增的是可通过 API 演示的模拟支付后端。

## 失败与恢复

| 失败窗口 | 恢复方式 |
| --- | --- |
| 建单事务中断 | 订单和关单任务一起回滚 |
| MySQL 已提交，尚未写 ZSet | 后台重新投递，数据库到期扫描兜底 |
| 取到 ZSet 任务后中断 | 未提前移除；下次继续处理 |
| 关单成功、尚未移除 ZSet | 重复执行读取终态，不重复回补 |
| 支付回调重复 | 固定渠道流水唯一去重 |
| 关闭后付款 | 持久化退款任务，不复活订单 |
| 退款渠道失败 | 退避重试，任务保持未完成 |
| 渠道退款成功、本地确认失败 | 用同一渠道流水重试，渠道端幂等 |

`life_business_close_overdue` 和 `life_business_refund_pending` 指标用于查看到期任务及退款积压。

## 简历表述与范围

基于 **Redis ZSet 和持久化任务**实现延迟关单，通过 **CAS 条件更新**处理模拟支付与关单并发，防止订单状态覆盖及库存重复回补；支持遗漏任务补偿和关单后付款的退款处理。

尚未接入真实支付渠道的签名验证、查单、主动关单、资金对账和真实退款 API。接入时必须以渠道事实补齐这些流程，不能把当前模拟账本称为真实资金闭环。
