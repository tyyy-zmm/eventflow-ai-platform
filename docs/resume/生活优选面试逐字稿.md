# 生活优选面试逐字稿

实验环境和逐轮数据见[数据复核记录](../verification/2026-10-03-cache-payment-audit/README.md)。支付关单讲解见文末，渠道为模拟渠道。

## 两分钟主线

这个项目基于黑马点评，我把重点放在商家缓存和优惠券秒杀。用户可以注册登录、浏览商家、抢券、查看异步结果、确认或取消订单；售罄后还能进入候补。后端使用 Spring Boot、MySQL、Redis 和 Kafka。

读链路是 Caffeine、Redis、MySQL。Caffeine 减少网络往返，Redis 使用软硬过期和带所有者的回填锁，MySQL 回源受并发与速率限制。为了拦截大量不存在的商家 ID，我增加了本地 Bloom。但多实例新增商家会产生漏判风险，因此 Bloom 判定不存在后，还会检查 Redis 中的共享新增 ID；索引丢失时选择放行，不把故障误判成商家不存在。

写链路先由 Redis Lua 预占库存，再由 MySQL 在同一事务中保存请求和 Outbox。Kafka 消费端锁定活动行、条件扣减并建立订单，数据库提交后再确认消息。Outbox 和 Kafka 都可能重复，所以最终依赖请求终态、订单唯一约束和幂等状态机消除重复效果。Redis 和 MySQL 不是分布式事务，预占后的失败通过持久化补偿动作和 epoch 恢复收敛。

历史订单查询没有拆开交易事务。我保留库存、建单和状态更新的本地事务，把订单异步投影到按用户路由的 32 张查询表。同步至少一次，目标表只有更高版本才能更新，后台还会游标核对源订单，发现缺行或状态不一致后自动补数。前端把它明确标成最终一致，确认和取消仍然查交易库。

最后我补了 Micrometer、Prometheus 和 Grafana，监控缓存命中与熔断、Outbox、补偿及投影积压。本轮 138 项后端测试通过。缓存 A/B 使用正常 Cookie 会话、20 个商家、双 JVM、总并发 8，每种模式三轮各 30 秒，多级缓存的吞吐中位数从 Redis TTL 的 6,204 提升至 8,396 req/s，P95 从 1.882 降至 1.707ms。基线有 5 次 503，三轮也有明显波动，所以只把数字描述为本机商家基础信息接口的实测，不当作整站容量。

## 五分钟缓存展开

一次查询先访问 Caffeine。L1 不会重新授予完整寿命，它继承 Redis 条目的绝对硬期限；Redis 熔断时只额外允许最多 1 秒旧值，并且不能越过硬期限。L1 未命中后，Bloom 先判断 ID；本地判断不存在仍检查共享新增集合，以解决另一实例刚创建商家的问题。

Redis 条目有软期限和硬期限。软过期时可以返回旧值，由一个请求抢锁异步重建；硬过期后必须回源。锁包含随机所有者，Lua 只有在所有者仍匹配时才允许回填和解锁，防止旧请求覆盖新值。商家更新时，数据库事务内记录失效任务，后台删除 Redis 并发布本地失效通知；通知丢失最终由有界 TTL 收敛。

连续 5 次 Redis 失败，或者最近窗口中的错误/慢调用超过阈值，会进入熔断。熔断后数据库回源每实例每秒最多 20 次，同时最多 4 个；连续 5 次健康探测后进入 10% 试探，稳定 10 秒再完全恢复。这里强调保护数据库，不承诺依赖故障时所有请求成功。

## 五分钟秒杀展开

Lua 预占解决入口快速拒绝，数据库仍是最终裁决者。请求和 Outbox 同事务提交，避免数据库已经受理却没有可靠发布状态。发布成功后才更新 sent_at；如果发送后宕机，会重新发送，因此消费必须幂等。

消费者用活动行锁统一建单、取消、过期和恢复的时序，再用 available 大于零的条件更新、活动与用户唯一键做最后防线。订单取消和超时只有第一次状态转换会归还库存。Redis 确认、释放和恢复动作先写数据库任务，再由后台执行，失败可重试。

HTTP 202 只表示请求已受理，并不表示购买成功；请求 SUCCEEDED 表示已经建立订单，订单仍可能待确认、取消或过期。项目没有真实支付与核销。

## 延迟关单与模拟支付展开

订单创建时会在同一事务生成关单任务，保留 5 分钟完成窗口。后台把任务写入 Redis ZSet，以截止时间排序，到期尝试关单。因为 ZSet 可能丢数据，数据库任务不跟着删除，还有每 10 秒的到期扫描作为兜底。只有订单事务处理成功后才移除 ZSet 成员，因此取出任务后服务中断也可以重试。

支付确认与关单都只能修改待确认状态，依据条件更新的影响行数决定是否首次生效；库存恢复仍与状态变更处于同一个数据库事务。这里保留了活动行锁，用来协调其他库存恢复路径，没有声称只靠一条 CAS 就能解决所有一致性问题。

模拟付款通知按渠道流水去重。如果关单先成功，付款通知不会把已关闭订单重新打开，而是记录收款和退款任务；另一笔不同流水重复扣款也会退款。退款渠道用固定流水幂等，渠道已退款但本地任务尚未确认时，服务重启重试不会重复退款。当前渠道是数据库实现的模拟账本，没有真实扣款和第三方回调验签。
