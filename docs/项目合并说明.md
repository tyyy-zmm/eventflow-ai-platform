## 业务边界

主线是浏览商家 → 选择优惠券 → 秒杀受理 → 异步建单 → 确认/取消/到期。候补成功后进入同样的请求和订单模型。规划只给建议，不自动创建订单。

独立 EventFlow 的多人场次预约、Bearer 账户以及 ef_* 表没有硬塞进优惠券订单模型；它们保留在归档中。旧账户、旧订单也没有自动搬库。若要恢复该产品，需要单独设计场次与优惠券的关系，不能只拷贝接口后宣称已经统一。

## 本次关键处理

- 保留生活优选原 V1–V6 校验和，新增 V7 库存 epoch；未 repair、清库或覆盖旧迁移。
- 候补补位使用 acceptReserved 并传递 epoch；已释放请求不能迟到建单；数据库结果不确定时交给补偿裁决，不直接释放库存。
- 保留售罄/重复购买的明确拒绝处理，不把它们留成“待恢复请求”。
- 演示初始化只准备未产生请求的新活动；已有活动走显式恢复。
- 规划 stub 结果明确标注 stub，修复原来被标成 deepseek 的问题。
- 后端制品统一命名 life-choice-backend；前端、CI、Compose、脚本都位于同一仓库。
